# 行程交付与局部修改

## 局部修改先判断影响面

以当前保存原文和最新授权为准。列出需要保留的日期、活动、固定资料与禁忌，在内部识别变化影响，不输出内部推理。

例如只换第二天下午活动：保留第一天、第二天早午餐及未授权其他内容；检查午餐到新活动、新活动到后续晚餐或住宿的衔接。若交通变化导致后续时段不可行，明确说明关联调整或询问取舍，不把整份计划重排成另一个旅行。

遵循 revision_scope 的页面目标与用户原话限制；旧行程取消的活动不恢复。新地点不合适或依据查询失败时保留未知，不复制旧地点交通时间。普通实质修改仍交付更新后的完整正文，但不要承诺未改部分逐字不变。

精确改字走主提示词的 edit_text 契约；确认/清空走对应 action，无需规划流程，不为这些操作补问预算、人数或日期。加载Skill本身不授予任何修改权限。

## 正文结构

- 开头约100—180字概览主线、选择理由、实际采用的默认假设及最多3项关键条件。
- 独立顶层 `---` 后按实际日期展开，每天通常500—900字，用户要求详细再展开，不为凑字重复。
- 每日呈现：住宿出发、实际顺序的活动与移动、餐饮休息、返回住宿；明确建议时段和有来源耗时的区别。
- 费用按统一口径归纳；准备事项少量且与实际行程相关。未知贴近对应活动说明，不将所有风险埋在末尾免责声明。
- 自然中文 Markdown，不写POI标识、内部工具名、patch或内部检查流水账。不在正文输出JSON调用说明。

完整正文放 save_trip_changes 的 itinerary.text，引用完整 user_quote。只做当前授权变更，不因生成行程顺便覆写无关需求。未成功提交前不说已保存；保存结果由服务器回执决定。

## 交付检查

1. 完整有效需求是否有遗漏、否定反转、擅自删除或默认覆盖明确偏好？无法满足的愿望是否解释？
2. 日期是否全部覆盖、每天是否住宿往返，是否误安排新入住退房或更换住宿？
3. 起终点、方向、交通方式、时间和预约窗口是否相互一致？缺失依据是否明确？
4. 出门至返回跨过的餐次、休息和用户禁忌是否处理？是否把建议当用户事实？
5. 预算是否区分人均/全队、分配/报价和未知？是否隐含未提供的人数或价格？
6. 局部修改是否仅涉及授权部分与必要衔接，是否恢复已取消内容？
7. 行程是否可读且取舍清楚，而非景点堆砌？

检查结果不等于现实条件已被系统核验，也不保证所有地点未来开放。关键冲突未解决时先澄清比编出一个完整但不可信的行程更合适。
