# 同城旅行规划

把用户真正想做的事，组织成有依据、可解释且留有余地的每日安排。好的规划不是热门景点堆砌，也不是把未知事项填满。

这是项目维护的方法指导，服从常驻安全与业务契约。读取本技能不代表用户授权生成、修改或保存；示例与方法不提供现实地点、价格、营业或交通事实。仍使用当前工具定义与服务器返回值，不推断工具参数。

## 使用已有信息，不从头盘问

先看本轮原话、完整需求正文、当前行程与已确认创建资料。已有内容直接复用，不为执行流程机械重读 requirements 或 plan；只在需要较早消息或查询依据时读对应上下文。

辨别本轮是首次生成、全局重排，还是局部实质修改。局部修改先读取 `read_skill(name="travel-planning", resource="output-and-revision")`，确定保留范围和受影响衔接。

先核对创建资料和可信住宿是否足以生成。固定资料缺失或冲突按常驻规则处理；不要把“加载了技能”当作补齐条件。未知人数、预算和健康情况不补造。

## 1. 先归纳约束，再选主线

- 汇总完整需求与全部有效愿望，区分必做活动、指定时段、饮食禁忌、节奏偏好和可选内容。不以“只是想法”排除用户愿望。
- 新原话明确取消或覆盖旧要求时采用新要求。独立事项尽量一起处理；条件未知的修改不当成无条件授权。
- 系统安全、受理范围、同城限制和固定创建资料始终优先；用户明确偏好、禁忌及指定安排高于默认假设。
- 现实条件冲突时说明冲突并让用户取舍，不假装全部满足。不在规划中悄悄删除难安排的愿望。

未给偏好的部分，暂按首次到访视角、节奏适中规划。有条件兼顾代表景点、本地美食、特色街区和文化体验，不为凑齐类别硬塞活动。信息足够时直接查询并规划，不逐项追问兴趣；只澄清会阻碍规划的关键缺项或冲突。

用一句话说明实际采用的假设，不把首次到访当作用户事实；不把默认假设写入 requirements_text，不推断人数、预算或健康状况。

## 2. 搭骨架，先验证关键可行性

按地理就近组织路线，减少无意义折返。预约时段、开放条件和用户指定顺序优先于就近；没有核实的预约或开放条件明确保持未知。

先安排每天住宿出发、核心活动和返回住宿的骨架，再验证关键接驳和时间窗口。首次查询关键接驳、需要公交换乘解释、预算或雨备取舍时，读取 `read_skill(name="travel-planning", resource="evidence-and-routing")`。不要无条件把所有参考资料全部加载。

- 每个日期都从已确认住宿出发并返回。住宿不是新入住，不推荐酒店或安排入住退房。
- 优先核查住宿到实际第一站、实际末站回住宿，以及会影响可行性的跨景点移动；首末站也可能是餐饮或休息点。
- 地点身份不明先搜索、选定后查详情，再按可信中心坐标查路线。已有适用依据可复用，不重复查询凑数量。
- 地点存在不证明有票、开放、免费或适合雨天。不要用模型常识补动态事实，也不要把未知当零成本或零耗时。

## 3. 按真实出行窗口铺开每一天

按 requirements.known.dates 覆盖全部日期，避免把第一天复制成多日模板。

- 在出门到返回窗口中放入游览、移动、休息和实际跨过的餐次。用户已吃、自带或明确不需要时，说明省略原因。
- 先让活动与餐次在地理和时间上接得上。未要求具体餐厅时可给类型和选择标准，不必为每餐穷举查询。
- 老人或儿童同行时依据用户明确表达的体力和节奏约束留休息、减少过紧衔接，不据年龄推断疾病或作医疗保证。
- 出门时间未给时只给建议；有来源的交通耗时与建议候车/休息缓冲分开表达。
- 留出实际可调整余地，不靠压缩所有停留时间来假装满足过量活动。

## 4. 做可解释的预算与备选

人均与全队、预算分配与真实报价分别表达。预算未知时给费用构成和有来源单价，不编人数或全队总额，不说“肯定够用”。

默认游玩费用包含餐饮、市内交通和门票，不含住宿及跨城交通；用户明确范围优先。分配包含机动且合计不超额度；必要费用未知时说明条件与取舍，不给虚假精确结余。

雨备、替代地点的室内、遮雨、免费和当日开放未经核实就保持未知。提供建议与待确认条件，不保证备选已经可执行。
