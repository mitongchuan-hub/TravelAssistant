# 同城游玩改造与验收（2026-10-15）

`main` 已改为以住宿地址驱动的同城游玩助手，默认一天。创建时只填写住宿地址或酒店名称，匹配地图位置后即可在聊天中说“生成路线”，也可从聊天菜单或想法页生成。重名或详情不完整时选择具体地图候选。日期、天数、每日出门/返回时间、人数、预算、必去、饮食和节奏均可选。

## 分支与数据

改造前全部未提交的修复、少样本、文档清理及原始评测已保存到本地 `travel-full`，快照提交 `79bcd28`。`main` 在该快照基础上改造，保留完整历史。

源码分支与业务数据库分别保存：同城版默认 `.cache/cityassistant.sqlite3`，由 `CITY_DB_PATH` 配置；`travel-full` 保留原 `.cache/travelassistant.sqlite3` 与 `TRAVEL_DB_PATH`。本次使用SQLite在线备份接口建立已验证备份，再复制原库到新的同城库，账号与会话一起保留。之后两库各自保存，不自动同步。

加载前无活跃业务/卡片任务。最初切换和最终加载前后，用户、旅行、消息、想法、行程五类业务表指纹一致，账号与会话也相同。最终基线6旅行、41消息；测试没有向业务服务写入旅行、消息或行程。备份见[初次备份记录](evaluations/city-outings-20261015/deployment/backup.json)和[同城库备份记录](evaluations/city-outings-20261015/deployment/city-backup.json)，数据库和密钥不进入Git。

切换分支前先停止当前服务，再切换并重新启动。两个分支都可用 `python -m uvicorn app.main:app --host 127.0.0.1 --port 8000`，工作目录须为项目根。当前同城服务已启动，`/health`正常，静态版本 `20261015-city-1`。

## 产品行为与实现

- 创建与设置共用地址匹配流程，支持无城市提示的高德全国POI搜索；城市和坐标来自实际返回。候选及原始表单保存在15分钟、最多128份的服务端草稿中，绑定账号和旅行，不接受客户端自报坐标。地图失败保留输入并允许重试。
- `Trip.mode=city`、确认的住宿POI与`lodging_address`区分同城行程。旧记录默认`travel`，原需求、聊天、行程和五组生成条件保留，不自动转换旧旅行。
- 同城日期未填时 `travel_window.dates=null`，使用第几天标签；不默认今天，不为规划查询当天预报。每日出门/返回时刻未填时给建议时段。已给日期时根据开始日期和天数计算结束日期。
- 人数、预算未知不强制追问。人均与全员总额分别使用；默认游玩费用包括餐饮、市内交通、门票，不重复计住宿及跨城交通。聊天自定义费用范围在设置保存时保留。
- 同城规划/修改限制在住宿城市。住宿可信POI直接进入模型上下文与地点目录，每天从住处出发并返回；生成检查当前轮是否尝试首末接驳，未查允许一次补查。检查证明查询尝试，不证明正文正确使用或现实可行。
- 换住宿地址或城市后旧位置失效，在设置中重新匹配；更换城市时自动标题同步，已有原文仍保留，待用户生成/修改后替换。
- `roles(mode)`选择同城规划、规则、少样本、修改提示词及需求Schema，沿用原模型、思考档位、调用预算和四意图，不增加独立模型复核。生成先保存原文，后台整理卡片；未知日期卡片可用null日期，失败保留原文。
- 地点结果新增上游提供的类型和参考营业资料，缺失不补值。营业资料不保证未来日期开放，普通POI费用不冒充门票。路线仍返回原有耗时/距离摘要，具体线路明细尚未扩展。
