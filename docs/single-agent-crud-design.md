# TravelAssistant 单 Agent 增删改查方案

- 整理日期：2026-10-28
- 状态：已直接替换现有框架并通过 266 项离线自动化回归（2026-10-28）；尚未进行真实模型/地图生成质量验收。
- 验证范围：含伪模型到真实执行循环、原子提交、独立临时 SQLite 重载及隔离 Web/API 测试；不使用正式业务库，不证明现实路线可执行。
- 最新方向：一个旅行 Agent，通过增删改查工具完成工作，不再采用主 Agent 加四个专业 Agent 的编排。
- 范围：单 Agent 框架与必要 CRUD 保存适配；本轮不实施 HTML/guide 展示迁移，不改聊天布局，不改正式业务数据。

> 首版落实边界：`submit_changes` 是终止工具，一轮至多一次完整提交。内部校验并封装提案后模型停止，由提交层原子保存，成功文案来自实际结果。不支持同轮“先保存再继续规划”；本文件早期讨论中的分步写入仅保留为未来方向，以下以首版说明为准。

## 1. 一句话结论

> 一个 Agent 负责理解用户、获取必要事实并规划方案；工具提供受限的增删改查；程序负责权限、业务校验、版本冲突和原子保存。

不新增 TurnSession，不先建设插件平台，不再为了“需求整理、查询、规划、修改”分别创建子 Agent。

单 Agent 是当前选定的设计方向，不代表它的模型效果、速度或费用已经经过对照验证。

## 2. 我们的讨论如何收敛到这个方案

### 2.1 从当前代码的学习开始

围绕 `TaskExecutionRuntime.run()`，我们讨论了：

- Agent Loop 就是“调用模型 → 模型选择工具 → 程序执行 → 把结果交回模型”的循环。
- 工具定义只是说明书；真正执行依靠运行器把工具名称对应到 Python 方法。
- Schema 验证检查字段、类型、必填项和枚举，不证明内容真实或行程合理。
- 模型回复“已完成”、工具返回成功、候选产生和数据库提交成功，是不同阶段。
- 预算预检不等于实际扣减，也不保证剩余时间一定够用。

这些基础机制仍然成立。新设计要让它们更直接，而不是引入更多名词。

### 2.2 曾提出过较重的框架

此前提案包含：

- 一个主 Agent 加需求、查询、规划、修改四个专业能力；
- 通用 Runner 与角色配置；
- TurnSession，下设 authority、snapshot、transcript、budget、cancellation、workspace、events；
- 更完整的事件、终止和扩展接口。

它试图明确职责，但存在过度设计：过多包装对象增加学习成本，默认保留多 Agent 也没有先证明收益。

### 2.3 最新取舍

用户明确表示“增删改查就可以”。因此目标收敛为：

1. 一个模型角色、一套 Agent Loop。
2. 工具按增、删、改、查组织。
3. 规划由这个 Agent 完成，不再包装成规划子 Agent。
4. 不新增 TurnSession 或通用插件体系。
5. 复用现有存储、查询工具和必要校验，不把简化理解为取消安全边界。

之前的 `agent-framework-proposal.html` 是方案演进过程中的多能力提案，不再作为最新推荐架构。`v3-agent-architecture-pi-reference.md` 保留为研究背景；如其表述与本文件的最新产品取舍不同，以本文件为本次讨论的结论，不自动修改历史研究稿。

## 3. 借鉴 Pi，但不照搬 Pi

值得借鉴：

- 小而清晰的模型—工具循环。
- 工具定义、参数规则与执行实现直接关联。
- 模型通信适配与业务逻辑分离。
- 完整应用数据与发给模型的上下文分离。
- 先满足实际需求，证明必要后再增加能力。

不照搬：

- 编码 Agent 的任意 shell、文件写入或代码执行能力。
- 默认所有工具都并行。
- 为扩展预建动态插件、任意 hook、多 Agent 调度。
- 把 Pi 的会话管理对象重新包装一遍，增加本项目不需要的概念。

本项目继续使用现有 Python/FastAPI 技术栈。本方案没有要求引入 Pi SDK、切换供应商或迁移到 TypeScript。

## 4. 目标整体流程

```text
用户发送消息 / 点击一个明确操作
                 ↓
应用入口：鉴权、绑定旅行、捕获当前版本
                 ↓
准备当前旅行上下文
                 ↓
一个 Agent Loop
  模型判断下一步
      ↓
  选择增删改查或外部查询工具
      ↓
  程序验证参数与权限，执行工具
      ↓
  结果交回同一个模型
      ↓
  继续、追问或结束
                 ↓
明确的业务变更交给现有提交层
                 ↓
校验并原子保存，返回实际结果
                 ↓
向用户说明已保存、未完成、失败或需要补充什么
```

这是业务流程，不要求每一轮都进行数据写入。纯咨询可以只查询和答复。

## 5. “增删改查”的准确含义

### 5.1 操作的是旅行对象，不是数据库表

允许表达：

- 添加一条饮食需求。
- 修改旅行天数。
- 删除用户指定的想法。
- 读取当前行程。
- 用完整的新行程替换当前方案。

不允许表达：

- 任意 SQL。
- 任意表名、字段名或存储路径。
- 修改任意账号或旅行。
- 跳过业务检查直接写 SQLite。

身份、旅行归属和本轮版本由服务器绑定，不让模型自报后直接信任。

### 5.2 四类能力，不是强行只有四个函数

| 分类 | 用户操作示例 | 必要边界 |
|---|---|---|
| 查 | 看需求、行程、想法和聊天；查地点、天气、路线 | 只读授权数据；对外部结果说明来源与未知 |
| 增 | 添加想法、补充需求、首次生成行程 | 用户明确授权；字段合法；不补造未知 |
| 改 | 改天数、饮食、某项安排或完整行程 | 目标与范围明确；使用当前版本；未授权内容不顺手改变 |
| 删 | 删除想法、移除某个安排、清空指定内容 | 目标明确；必要时确认；清理相关中间状态 |

“读取本地行程”和“查询高德路线”都属于查，但输入、权限和实现不同，可以保留不同工具。四类是理解方式，不是限制工具数量必须等于四。

### 5.3 生成路线不需要一个规划子 Agent

模型本身可以读取需求、分析路线、调用地图工具，最后提交完整方案。

```text
以前：Main → 需求能力 → Main → 规划能力 → Main → 提交

目标：一个 Agent → 读取/查询 → 提交需求和行程变更
```

这不意味着删除查询证据，也不意味着模型可以凭空编造交通、价格、开放或预约信息。

## 6. 最小工具方案

以下是建议接口，名字与参数在实施时按现有业务模型确定；不是当前已上线 API。

### 6.1 读取与外部查询

| 工具 | 用途 |
|---|---|
| `read_context` | 按类型读取本旅行需求、行程、想法、聊天和必要证据；支持有界分页 |
| `search_places` | 查询真实地点候选和详情 |
| `query_route` | 在已匹配地点之间查询交通 |
| `query_weather` | 查询适用日期的天气，超出范围时说明未知 |
| 其他确有需要的查询 | 优先复用项目已存在的餐饮等工具，不为凑数量删除真实能力 |

### 6.2 统一写入入口

推荐使用一个明确的业务写入工具，例如 `submit_changes`，承载增、删、改，不拆成多个子 Agent。

它应支持：

- 需求 patch；
- 想法添加、修改和删除；
- 行程创建、替换、受限修改或明确清空；
- 展示偏好修改；
- 明确的当前方案确认操作，且确认不等于事实核验。

不要求第一次实现就支持所有资源的所有操作；以当前产品实际存在的操作为边界，不借此增加预订、支付、社区等新功能。

```json
{
  "requirements_patch": {
    "day_count": 2,
    "dietary_restrictions_add": ["不吃辣"]
  },
  "itinerary": {
    "action": "replace",
    "content": "完整的新行程……"
  }
}
```

上面仅说明“相关变更一起表达”的思想。`dietary_restrictions_add` 等名字不是对现有字段的声明，最终必须映射到项目真实需求字段与校验规则。

### 6.3 工具定义与执行绑定

避免继续维护“工具 Schema 一处、字符串分发一处、实现又一处”的松散关系。

```python
# 目标接口示意，不是已存在的类或可直接运行代码。
ToolSpec(
    name="read_context",
    description="读取当前旅行资料",
    parameters=read_context_schema,
    execute=read_context,
)
```

调用链：

```text
模型返回工具名称和参数
        ↓
从注册表找到工具
        ↓
解析参数、验证 Schema
        ↓
校验当前操作权限与业务条件
        ↓
执行对应函数
        ↓
把结构化结果交回模型
```

注册机制做到能统一查找和校验即可，不扩展成插件平台。

## 7. 单 Agent Loop 应该负责什么

只负责：

1. 准备当前模型输入。
2. 检查预算与取消状态。
3. 调用模型，接收完整响应。
4. 验证并分发工具调用。
5. 回填工具结果。
6. 继续、追问、正常结束或失败结束。

不负责：

- 具体数据库表结构。
- 酒店、天气、饮食等所有业务校验细节。
- HTML/CSS 页面生成。
- 任意子 Agent 编排。
- 隐藏的二次模型复核。

```python
# 流程示意，不是可执行实现。
while 可以继续执行:
    response = 调用模型(当前消息, 可用工具)

    if response 包含工具调用:
        result = 校验并执行工具(response)
        将工具结果加入消息
    else:
        形成最终答复并结束
```

真正实现还要处理完整响应检查、工具调用与结果配对、超时、错误和写入回执，但不需要为每个环节新建一套框架对象。

## 8. 不新增 TurnSession

之前 TurnSession 的七项职责都不是凭空产生的问题，但不需要再包装为七个子系统。

| 需要处理的事情 | 简化方式 |
|---|---|
| 请求身份、旅行和版本 | 复用现有 `RequestContext` |
| 当前旅行数据 | 复用现有执行快照/上下文 |
| 模型消息和工具结果 | Loop 内维护 `messages` |
| 次数、时间、取消 | 复用并适度整理 `TurnBudget` |
| 暂存业务候选 | 若写入链路需要，内部复用 `TurnWorkspace`，不暴露额外编排工具 |
| 进度显示 | 使用现有进度回调，统一必要事件，不重建事件总线 |
| 保存 | 复用 `TurnCommit` 及存储服务 |

新框架首先应降低理解成本。不要为了目录好看，引入业务上没有新价值的 SessionManager、Finalizer、PolicyEngine 等一串对象。确有独立职责时再提取函数或模块。

## 9. 需求补充、追问与规划怎样完成

### 9.1 用户已给出足够信息

用户：“改成两天，不吃辣，按这个生成路线。”

前提：旅行已有有效住宿和明确日期，变更不会产生未解决的日期歧义。

```text
一个 Agent 读当前需求和行程
        ↓
理解“两天、不吃辣”是本轮明确变更
        ↓
按需查询地点、天气、交通
        ↓
模型规划完整两天路线
        ↓
submit_changes 同时提交需求变更和完整新方案
        ↓
程序验证授权、字段、日期、证据和版本
        ↓
原子保存；把真实保存结果交回模型/界面
```

不再调用 `prepare_requirements`、`draft_itinerary` 两个专业 Agent。其必要的字段检查和业务规则保留为普通 Python 函数。

### 9.2 信息不足

用户：“帮我生成路线。” 但缺日期。

```text
读取当前旅行资料
        ↓
发现生成前提缺失
        ↓
同一个 Agent 直接问“你打算哪天出发？”
        ↓
本轮结束；不在进程中阻塞等待回答
        ↓
用户回答后开启下一轮
```

必要时保存简单的 `pending_question`，记录问题、关联消息、目标字段和版本即可。它不能让一句“可以”变成对所有需求的通用写授权。

### 9.3 只有需求补充

用户：“我不吃辣。”

Agent 不必规划新路线。校验当前消息确实授权补充饮食需求后提交需求变更，并明确已有行程是否需要另行调整；不因设置变化自动重排。

### 9.4 规划失败但需求可以独立保存

首版一轮只有一次终止提交，不能保存后继续规划，也不能依赖隐式部分提交：

1. 规划尚未完成、尚未提交时，Agent 可以明确选择仅提交本轮已授权的需求，并结束本轮；回执据实说明需求已保存，没有新行程。
2. 已提交需求与新方案的完整包，但程序验证失败时，整包拒绝，需求也不能偷偷保存。若要重新尝试，必须由新的用户请求开启新一轮。
3. 用户先明确要求保存需求，下一轮再要求规划，也属于合法的两次独立请求，不是同轮连续写入。

完整 `submit_changes` 按提交内容全有或全无，不悄悄跳过非法部分。内部复用 Workspace 密封整包、Commit 统一保存，不把候选编排重新暴露给模型。

## 10. 保存设计：简单接口，严格底线

### 10.1 推荐语义

`submit_changes` 是单 Agent 调用的写入入口；它最终通过现有提交服务校验和原子保存，不直接拼 SQL。

为了简化正常流程，不再要求模型先注册候选、管理跨轮任务、采用多种 artifact，最后另调用一个工具才保存。内部若需要兼容现有 Workspace/Commit，可以由适配层封装，模型不必理解所有内部引用。

### 10.2 必须保留的检查

- 当前用户拥有该旅行。
- 写入来自本轮明确授权，不来自旧聊天、查询结果或假设。
- 参数 Schema 正确，业务字段与组合合法。
- 日期、天数、住宿、费用口径等满足现有同城规则。
- 修改对象及范围准确，精确编辑不能悄悄改写其他文字。
- 计划、需求版本及请求代次仍匹配。
- 同一请求/同一操作不会因重试而重复创建或删除。
- 相关写入原子保存；持久化失败不发布半份内存状态。

Schema 只能验证结构，不保证地点存在、预算足够、餐厅营业或路线现实可行。事实必须依靠适用证据，未知保持未知。

### 10.3 模型输入不包含任意写权限

允许传给模型：当前需求、行程、必要对话与查询结果摘要。

不能让模型决定：owner_id、任意 trip_id、数据库路径、SQL、任意服务端字段或未经确认的坐标。

服务器为工具绑定当前旅行和版本。确实需要修改其他对象时，也必须从当前授权旅行中解析受控标识。

### 10.4 保存回执先于成功宣称

必须区分：

```text
模型已形成方案 ≠ 已请求保存 ≠ 保存成功 ≠ 事实已核验
```

提交失败时，模型不能继续说“已更新”。关键成功文案应由程序依据回执生成或约束。

首版复用执行任务 request_id 与终止回执，并保存整包规范摘要：相同请求、相同包可回放，异包不能复用已提交身份。一轮只有一次终止写入；多个相关操作合并在同一包内，不并行提交。连续写入需下一轮新请求与服务器的新版本，不增加同轮多写账本。

## 11. 删除与修改的特别规则

### 删除

- “删掉这个”但目标不明确：先问，不猜。
- 单条、明确、可控的删除可以执行；清空整份行程、聊天或旅行等范围大/难恢复的操作按产品规则确认。
- 删除行程中的一站不能只删标题而留下矛盾交通段；需要给出一致的新行程，查询不足时如实说明。
- 删除旅行或任务时，按项目要求清理关联中间文件、卡片、临时记录和模型运行记录；具体范围与历史兼容在实施时核实，不把所有删除视作同一种清理。
- 确认操作绑定明确目标和版本，过期确认不能删除新内容。

### 修改

- 局部修改不能扩成整份路线自由重排。
- 用户要求精确字句编辑时，使用程序可验证的精确替换规则。
- 开放式路线调整仍可能返回完整正文，但要明确模型不能天然保证其他段落逐字不变。
- 纯风格修改不能改变事实、证据、计划身份或确认状态。

## 12. 并行、预算与错误处理

### 12.1 首版以串行为主

只有独立、同一快照上的外部只读查询才考虑有界并行。写入、删除和依赖前一个结果的查询串行执行。

不为了接近 Pi 的默认行为而马上引入并发；先保证单循环正确、可理解。

### 12.2 预算

复用整轮模型、工具、外部请求次数和截止时间控制。

- `reserve()` 只预检，不扣次数，不保证一定剩下指定秒数。
- 真正开始调用时计数；兼容重试和备用请求也不能脱离总预算。
- 时间和取消应传到网络调用，迟到结果不能覆盖新状态。
- 收尾包括结束所需工具和本地提交时间，不只留一次模型调用。
- 不再在“最后一次调用”之后隐藏启动回复复核模型；若保留必要复核，明确为有预算的可见步骤，否则不引入。

### 12.3 错误

| 情况 | 目标行为 |
|---|---|
| 参数/Schema 不合法 | 工具返回清楚错误，允许有限修正；不执行非法操作 |
| 相同无效调用反复出现 | 程序停止或要求澄清，不仅向模型写 recoverable=False |
| 权限不足/越权 | 拒绝操作，不通过重试换说法绕过 |
| 地图或天气不可用 | 保留未知和当前方案，不能由模型补造事实 |
| 数据版本变化 | 拒绝陈旧写入，重新读取或让用户确认 |
| 存储失败 | 原子回滚，明确未保存 |
| 新消息替代旧轮 | 取消旧轮，拒绝迟到写入 |
| 次数/时间用完 | 程序明确说明未完成，不无限让模型继续总结 |

进度/日志故障不应覆盖已得到的业务回执。敏感对话和模型轨迹仍应有脱敏与保留策略，但本轮不为此建设新的通用事件框架。

## 13. HTML 行程页的讨论结论

这是与 Agent 框架相关但可独立推进的展示设计，不要捆绑成一次大重写。

### 已认可的判断

当前方案的优点：

- 正文与 HTML 分离。
- 网页失败不丢行程。
- sandbox、CSP、版本绑定和旧结果保护有价值。
- 个性化、下载和成品感值得保留。

主要问题：

- 第二次模型把正文改写为 HTML，无法仅靠结构校验证明信息完整。
- HTTPS 不等于链接可信；应由程序基于证据生成/核对链接。
- 模型自由 CSS 不能稳定保证可访问性、手机重排和未知事项可见。
- 主页面 iframe 导致嵌套滚动。
- 纯风格变化不应要求重新解释事实、等待完整模型生成并承担新的遗漏风险。

### 推荐方向

- 主阅读体验由程序确定性渲染。
- 个性化采用受控主题、字号和排版参数。
- HTML 保留为可下载/预览的导出格式；完整自由生成页面如保留，只能是明确的非权威可选产物。
- 不将 HTML 反向作为正式旅行数据。
- 主阅读页尽量单一纵向滚动，未知与待核实信息由程序稳定表达。

### 与单 Agent 的关系

如采用结构化 guide，由同一个 Agent 的规划结果产出，或以结构化数据作为唯一内容源并由程序生成文字，不再增加 display/抽取子 Agent。

此前提出过“正文与结构在一次模型调用中同时输出”。这减少二次转换，但不天然证明两份内容完全一致；最终权威内容模型、精确编辑和历史兼容仍需在展示实施前确定。不能把 guide Schema 通过当成语义等价证明。

本次框架简化不以完成 guide 数据迁移为前提，也不恢复旧的固定卡片布局。聊天头部、消息、输入框和底栏保持现状。

## 14. 当前代码的复用与精简方向

以下是目标映射，不表示已经修改：

| 当前部分 | 推荐处理 |
|---|---|
| `model_transport.py` | 保留模型协议适配和完整响应检查 |
| `entrypoints.py` | 保留客户端、调用配置与必要轨迹，减少夹杂编排职责 |
| `roles.py` | 收敛为单角色提示词、工具注册与 Schema |
| `main_input.py` | 复用安全上下文投影、分页和版本绑定 |
| `travel_runtime.py` / `agent_runtime.py` | 提取成一套循环，移除主/子委派的重复机制 |
| `TurnBudget` | 保留必要计数、时间和取消，明确预检与实际调用 |
| `TurnWorkspace` | 视现有提交依赖内部复用/简化，不再要求模型进行复杂候选编排 |
| `TurnCommit` | 保留唯一提交口、版本复验和事务保护 |
| 地点/路线/天气工具 | 复用已存在的服务端查询与证据处理 |
| `manage_todos` / `manage_task` 主工具 | 不作为新框架必备；需要的任务状态由应用管理，避免模型为做旅行任务先维护一套任务系统 |
| 四个专业能力 | 目标不再作为独立模型角色运行，必要规则保留为代码或提示词 |

不简单“删除旧文件再重写”；先确认函数真实用途、持久化兼容和所有调用点，再逐步移除已被替换的路径。

## 15. 建议实施顺序

本节是后续实施建议，不是立即开工授权。

### 第一阶段：明确操作合同

- 列出现有可增删改查的旅行对象与授权范围。
- 定义 read_context、外部查询和 submit_changes 的实际字段。
- 确定写入回执、幂等标识和版本绑定。
- 用现有业务模型定义 Schema，不让设计示例字段变成另一套需求模型。

### 第二阶段：工具注册先落地

- 把定义、Schema 和实现建立直接关联。
- 复用现有服务；暂不同时移动所有文件或改数据库。
- 验证每个工具的权限、参数、错误及副作用边界。

### 第三阶段：单 Agent 循环替换编排

- 主模型直接查询、理解和规划。
- 不再调用需求/查询/规划/修改子 Agent。
- 让写入经统一工具进入现有提交服务。
- 保持历史记录可读，旧任务不会被重启后自动重跑。

### 第四阶段：删除不再需要的机制

- 移除重复循环、失效角色配置和未被消费的模型参数。
- 只有在确认替代路径和测试通过后，才移除复杂候选编排或旧任务兼容逻辑。
- 删除时清理对应中间状态，不遗留幽灵任务或卡片。

### 第五阶段：单独推进展示

- 确定主数据合同后再迁移 guide/HTML。
- 不把单 Agent、数据库改造和页面重排混在一次未经验证的提交里。

## 16. 验证和验收

### 功能场景

1. 只读问题不写业务数据。
2. 只补需求不自动重排行程。
3. 补需求再规划，用一个 Agent 完成，按明确提交单元保存。
4. 缺日期/住宿时追问，不默认今天、不补造住宿。
5. 局部修改和精确编辑不越界。
6. 删除目标不明确时追问，破坏性删除有有效确认。
7. 写入后依据回执回复，不把候选或工具成功说成已保存。
8. 地图失败保留未知、原需求和旧方案。
9. 单次提交失败没有部分持久化；分步需求已保存但规划失败时如实说明。
10. 新消息和旧版本提交竞争时，旧结果不能覆盖当前状态。
11. 同一操作重试不产生重复想法、重复删除或重复提交。
12. 不为换风格重跑规划，不改变确认状态。

### 工程检查

- 工具 Schema、角色权限、业务验证和实际参数消费逐项对应。
- 预算耗尽或不可恢复错误后没有隐藏模型调用。
- 真实模型、地图和存储失败分别记录，不混成“Agent 不行”。
- 离线回归通过不等于真实生成质量通过。
- 单 Agent 与当前链路在同类场景对照：约束遗漏、路线证据、延迟、调用次数、费用；没有对照结果前不宣称更快、更好或更便宜。
- 固定使用项目解释器：`E:/anaconda/envs/TravelAssistant/python.exe`。
- 真实模型评测需单独明确授权，不能因为批准写方案就自动发出付费请求。

## 17. 已确定、建议与待验证

### 已确定的方向

- 一个 Agent，围绕旅行业务增删改查。
- 暂不采用四个子 Agent 和 TurnSession。
- 不给模型任意数据库执行权。
- 必要授权、查询证据、版本检查和原子保存保留。
- 已授权并实施单 Agent 框架替换；现有排版和 HTML 展示架构不在本轮迁移范围。

### 本文推荐的实现选择

- 工具注册直接绑定定义与实现。
- 写入优先用统一 submit_changes 表达相关业务变更。
- 模型不需要管理复杂 artifact/跨轮任务系统，内部必要保护由代码承接。
- 默认串行，独立只读查询按需要再并行。
- HTML/guide 展示与 Agent 框架分开推进。

### 实施前仍需验证/定稿

- submit_changes 的精确字段、删除确认合同与幂等粒度。
- 现有 Workspace/Commit 内部保留到什么程度，怎样适配直达写入工具而不双重提交。
- 是否需要简单 pending_question；现有任务记录的兼容策略。
- 单 Agent 在长行程、多轮修订、想法覆盖上的真实效果。
- 主行程内容是结构化唯一源，还是正文与 guide 的一致性合同。

这些问题可以通过代码与原型验证收敛，不应为此重新引入一套庞大框架。
