## 主要发现

### 1. 东京行程有硬约束错误（TA-010，失败）

输入明确为11月14日20:00抵达羽田，11月16日09:00离开。输出却安排“18:30前到酒店取行李”，早于落地；这段日期需要两晚住宿，预算只列1晚。费用合计写4500～6200元，同时声称在6000元内可行。

此外，工具没有日本资料时，仍补写新宿御苑免费、1CNY约21JPY和具体接驳耗时。这些是无本轮工具证据的陈述，不能因为结尾列了待核实就当作可靠。

### 2. 外部未知仍被补成具体事实（TA-007失败；TA-004、009附加问题）

TA-007当天往返与无住宿基本正确，但没有路线查询证据，仍给出地铁1号线、27/4路公交、免费开放和具体交通价格，未满足“未知费用和耗时不伪造”。

TA-004的取消必去与后续规划流程符合该案例功能检查，但正文补写地铁约15分钟、打车费用、门票与预约结论。天气工具已经明确超出预报范围，仍给出8～17℃范围，来源不能追溯到工具。

TA-009跨月日期和两晚住宿正确，但同样补入无工具依据的门票、线路和耗时。上述案例的功能通过不代表事实质量达标。

### 3. 新需求与直接规划的组合输入可能跳过需求落档

TA-007、008、009、010均从空需求开始。模型可以使用本轮原话生成行程，但完成后独立需求档案的城市、日期、人数、预算等仍为空。

这是原案例检查之外的附加发现：后续修改或清空聊天时，这些硬约束缺少独立持久依据。当前主Agent提示词已经要求有依赖的组合诉求先更新需求，再规划，本次没有修改提示词来掩盖问题。

### 4. 日期缺失时先查了大量资料（TA-005）

最终正确询问日期且未保存行程，但询问前执行10次外部查询，整轮51.557秒。应先解决关键缺失信息；本次受控工具几乎不耗时，因此该数字不能解释成真实地图服务慢。

### 5. 模型推理服务中途不可用

TA-011、012先完成了需求更新，后续请求出现`APIConnectionError`；TA-017～026明确返回HTTP 503、`Loading model`，说明推理服务正在加载模型。TA-027、028出现约181秒的`APITimeoutError`，TA-029、035整轮约241秒后超时。这证明了部分需求保留，不能算完整用例成功。

独立探测时`GET /v1/models`返回200，但最小聊天补全分别等待15秒和45秒后超时。`/models`健康不等于推理接口可用。剩余案例未得到可评审业务结果，不把连接故障包装成Agent业务失败，也不盲目重试整套测试。

### 6. 测试题TA-002需要修订

输入说“14日10点到杭州东站，15日18点离开”，没有明确离开车站。Agent保留离开地点未知是合理的，但检查项要求抵离时间地点完整。明确提供的信息均实际保存，未擅自规划。后续应补“15日18点从杭州东站离开”，或将验收改成“未提供的离开地点保持未知”。本次保留原题，不追改输入来美化结果。
