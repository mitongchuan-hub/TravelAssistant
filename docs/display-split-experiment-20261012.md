# 独立提取准备事项与全局条件：首轮对照结果

日期：2026-10-12。状态：实验已完成；当前候选未通过生产接入门槛。后续按用户选择完成[衣物、住宿、天气合并单次提取实验](display-combined-weather-experiment-20261012.md)，准备信息覆盖改善，后续优先继续单次合并方向；本文保留首次两次提取对照证据。

## 结论

将全局信息独立为一次LLM提取，能改善部分多日资料覆盖，但不能稳定解决遗漏，并增加一次请求及总等待。本轮保留实验入口和全部证据，生产展示继续使用已有整篇转换。

四份固定原文、每方案各3次，共24次正式转换全部返回结构/日期正确的卡片，没有连接或超时失败。实际SDK请求：整篇12次，独立提取24次，共36次。两种方案均未触发协议兼容；整篇未触发结构纠错。独立提取正常两次调用用完请求额度，没有追加纠错。

结构通过不代表语义通过：独立方案仍漏准备事项，生成原文没有的装备条目、错放天气核对、无依据断言酒店未预订，以及七日概览单字“以”。这些已作为失败样本保留。

## 实验实现

新增隔离模块`tests/performance/display_split_experiment.py`及配对执行器`tests/performance/run_display_split_experiment.py`。生产`app/agent_client.py`、后台调度和持久化没有因实验切换。

- whole：当前生产整篇提取，一次正常请求；结构/日期错误时沿用原纠错规则。
- split：第一阶段提取overview、budget_note、preparation、pending_items、risks；第二阶段提取schema_version、title、days。两次均读取同一份完整原文；两种子Schema字段互不重叠，程序只合并与校验，不补写衣物/酒店/价格。
- 两阶段共用180秒总截止、最多2次实际SDK请求，无工具。任何片段失败不返回半份卡片。兼容请求计入总额；取消/前台优先callback阻止后续工作。正式后台接入、发布及旧任务回写仍需另行验收。
- 同模型、协议、display思考档位与源文字，第1/3组whole→split，第2组split→whole，串行执行；不在测试中途调整提示词或预算。

71项[人工核对清单](../tests/datasets/display_semantics_v1/review-checklist.json)覆盖每份原文的装备、住宿、费用、电话/营业、时间限定、忌口及核实条件。引用执行前检查均存在于源文字。这份清单只用于评审，不送给LLM作为答案。

## 逐场景人工评审

### 聊天当天

两种方案均有一次漏衣物。独立提取三次保留餐厅电话，整篇两次遗漏电话；但独立方案第一份新增了原文没有的“雨具”栏目（正文承认原文未明确要求），第二份把天气核对放入衣物，并把待核实清单作为每日活动追加。这些不能因为卡片非空而忽略。

### 页面当天

独立提取两份在专项核对中未发现问题，一份衣物准备为空；其risks仍提到备伞，但分层/外套漏掉。整篇两份虽然有衣物，仍漏饮水小食预算、380元机动缓冲和420元分项合计；第三份连准备/清单/风险都为空，遗漏高价改备选、餐厅无法保证不辣时的应对和雨天合并安排，日期label成为冒号。

### 三日

独立三份均有衣物和住宿准备，酒店地址、房态/价格/取消待确认、提前1–2周预订、餐厅电话和营业信息覆盖较好；整篇有一份大面积遗漏，另外两份仍漏门票0元或部分总览分项。

独立第二份却将待确认的住宿状态写成“酒店尚未预订”。原文只说明候选、房态和价格待确认，不能据此断言未预订。该无依据状态断言使这份候选失败，不能用另外两份较完整输出抵消。

### 七日

两种方案衣物都仅1/3有内容；独立前两份全局准备、核实、风险字段均为空，第一份overview只剩“以”。每日阶段保留酒店候选与状态，因此不能把这些地址判成全局彻底丢失，但专用住宿准备仍为空，微辣也不要、天气复核和提前1–3天核实等条件未完整保留。

第三份独立提取衣物、住宿、微辣也不要与菜名不能保证完全不辣都保留，但仍漏出发前1–3天确认的时间提醒。整篇第三份还将美居地址“中河北路3号”改成“中河中路3号”。

专项检查与补充问题合计：整篇12份均发现至少一项问题；独立12份中4份在当前专项范围未发现问题，其余8份失败。这个结果不是全部旅行质量通过率，也不能证明这4份不存在其他问题；v2过敏/未知等扩展验证尚未执行，因为首轮门槛未达到。

## 验证与证据

- 自动回归489项通过，75.32秒。新增11项覆盖字段隔离、源文字一致、合并不改写、子阶段失败不发布半成品、前台/总截止/兼容耗尽预算、空原文准备不补写、执行器保留失败和停止。
- 异步浏览器回归通过：文字先可读、草稿/选区/阅读位置保持、卡片失败后只重试卡片；受控文字可见1415ms、卡片3328ms，不是实际模型延迟。
- 业务库执行前后14趟旅行、84条消息及全部原文SHA-256一致，schema5，无活跃任务。实验不使用业务Store、不向8000服务提交业务。
- 全部71项在每方案每次输出下进行人工原文对照，426项记录及补充问题保存为semantic-review.json；合理跨字段保留与专用字段遗漏分别判断。原文自身事实是否真实不在本轮展示忠实度验收中自动认定。

## 下一轮方向

当前方案不满足四份原文12份均无已知遗漏/改义的门槛，三个场景的中位数额外等待也超过计划20%的权衡阈值，因此不接入生产，也不直接扩张为七天八次请求。

下一候选优先进一步缩小全局阶段的任务：集中提取准备事项与关键条件，为每项给出原文引用，并在实验中验证引用真实存在、分类合理、未知没有变成确认状态。引用校验可以拒绝部分无依据输出，但不能单独证明完整性；空字段仍要检查原文覆盖。先用七日和原文无准备信息的反例验证，再扩大到四份固定原文。是否需要按章节提供源片段，要先验证边界不丢条件，不以关键词直接补写事实。

只有候选通过固定原文与扩展语义验收，再设计请求/纠错预算和后台接入，最后补验七日完整规划。生产原文先交付、旧结果保护与卡片回退继续保留。
