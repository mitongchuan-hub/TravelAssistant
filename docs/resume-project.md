# TravelAssistant｜AI 同城游玩规划助手

**项目类型：个人项目｜从 0 到 1 独立设计、开发与验证**

## 项目简介

面向已确认住宿地点的同城游玩规划助手。用户填写住宿、出行日期和游玩天数后，可通过对话整理偏好、查询地点/餐饮/市内交通/天气，生成并调整从住宿出发、最终返回住宿的多日路线。项目同时处理模型失败、查询结果不完整、并发旧请求和行程状态一致性等实际产品问题。

## 最具区分度的三条亮点

1. **从 0 到 1 完成 AI 旅行产品闭环**：独立完成需求定义、页面交互、认证、住宿地图匹配、聊天规划、路线展示、行程调整、SQLite 持久化和失败重试，形成从“创建旅行”到“生成/修改行程”的可运行 Web 产品。

2. **设计可控的 Agent 执行与原子提交架构**：采用 `main Agent + research / requirements / planning / revision` 专业能力分工，由 `TaskExecutionRuntime` 在有界工具循环中编排；通过 `TurnWorkspace` 汇总候选、`TurnCommit` 一次性提交，配合 request ID、版本校验和旧结果失效机制，避免重复请求或过期结果覆盖当前行程。

3. **把 LLM 的不确定性纳入产品设计**：建立同城业务边界、必填日期/天数、未知事实不补造、查询失败可恢复和正文/卡片解耦等规则；构建覆盖 12 个越界领域、混合请求、多轮诱导和提示词注入的 80 条评测集。本轮模型评测中，70 条越界/混合请求未观察到其他领域实质作答，10 条合法对照未被误拒，同时识别出无授权工具调用和异常回复等流程问题并单独记录。

## 面试时可展开

- 为什么把“正文”作为主数据、路线卡片作为派生展示：卡片生成失败不影响用户已看到的完整规划结果。
- 如何避免旧请求覆盖新状态：任务绑定 request ID、需求/行程版本和执行轮次，提交前再次校验基础版本。
- 如何评估 Agent 是否越界：把“最终回答是否越界”和“内部是否错误调用工具”拆成两个指标，避免只看拒答文本。

> 注：评测结果来自隔离测试夹具，专业能力使用 unavailable 模拟，不代表真实地图数据质量或线上业务成功率。
