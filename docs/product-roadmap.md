# TravelAssistant 产品化规划

本文基于本次工作区中的实际代码、现有页面模板、产品文档和回归结果。部分行程页面改动尚未提交，评估覆盖这些工作区改动。第 3、4 节保留实施前的现状与证据，最新实施进展见第 11—16 节。

本次交付是产品评估与推进计划，功能实施需按本计划拆分任务。用户群、团队投入、上线渠道和商业模式还没有明确，以下定位为建议，里程碑以结果验收，不作为工期承诺。

## 1. 产品判断

项目已经具备可工作的旅行规划原型：账号、私人旅行、聊天、想法卡、结构化行程、天气与餐食工具、单项调整、历史恢复和本地持久化均有实现。

现阶段的关键差距是：用户需求不能长期可靠保留；行程缺少地点和时间的事实验证；生成后的旅行安排缺少实际出行入口；多用户运营所需的数据、任务和成本管理尚未完整。

首版产品应让用户完成一件明确的事：把一次短途旅行的偏好，变成可以核实地点与交通、可以调整、可以在出门时直接使用的行程。

已有行程页优化计划解决的是阅读与交互问题。本文覆盖从首次使用到实际出行、再到产品运行的整体闭环。

## 2. 建议的第一版定位

- 使用渠道：手机浏览器 H5，账号保存私人旅行。
- 主要场景：国内单城 2—5 天的周末或短假自由行。
- 规划者：一位主要规划者；可填写同行人数、儿童或老人情况，旅行数据仍归账号所有。
- 核心需求：减少查攻略、排路线和反复修改的时间，出行时快速找到当天安排与地点。
- 首批验证：邀请约 10 位确有近期出行需求的用户，覆盖 3—5 个城市。人数是研究规模建议，不是现有用户数据。

第一版围绕行程规划与使用展开。订票、酒店交易、多人实时协作、内容社区等可在核心价值得到验证后独立评估。

需要在功能实施前明确的三个产品条件：主要服务的人群、首批目的地范围、首发渠道与投入规模。当前代码支持私人账号场景，本计划据此展开。

## 4. 已确认的问题与证据

### 4.1 需求会被展示数量限制删除

`app/store.py` 的 `MAX_IDEA_CARDS = 8` 同时限制展示与保存。新增手动想法、模型整理想法和修改反馈都会裁掉前面的卡片。

`app/agent_client.py` 的 `MAX_CONTEXT_MESSAGES = 12` 仅保留最近 12 条已发送消息供模型读取，当前没有独立的完整需求档案。

专项复现：连续添加 9 条不同想法，剩余 8 条，第 1 条已不在保存集合中。早期消息也离开上下文后，未写进基础资料或当前行程的需求可能不再传给模型。

产品决定：展示数量和保存数量分开；日期、预算、必去、避开事项、忌口与体力限制进入独立需求档案。硬性要求不能因为新消息或卡片排版被移除。

### 4.2 结构正确不等于安排合理

`app/agent_client.py::_validate_plan_shape` 检查必需字段、分类和部分对象结构，没有检查真实日期、重叠时间、旅行日期覆盖和交通可达性。

专项复现：将示例行程的日期全部改为 `2026-02-31`，把条目时间全部设为 `10:00-11:00`，仍能通过当前形状校验。

当前缺失日期提示有帮助，但发生在展示层，不能代替生成结果的完整性校验。天气与餐食工具也不能代替景点、坐标和路线验证。

产品决定：未知日期允许保留并明确展示；具体但无效的日期、已知时间冲突应在保存为成功结果前处理。已核实事实、估算值和待核实事项分开呈现。

### 4.3 生成与调整尚未形成可靠任务

普通聊天通过 FastAPI `BackgroundTasks` 执行，进程重启会把未完成占位消息改成失败提示；这保住了用户消息，但不能恢复任务。

`app/main.py` 的显式生成与调整接口直接等待模型处理完成。模型单次请求超时默认 180 秒，规划可能包含多个请求，尚无统一的任务总时限和可查询任务状态。

聊天发送端超时后提示重试，服务端没有客户端请求 ID 去重；响应丢失时重发可能产生重复消息或任务。

产品决定：聊天、生成、修改共享持久任务协议。页面可以离开，结果可以查询；重发同一个请求不会重复写入或重复扣除额度。界面只显示实际已完成的阶段。

### 4.4 多实例会覆盖数据

`app/store.py::DemoStore` 以进程内字典作为运行状态，`app/persistence.py::sync_relational_tables` 每次保存会清空主要业务表再从全量快照重写。

隔离复现：两个独立 Store 使用同一临时 SQLite 文件，依次新增不同旅行，后写实例保存后，先写实例的新增旅行已不在快照中。此复现证明独立状态相互覆盖，不是并发性能测试。

产品决定：受控内测使用单进程部署并明确容量；对外扩展前改成数据库作为统一状态来源，按旅行/记录增量事务写入，并用修订号检查过期更新。SQLite 可用于初期，数据库类型应由实际并发需求决定。

### 4.5 调试日志与文档不一致

README 描述日志不记录完整对话或模型回复，但 `app/agent_client.py::ConversationTrace` 会保存用户输入、完整上下文、模型请求、工具结果和模型回复到 `.cache/llm_logs`。代码中没有显式启用开关或保留时限。

产品决定：完整调试日志受显式配置控制并设清理周期；运行指标主要记录请求 ID、阶段、耗时、状态、模型、token 和费用估算。清空聊天、删除旅行、删除账号与调试数据清理的语义应明确。

### 4.6 现有测试覆盖实现回归，尚未证明旅行效果

本次验证：

- Python 回归：115 项全部通过。
- 聊天浏览器回归：通过，覆盖发送失败、轮询、输入保留和占位消息隔离。
- 行程浏览器回归：通过，覆盖 320/390/430/1000px、日期导航、面板焦点、草稿恢复、失败反馈、单次提交与返回目标安排。
- 浏览器中的网络中断为测试主动模拟。
- 上述专项复现使用内存或临时数据库；浏览器使用合成行程页面。

本次没有调用真实模型、核实真实城市路线、测量实际 token 费用或进行生产并发压测。不能从测试通过推导真实规划质量已经达标。

## 5. 建议的产品流程

1. **了解产品**：看一份真实示例，知道能得到什么，以及哪些信息仍需核实。
2. **建立旅行**：填写城市、日期/天数、人数、预算；可补充出发地、抵离时间、住宿点。
3. **补齐需求**：用快捷选项和聊天补充节奏、必去、避开事项、饮食与体力限制；随时编辑需求档案。
4. **生成第一版**：显示正在整理需求、核实地点、检查路线等实际阶段。完成后直接进入行程。
5. **看懂并核实**：每天查看主要地点、移动耗时与预算摘要，发现未核实信息并继续处理。
6. **进行调整**：简单字段可直接编辑；复杂修改交给助手。涉及相邻安排时提示影响，并让用户选择是否联动调整。
7. **实际出行**：定位今天与下一站，打开地图导航，勾选行前事项，向同行者分享只读计划。
8. **保存与反馈**：保留历史调整，能够归档、删除旅行并反馈不合理安排。

## 6. 页面规划

### 入口与我的旅行

- 入口增加示例行程与简短使用说明，评估“先体验示例、再注册保存”的路径。
- 旅行列表优先打开已有行程；未生成旅行进入需求补充，生成中旅行显示可恢复的任务入口。
- 基础资料支持编辑，旅行支持归档与删除。
- 用户端统一旅行状态与名称，避免各页混用草案、确认版本和内部 Agent 用语。

### 旅行需求

- 基础资料：目的地、开始/结束日期或天数、出发地、抵离时间、人数、住宿点。
- 预算明确是每人还是总额，是否包含往返交通与住宿。
- 偏好区分“必须满足”“尽量满足”和“避开”；未知资料允许保留，生成前说明影响。
- 关键限制固定展示，可编辑和撤销；重复需求合并时保留来源，冲突由用户选择。
- 想法墙保留灵感记录功能，较多内容用列表/分页查看，保存层不受屏幕卡片数量约束。

### 聊天

- 增加真正的重试入口，关联同一请求或失败任务。
- 长任务显示真实阶段，刷新后继续查询；只在确有进度时更新提示。
- 用户侧失败文案说明消息是否保留、安排是否更新和可做的下一步。
- 需求摘要可直接编辑，生成完成时明确提供“查看行程”入口。

### 行程

- 保留已有日期导航、时间线和底部调整面板。
- 增加当天路线、地点与交通详情；地址可复制，地点可打开地图。
- 增加费用估算、核实状态、数据来源和更新时间。
- 简单修改支持时间、备注、增删安排；复杂修改支持替换地点、减少步行、雨天调整。
- 单项调整默认仅影响目标；若改变时间造成冲突，提示问题。用户选择联动调整后再重排受影响部分。
- 历史记录用调整内容与时间描述，必要时可查看变化和恢复。

### 出行与行前事项

- 在现有行程内提供“今天/下一站”，可先用页面内入口验证，暂不增加一级导航。
- 行前事项有持久化完成状态，信息核实与准备完成分别管理。
- 增加只读分享链接，可关闭；分享内容不包含聊天与私人备注。
- 提供打印/导出与最近一次行程的弱网查看，再依据真实使用选择缓存范围。

## 7. 分阶段推进

### 阶段 A：保住需求、建立结果规则、统一任务

交付：

1. 全量需求保存，独立需求档案，硬性限制固定保留与可编辑。
2. 日期、人数、预算的基础结构化字段与创建后编辑能力。
3. 日期覆盖、重复日期、时间范围与冲突等确定性校验；未知字段有明确状态。
4. 聊天、生成、修改共享任务 ID，持久任务状态、幂等提交、失败原因和总时限。
5. 对话日志开关、保留周期及文档修正。

验收：

- 超过 8 条想法、超过 12 条消息后，早期必去/避开/忌口仍保留并进入规划上下文。
- 更新某项偏好后，有可解释的当前有效值；展示收起或分页不影响保存。
- 明确日期行程覆盖用户所需日期；无效日期与已知重叠时间不能作为成功结果静默保存。
- 页面刷新、离开和重入能够找到生成状态或已完成结果。
- 同一请求重发只产生一条消息和一个任务；同旅行任务的写入顺序有明确规则。
- 模型失败保留现有行程，失败任务能重试；进程重启后的未完成任务可恢复或进入明确可重试状态。
- 默认运行不持续落盘完整对话日志。

### 阶段 B：路线可信、可修改、可带出门

依赖：阶段 A 的结构化需求、稳定任务与校验接口。

交付：

1. 接入一个景点 POI 与路线服务，保存地点 ID、坐标、来源和查询时间。
2. 交通耗时进入行程检查，加入可获取的营业/开放时段与预约信息；查不到的内容保留待核实。
3. 地址复制与地图导航入口。
4. 简单编辑与增删安排，复杂修改按影响范围处理，记录实际变化。
5. 当天/下一站入口、行前清单勾选、只读分享和基本导出。
6. 基础预算分项与总额估算，明确来源和不确定范围。

验收：

- 选定试点城市的关键地点可以核实，坐标无法确认的地点不会给出确定导航结果。
- 每段主要移动有来源明确的耗时或清楚的待核实提示；无法赶上的安排不能被标为已检查通过。
- 仅改备注不调用模型；复杂修改只改变用户选择的范围。
- 调整导致相邻冲突时可定位问题，并能选择联动修正。
- 清单勾选刷新后保留；分享者能关闭链接，访问者只能读取分享的旅行内容。
- 用户出门时能找到当天安排并打开下一地点；导出结果包含目的地、日期、安排、地址和待核实事项。

### 阶段 C：可邀请真实用户、可持续运行

可以与阶段 B 中低依赖事项并行。多实例发布依赖增量持久化完成。

交付：

1. 从全量内存快照转成数据库增量读写，旅行修订号与事务保护；历史数据迁移与备份恢复演练。
2. 账号找回、账号/旅行数据管理和必要的请求防护；按真实发布入口验证会话与权限。
3. 持久任务恢复、用户/旅行额度、并发限制和模型总预算控制。
4. 结构化运行指标、错误反馈与用户行为事件。
5. 分离开发与发布配置，固定依赖、自动回归与发布回滚步骤。
6. 组织真实用户试用，持续修复需求丢失、地点错误和不合理路线。

验收：

- 两个独立进程操作不同旅行不会相互覆盖；同旅行过期更新能被识别并保留现状。
- 备份可以恢复账号、旅行、当前行程与历史记录。
- 找回密码与删除旅行在手机端可完成；删除规则包括聊天与相关调试数据。
- 可追踪每次生成的成功/失败、耗时、调用次数与用量；额度在后端执行。
- 具备明确的发布检查、回滚与错误反馈入口。
- 完成首批真实用户任务观察，形成下一阶段的实际问题清单。

### 阶段 D：依据使用证据增强

候选方向：多方案比较、天气变化后的主动替代安排、更完整预算与实际支出、个人旅行偏好复用、多人协作。

每个候选项先明确用户问题与成功指标，再决定是否进入开发。支付与商业化也需要先验证有效行程率、持续使用与服务成本。

## 8. 下一轮任务拆分建议

以下是阶段 A 可直接拆成独立交付的工作，不要求一次重写全部架构。

| 顺序 | 任务 | 主要涉及文件/模块 | 完成条件 |
| --- | --- | --- | --- |
| 1 | 分离想法保存和页面展示限制 | `models.py`、`store.py`、想法页、持久化 | 旧想法不被第 9 条覆盖；页面可查看全部内容 |
| 2 | 建立旅行需求档案与基础编辑 | 新需求模型、`store.py`、`agent_client.py`、创建/需求页 | 日期、人数、预算、硬性偏好有稳定数据；聊天只更新已识别的字段 |
| 3 | 增加行程业务校验 | 新校验模块、`agent_client.py`、保存路径 | 非法日期、缺天、时间重叠有规则与可定位提示；未知字段按状态处理 |
| 4 | 统一生成与修改任务 | 任务模型与存储、`main.py`、`store.py`、前端状态查询 | 先返回任务 ID；刷新可继续查询；重复请求去重；失败可重试 |
| 5 | 整理日志与运行信息 | `agent_client.py`、环境模板、README | 调试显式启用；定义保留期；运行记录避免不必要的用户原文 |

需求档案与业务校验的协议确定后，POI/路线模块可开始设计。任务状态直接写入现有 SQLite 是初期可评估方案，是否引入外部队列由部署与吞吐需求决定。

现有单项调整已提供目标 ID 与过期行程检查，应复用这些保护。扩展联动调整时增加明确范围与差异检查，不能通过整份模型输出直接覆盖用户未授权的部分。

## 9. 质量验证与产品指标

### 旅行效果验证集

建立约 30 个固定旅行需求案例，先由人工整理约束与可接受结果，不以生成文本是否顺眼作为唯一依据。

### 建议采集的指标

| 指标 | 定义与用途 |
| --- | --- |
| 创建到首版成功率 | 发起首版生成的旅行中，成功保存并被用户打开的占比 |
| 首次有效行程耗时 | 从开始创建到打开可用首版的实际时间，按中位数/P95观察 |

| 单次成功成本 | 成功生成或修改对应的调用次数、token、工具用量和费用估算 |

目前没有这些产品指标的基线。先采集再设目标；初步关注“成功生成后被实际使用”的比例，避免只统计聊天数量或返回成功的请求。

## 16. Agent 路线耗时与排程检查实施进展

- 新增 query_route：使用已匹配 POI 的坐标查询高德步行、公交和驾车预计耗时，只接受可信地点目录中的 ID，不接受模型自报坐标，不查询火车票。
- 信息收集支持最多 3 轮，允许先获取地点、再查路线。同一请求按起终点 ID/坐标和交通方式缓存结果，包括失败结果；最多查询 32 个不同路段，超出部分明确待核实。
- 生成后检查相邻停留地点，以及明确抵离地点的接驳。抵离名称只有唯一精确匹配时绑定；城市未知、重名、区域建议和时间不完整不猜测，保留待核实事项并明确未完成全部路线可行性检查。
- 交通条目不作为新的停留地点，不重复计算接驳；有独立交通条目时采用其交通方式。活动间隔及显式交通条目长度必须容纳查询耗时，固定休息时间不能挪作交通，末站和返程需满足离开边界。
- 冲突将真实路线结果反馈给 Agent，最多修正一次；仍有冲突保留原行程。单项调整先合并原行程再检查，不允许改邻居绕过冲突；可同步更新受影响的路线资料。
- 多日行程只在上一晚明确住宿地点已匹配时使用该起点查询次日首站，并检查当日显式接驳时段；住宿或出发时间未知时明确待核实，不用前一天最后一个景点猜测出发位置。
- 路线状态、方式、耗时、距离、来源、查询时间与说明随行程和版本保存。行程详情展示“前往这一站”和“前往离开地点”，没有逐条查询或候选选择页面；原想法白板布局不变。
- 最终生成使用严格 JSON Schema，要求 plan 非空及条目 ID，避免真实模型输出标点前缀字段或局部候选列表。兼容服务不支持时按原流程退回 JSON 对象/普通输出，仍执行结构和业务校验；信息收集后显式切换到最终生成任务。

验证：226 项 Python 测试通过，覆盖三种交通方式、权限/网络/空路线/无效耗时降级、缓存与查询上限、活动间隔、交通条目时长、休息占用、抵离接驳、模糊时刻、重名抵离地点、模型伪造路线拒绝、有限修正、实际单项合并及持久化/版本恢复。地点与路线展示、320/390/430/1000px、行程、聊天、需求和任务浏览器回归通过。

真实验证使用合成旅行，不保存到用户数据库。当前 Key 成功查询杭州东站→灵隐寺的步行、公交和驾车路线。完整真实模型案例：2026-11-01 10:00 到杭州东站，20:00 离开，灵隐寺、庆春朴门(灵隐店)午餐及原地休息；7 个条目、4 个匹配地点条目、5 条可用路线记录，其中 3 条真实跨地点查询、2 条同一已匹配 POI 的零移动记录，无待核实交通段。查询时估算分别为东站→灵隐寺公交 67 分钟、寺→餐厅步行 17 分钟、餐厅→东站公交 60 分钟，排程和抵离检查通过。期间发现交通条目重复计为停留点以及模型输出结构不稳的问题，已修复并回归；失败案例未保存行程。

边界：路线是查询时估算，不保证未来路况、公交班次或景点开放；额外候车、安检、内部步行仍需估算并核实。混合交通接驳及详细导航线路尚未完整覆盖，跨日首站仅在住宿与当日接驳信息明确时可核实。单进程、任务总时限和取消等限制维持现状。下一阶段建议开放时间、门票/预约和真实用户试用。

## 17. 受控 Agent Loop 新版本

- 保留现有路线版本的本地快照后，新增 `app/agent_loop.py`。它提供可序列化的工作状态、动作、观察结果、阶段、工具调用预算、步数预算、动作历史和明确终态。
