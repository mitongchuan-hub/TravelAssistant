# TravelAssistant 模拟面试问答

> 本文根据当前仓库代码、提示词、测试数据和项目文档整理。面试回答应以当前真实实现为准；没有实现的能力要明确说“当前版本尚未实现，计划这样改”，不要把设计设想说成线上事实。
>
> 重点代码：[`app/agents/task_runtime.py`](../app/agents/task_runtime.py)、[`app/agents/agent_runtime.py`](../app/agents/agent_runtime.py)、[`app/workflow/turn_workspace.py`](../app/workflow/turn_workspace.py)、[`app/workflow/turn_commit.py`](../app/workflow/turn_commit.py)、[`app/workflow/tasks.py`](../app/workflow/tasks.py)。

## 一、先记住项目真实口径

### 90 秒项目介绍

> TravelAssistant 是我独立开发的同城游玩规划 Web 产品，面向已经确认住宿、刚到陌生城市、希望少查资料并快速形成短途行程的用户。用户先确认住宿地点、出行日期和游玩天数，再通过聊天补充节奏、必去、避开项、交通方式、预算和饮食偏好。系统由主 Agent 统一调度需求整理、实时查询、路线规划和行程修改能力，调用高德地图查询地点和路线，调用 Open-Meteo 查询天气，最后生成每天从住宿出发并返回住宿的中文行程。
>
> 项目采用 FastAPI、SQLite 和 OpenAI 兼容模型 API。Agent 的结果不会直接写数据库，而是先进入本轮工作区形成候选，主 Agent 明确选择后，由服务端在提交边界再次校验请求、需求版本、行程基线、任务代次和候选来源，再原子提交。用户连续发送新消息时，旧任务会被标记为已替代或在提交前被判定为过期，避免旧结果覆盖当前状态。当前版本没有使用 RAG，核心事实主要来自地图和天气工具；景点背景知识库属于后续扩展方向。

### 项目边界

- 当前只做已确认住宿所在城市的同城游玩。
- 每天以同一住宿为起点和终点。
- 出行日期、游玩天数、住宿地址和地图位置确认是生成行程的必要条件；人数、预算和出门/返回时间可以未知。
- 当前不支持购票、预订、支付、跨城路线，也不承诺未来路况、班次、开放、票价或现实可执行性。
- 当前没有 RAG、Embedding 或 Rerank。不要说已经使用了这些技术。
- 行程正文是主数据，卡片是异步派生展示；卡片失败不能覆盖正文。
- 当前应用按单进程运行，不支持直接增加多 worker。

### 评测口径

`tests/datasets/off_domain_answers.json` 共 80 条：60 条其他领域请求、10 条混合请求、10 条合法对照；60 条其他领域请求覆盖 12 个领域，每个领域 5 条。一次真实评测中，80/80 正常结束，70 条越界/混合请求中 0 条出现其他领域实质作答，10 条合法对照中 0 条被误拒；但另有 2/60 条纯越界请求出现无授权业务调用。这个结果只能说明该轮范围遵守情况，不能证明端到端路线质量或长期稳定性。

另一套 `scope_comprehensive` 共 50 条，历史记录曾发现错误历史承诺导致数学越界、无授权工具调用、把“未保存”说成“已记下”等问题。因此面试时应主动说明：评测不仅统计通过，也保留失败和流程问题。

## 二、基础项目介绍与个人贡献

### 1. 请用 1～2 分钟介绍 TravelAssistant。

**建议回答：**

它是我独立开发的同城游玩规划 Web 产品。用户确认住宿、日期和天数后，通过聊天补充游玩偏好，系统调用高德地图和 Open-Meteo 获取地点、路线和天气信息，生成每天从住宿出发并返回住宿的路线，并支持对现有行程局部修改。

实现上不是让模型直接改数据库，而是由主 Agent 调度需求整理、研究查询、规划和修改四类能力；每个能力返回候选成果，主 Agent 选择后进入 `TurnWorkspace`，最后由 `TurnCommit` 在服务端做版本和来源校验并原子提交。当前版本不使用 RAG，重点解决的是实时工具调用、业务边界、失败恢复和旧任务一致性。

### 2. 这个项目主要解决了什么问题？

解决用户在陌生城市中需要自己查地点、看天气、拼接交通和安排每日时间的问题。系统把住宿、日期、偏好和实时查询结果组织成一份可阅读、可局部调整的同城路线。

### 3. 目标用户是谁？为什么选择同城游玩？

当前定位是假设：已经订好住处、来到陌生城市、想少查攻略的人。选择同城游玩是为了先控制问题边界：住宿是稳定起点，地图和天气查询相对明确，跨城票务、酒店和支付等复杂能力可以暂不纳入。

### 4. 从进入系统到拿到行程的完整流程是什么？

用户注册或登录，创建旅行，填写住宿、城市、日期和天数；住宿地址通过高德搜索后由用户选择候选，服务端保存可信 POI（**名称、地址、经纬度、类别、唯一 ID**）。聊天消息提交为任务，主 Agent 读取当前需求和任务状态，必要时调用需求整理能力或研究能力，条件满足后调用规划能力。规划候选经工作区和提交边界校验后保存为正文，后台展示任务再从正文提取卡片。用户可以基于当前行程发起局部修改。

### 5. 和普通聊天机器人有什么区别？

普通聊天机器人主要输出一段文本；本项目有明确业务范围、结构化任务状态、实时工具、可信地点来源、行程版本和提交校验。它会区分“查询尝试”“候选结果”和“已保存效果”，也会保留未知信息，而不是让模型凭常识补全。

### 6. 哪些模块是你独立完成的？

可以回答：我独立完成了产品流程、FastAPI 路由、认证、住宿地点匹配、需求校验、AgentLoop、MCP/地图与天气工具适配、任务状态和提交边界、SQLite 持久化、正文与卡片展示、局部修改以及自动化测试和评测基础设施。

### 7. 最难的问题是什么？

最难的是 LLM 任务执行期间状态可能变化：用户发来新消息、需求变了、行程被修改或卡片异步生成完成。单纯依赖模型输出无法保证一致性，所以我把模型输出降级为带来源的候选，服务端捕获请求基线，提交前再次验证，过期候选被拒绝。

### 8. 如果重新设计，优先改进什么？

第一，补充端到端的真实业务评测，尤其是路线时间、营业状态和用户偏好满足度。第二，把数据库和任务队列改成适合多进程部署的架构。第三，增加可解释的观测指标，例如每轮模型调用、工具调用、耗时、失败原因和最终提交结果。

### 9. 当前有哪些功能没有实现？

没有 RAG 知识库、票务和酒店预订支付、跨城规划、在线地图几何校验、多版本行程恢复和独立第二模型事实复核。当前天气、营业、票价和路线结果也不等于现实可执行性保证。

### 10. 如何证明它有使用价值？

当前主要证明了产品闭环和技术合同可运行，尚没有真实用户研究或线上转化数据。可以用任务完成率、有效行程率、修改成功率、查询失败恢复率、用户采纳率和人工评审质量继续验证；不能只用模型回复长度或评测拒答率证明产品价值。

## 三、需求整理与多轮对话

### 11. “帮我安排一个周末行程”还缺少什么？

至少需要住宿地址并完成地图位置确认、目的地城市、出行开始和结束日期或可计算的游玩天数。人数、预算、交通方式、节奏、必去和避开项可以后续补充，不应因为这些可选项阻止首轮生成。

### 12. 哪些信息必须问，哪些可以默认？

住宿和日期窗口是当前生成流程的必要条件，不能默认今天、一天或当前位置。人数、预算、出门/返回时间不默认成用户事实；出门时间未知时可以在行程中给建议时段，但必须标明是建议。

### 13. 如何避免一次问十几个问题？

按任务阻塞程度分层，只追问当前生成真正缺失的必要条件。已知住宿和日期后，人数、预算等可选信息不应一起追问；一个 `ask_user` 只提出一个关键问题，并把答案绑定到明确的任务和字段。

### 14. 用户输入互相冲突怎么办？

把冲突保留在本轮，不擅自选择。例如先说总预算 300 元、后说人均 500 元，应澄清预算口径。服务端的 `update_requirements` 会校验日期、天数、预算口径和时间格式，校验不通过就不写入正式需求。

### 15. 没有偏好时如何生成默认方案？

可以在已知条件下选择少量、相对紧凑的同城主线，但不能把默认路线说成用户偏好。规划提示词要求少排景点、减少跨区移动，并把未确认的开放、票价、预约和雨备条件标成待核实。

### 16. “轻松一点”“适合约会”如何变成约束？

先作为语义偏好保存在 `pace` 或备注中，规划能力再将其解释为减少换乘、预留休息、控制景点数量等软约束。软约束不能伪装成硬事实，最终应在 `constraints_met` 或正文中说明采用了什么安排。

### 17. 用户改变日期怎么办？

先整理本轮正式需求并增加需求 revision；旧行程基于旧需求的 `plan_basis` 不再是当前依据。天气和路线证据也按新日期重新查询，不能继续使用旧日期的结果。

### 18. 如何区分修改行程和新问题？

看本轮消息的实际目的、当前任务和当前行程。用户说“第二天下午换成室内景点”属于 `revise_itinerary`；问“当前方案为什么减少换乘”属于只读解释；提出新的全局日期或住宿变化，则先进入需求整理。

### 19. 只修改第二天上午时如何避免重排全部行程？

请求携带服务端解析的 `display_target` 或有效 `item_id`、当前 `plan_basis` 和修改范围。修改 Agent 只处理授权范围，但开放式修改最终仍返回完整正文；系统不会承诺未授权段落逐字不变，会对受影响的邻接路线和住宿往返重新核对。

### 20. 多轮上下文如何保存？

消息、旅行需求、想法卡片、当前计划、任务和工作流状态都保存在 `DemoStore`，持久化时写入 SQLite 快照及关系表。主 Agent 首先接收服务器投影，需要更多内容时通过 `read_context` 按需读取，不能把模型看到的最近几条消息当成完整状态。

## 四、AgentLoop 与系统架构

### 21. 为什么需要 Agent，而不是固定函数编排？

因为用户可能只问天气、只查餐厅、提出局部修改、补充需求或混合多个事项，下一步不固定。主 Agent 可以根据任务状态选择需求整理、研究、规划、修改或追问。不过日期校验、权限、版本、工具参数和提交都由代码完成，不能把确定性规则交给模型。

### 22. AgentLoop 每轮做什么？

主循环最多 12 步：读取服务器提供的上下文，模型选择一个主工具，运行时校验工具名和 JSON Schema，执行专业能力或上下文读取，返回结构化观察结果，再继续决策。最后必须调用 `ask_user` 或 `finish_turn`，或在异常/预算耗尽时 fail-closed。

专业能力内部也有有界循环：需求和研究能力最多 6 步，规划和修改能力最多 10 步；最后一步只允许 `complete_capability`，避免在没有收尾额度时继续查工具。

### 23. Agent 如何选择高德还是天气工具？

主 Agent 先选择 `research` 能力并给出问题，研究能力根据问题从 `search_places`、`search_food`、`query_weather` 和 `query_route` 中选择。提示词规定工具用途，运行时再用允许工具集合和参数 schema 限制。需要工具结果才能规划时，规划能力消费已经登记的 evidence。

### 24. 如何知道任务完成？

主 Agent 只能用 `finish_turn` 或 `ask_user` 结束；专业能力必须调用 `complete_capability`，并返回 `ok`、`needs_input`、`unavailable` 等状态。没有结构化结束工具的普通模型正文不能直接当作完成合同。

### 25. 重复调用同一工具如何避免死循环？

通过主循环和专业能力最大步数、模型数、工具数、外部查询数及总时间预算限制；相同无效调用重复出现时失败关闭。每个工具的参数也必须通过 JSON Schema，外部 MCP 还有单次查询上限。

### 26. 如果 Agent 不调用工具直接编造怎么办？

当前代码已经有部分运行时防护：专业能力没有调用 `complete_capability` 时不会把普通正文当作完成；规划提示词要求具体事实来自工具，地点和路线只能引用可信 POI，天气和路线失败返回未知。若要进一步强制“生成前必须查天气/路线”，应增加确定性的前置状态，例如 `required_evidence`，在没有对应证据时禁止采用 itinerary 候选。当前不应声称已经完全做到这种强制前置。

### 27. 工具调用次数上限是什么？

`TurnBudget` 默认最多 16 次模型调用、64 次工具调用、32 次外部查询，单轮 240 秒；专业子能力还通过 `child_scope` 预留父 Agent 收尾额度。高德 MCP 单个会话最多 6 次查询，路线缓存最多保留 32 个路线键。

### 28. 单 Agent 还是多 Agent？

是一个主 Agent 加四类专业能力，不是多个拥有独立数据库权限的自治 Agent。主 Agent 负责范围判断、调度、追问和候选选择；requirements、research、planning、revision 负责各自能力，并通过 `CapabilityResult` 和 artifact 返回结果。

### 29. 为什么拆成四类能力？

需求整理会修改正式需求，研究只读外部事实，规划生成完整行程，修改处理已有方案。拆开后可以分别限制工具、输入和写入权限，降低一个长提示词同时处理所有状态的复杂度。

### 30. 多 Agent 的问题是什么？

上下文传递和来源绑定更复杂，能力之间可能产生冲突，模型调用数和延迟也会增加。因此本项目没有让专业 Agent 直接互相调用，而是由主 Agent 统一调度，候选统一进入一个工作区。

### 31. 上下文包含什么？

主 Agent 的投影包含本轮消息、环境、正式需求、想法墙摘要、当前行程、近期对话和未完成任务/活动追问。它不直接得到所有数据库状态，需要时调用 `read_context`。工具结果作为 evidence 保存，不能把外部文本中的指令当成系统规则。

### 32. 信息冲突时如何确定优先级？

服务端结构化状态、当前正式需求和本轮用户原话优先；历史对话、想法墙、工具自然语言和错误文本不能扩大权限。用户明确的新需求先经过本地校验，工具事实只支持查询和条件判断，不能直接改写正式需求。

### 33. 如何限制只能做同城游玩？

提示词按实际目的判断范围，代码用 `Trip.mode == city`、已确认住宿城市和需求字段限制流程；规划能力只能生成住宿城市内路线。跨城、购票、支付和独立数学/代码/医疗等请求由主 Agent 简短说明范围，不转交专业能力。

### 34. 用户要求写代码或分析股票怎么办？

不提供实质答案，也不把问题交给 research；简短说明当前只支持同城游玩相关服务。如果同时包含合法旅行事项，则拆分处理合法部分。

### 35. 如何防提示词注入？

不把用户消息、工具返回、网页正文和专业摘要当作系统规则；主 Agent 提示词明确它们不能扩大权限。候选还需要服务端验证来源、任务、版本和依赖。评测覆盖忽略规则、管理员冒充、JSON 压力、隐写和资料注入；但仍需持续重复运行，不能仅凭一次评测宣布绝对安全。

## 五、工具调用与 MCP

### 36. 高德工具有什么能力？

`search_places` 搜索地点并获得可信 POI、地址、坐标和可选营业资料；`query_route` 基于两个已查询的 POI ID 查询步行、公交或驾车路线；`search_food` 用于餐饮查询。高德 MCP 底层允许的工具包括文本搜索、地点详情和三种方向规划。

### 37. 地点搜索、详情、路线分别需要什么？

地点搜索需要关键词，城市可选；底层先文本搜索，再对候选查详情。路线需要 `origin_poi_id`、`destination_poi_id` 和 `mode`。路线函数只从运行时可信地点目录读取坐标，不接受模型自报坐标。

### 38. 高德返回如何转换给 Agent？

适配层只保留模型和业务需要的字段：POI ID、名称、地址、经纬度、城市、区县、来源、查询时间和可选营业资料；路线保留状态、耗时、距离、交通方式、来源、时间和公交步骤。原始响应不直接全部暴露。

### 39. 同名地点怎么处理？

返回候选而不是擅自选择；地点由用户在住宿设置中确认。规划中如果具体必去地点仍有重名或无法确认，会追问。可信地点由程序保存，模型不能提交自己的坐标。

### 40. 住宿地址匹配失败怎么办？

返回“地点待核实”，保留用户输入，不生成依赖旧坐标的路线。用户必须选择有效地图候选，服务端还会校验 POI 城市与需求城市一致。

### 41. “学校附近”怎么办？

先查询明确的学校或区域；如果无法唯一对应具体 POI，就要求用户补充城市、学校名称或选择候选。不能把“附近”直接变成一个假坐标或具体门店。

### 42. 路线信息如何影响行程？

路线耗时和距离用于安排景点顺序、活动窗口和住宿往返；公共交通结果还要按 `transit_steps` 展示线路、上下车站、步行和换乘。查询耗时只是当时估算，不代表未来路况、候车或场地内部步行。

### 43. 天气日期超出范围怎么办？

`query_weather` 先校验日期格式，再检查日期是否在 Open-Meteo 返回的预报日期列表中；超出范围返回 unavailable 和预报范围，不能用今天或常识代替目标日期。

### 44. 天气失败时怎么办？

保留天气未知，必要时交付条件方案或提示出发前再次确认。外部请求有超时和预算，失败不会被模型改写成“晴天”或一个编造概率。

### 45. 工具超时怎么处理？

工具函数将网络异常、超时、权限和格式错误转换为结构化 unavailable；父 Agent 可以修正参数、换合法步骤、澄清或安全结束。重复相同无效调用会触发失败关闭，已有行程保留。

### 46. 返回字段缺失怎么办？

适配层只接受有效坐标、有效耗时和符合格式的字段；缺字段就保留未知。例如公交线路没有上下车站时，`transit_detail_status` 为 partial 或 missing，不能凭经验补站点。

### 47. 为什么使用 MCP？直接 Python 调 API 不行吗？

直接调用也可以。MCP 的价值是把地图能力作为标准化工具边界暴露给 Agent，便于发现工具、统一参数和替换下游；但本项目仍保留 Python 适配层做密钥、超时、错误、字段和可信 POI 校验，所以 MCP 不是安全边界本身。

### 48. MCP 工具 schema 如何设计？

工具参数使用对象 schema、必填字段、枚举和 `additionalProperties: false`；运行时再次用 `Draft202012Validator` 校验，不能只相信模型或供应商的 strict hint。

### 49. 是否把原始 API 全部暴露给模型？

不暴露。只返回经过适配和清洗的业务字段，减少上下文、隐藏供应商细节和潜在指令注入；原始响应只应在受控日志或调试环境中保存，并注意隐私和凭证。

### 50. 如何防止恶意工具参数？

工具名必须属于当前能力允许集合，参数通过 JSON Schema，路线 ID 必须来自运行前已知的可信地点目录，城市和日期也在业务层校验。MCP 客户端只允许预设的高德只读工具，密钥由服务端配置，不进入模型参数。

### 51. 工具是否可以并行？

相互独立的只读查询可以在一条专业能力响应中最多并行四项；依赖前一次地点结果的路线查询必须分轮。写入、完成工具和精确编辑必须单独调用。

## 六、行程生成与业务规则

### 52. 行程有哪些核心约束？

同一住宿城市内、每天住宿出发并返回；日期和天数一致；交通方式遵循用户选择；必去和避开项有效；餐次覆盖实际出行窗口；人数和预算未知不擅自补值；事实和路线依据来自工具，未知明确标出。

### 53. 如何保证每天从住宿出发并返回？

`city_outing_brief` 将已确认住宿写入 `daily_start` 和 `daily_return`；规划提示词要求查询实际第一站和最后一站到住宿的路线。提交前可以校验正文或结构化计划中的日期、住宿和证据，但当前没有一个完整的通用路线可执行性验证器，所以面试中不要说已经证明所有路线现实可行。

### 54. 如何避免景点安排过多？

提示词要求选择少量紧凑主线，并根据路线和出门/返回时间安排游览、用餐和休息；如果用户没有时间窗口，则用建议时段表达。当前主要是提示词和证据约束，仍可补充代码级的活动数量和时间重叠检查。

### 55. 如何处理开放时间冲突？

地点搜索返回的营业资料只作为查询时参考，不保证目标日期开放。系统不能把它当成已核实事实；如果开放时间对方案关键，应保留待确认或要求用户在出发前核实。

### 56. 两个景点距离过远怎么办？

先查询实际顺序的路线；如果时间过长或查询失败，减少跨区安排或给出条件方案。查询失败时不编造耗时，不能只根据景点名称说“很近”。

### 57. 跨城景点怎么办？

当前系统只做住宿城市内路线。对跨城请求说明边界，不生成完整跨城路线，也不模拟购票；如果请求中有独立的同城事项，可以继续处理同城部分。

### 58. 如何判断地点是否适合游玩？

由用户需求、地点查询结果和规划语义综合判断；系统可以使用 POI 类型和名称，但查询到 POI 不代表适合当天开放、可预约或有某种设施。没有证据的设施、雨备和门票信息保持未知。

### 59. 地图结果和用户偏好冲突怎么办？

正式需求和本轮明确约束优先于想法墙和模型默认。若所有候选都冲突，说明冲突并追问；不能因为地图返回热门地点就忽略用户明确避开项。

### 60. 天气不好会自动替换吗？

只有天气证据明确且用户授权条件替换时才可以形成条件候选。当前协议首版支持结构化“降雨概率达到阈值”条件；没有阈值或室内地点证据时，不能把下雨自动等同于必须换场景。

### 61. 用户要求排得很满怎么办？

可以按用户偏好尝试，但仍要保留交通、用餐和返回住宿的时间，说明查询耗时、候车和开放条件不确定。系统不能为了满足“满”而省略必要餐次或安排无法闭合的路线。

### 62. 行程由模型生成还是代码组合？

主行程正文由规划能力生成中文 Markdown 候选，服务端负责候选来源、需求依赖、证据引用和提交校验。后台展示卡片再由无工具展示 Agent 从已保存正文中提取到固定 schema，展示 Agent 不重新规划。

### 63. 自然语言再整理结构化有什么风险？

风险是第二次模型提取遗漏条件、误把建议变成事实或产生非法格式。因此正文保留为主数据，卡片是派生展示；展示输出使用 JSON/YAML 解析和 JSON Schema 校验，失败只影响卡片，不丢正文。当前不应说所有正文业务字段都已经由结构化 schema 完整校验。

### 64. 展示 JSON 字段有哪些？

`schema_version`、`title`、`overview`、`budget_note`、`weather`、`days`、`preparation`、`pending_items` 和 `risks`。每天有日期、标签、主题和 items；item 有时间、标题、类别、地点、时长、描述、费用和备注。展示 schema 不包含 POI ID 和坐标。

### 65. 非法 JSON 如何处理？

按配置解析 JSON 或 YAML，禁止重复字段、别名、标签和多文档，再用 JSON Schema 和日期窗口校验。解析失败或校验失败时标记 display 失败，正文仍可阅读，并支持只重试卡片。

### 66. JSON 正确但业务错误怎么办？

展示层主要验证结构、日期数量和字段类型；它不重新判断路线现实可行性。业务错误应在规划/提交边界或后续人工/规则评审中发现。这个边界要在面试中主动说明。

### 67. 前端和数据库保存的行程是否一致？

正文保存到 `TripPlan.text`，卡片是带正文 hash 的派生数据。卡片展示必须绑定 `display_source_hash`，正文变化会使旧卡片失效。前端拿到的是当前服务端状态，不能把异步卡片当成新的主计划。

### 68. 局部修改如何保护未修改部分？

请求携带当前计划基线和授权范围；精确追加/替换由 `edit_plan_text` 做唯一匹配和原文约束，开放式修改由修改能力返回完整正文。代码保证旧基线不会被静默覆盖，但开放式模型重写不保证其他段落逐字不变。

## 七、任务状态、并发与可靠性

### 69. 一次规划任务有哪些状态？

持久任务有 `queued`、`running`、`succeeded`、`failed`、`superseded`；工作流内的复杂事项还有 waiting_user、completed、cancelled、suspended 等状态。两套状态分别表示执行记录和跨轮业务任务。

### 70. 状态存在哪里？

运行时使用内存中的 `DemoStore` 和锁；开启持久化时保存到 SQLite 快照及关系表。当前按单进程运行，所以不能直接靠内存状态支持多 worker；生产扩展时需要外部任务队列和共享数据库。

### 71. 两次修改同时提交怎么办？

同一旅行有活动任务时，新的 plan/revision 通常会被拒绝，聊天消息可以将旧活动任务标记为 `superseded`。执行中的旧任务通过 `cancelled` 回调感知替代状态；即使它没有及时停止，提交前的 `_turn_conflict` 仍会检查任务状态、请求 ID、消息、需求 revision、workflow revision、sequence/epoch 和 plan basis。

### 72. 如何防旧结果覆盖新方案？

不是只靠一个版本号，而是多项基线联合校验：任务的 request ID 和原消息、需求 revision、工作流 revision、sequence、epoch、计划 ID、正文 hash 和 business hash。提交在独立 stage 上完成，只有上下文仍匹配时才发布；冲突则返回未提交，旧候选不能覆盖新状态。

### 73. 服务执行时重启怎么办？

启动恢复时不会自动重跑写入任务；`queued`/`running` 任务会被恢复为失败并提示用户检查后重试，思考中的消息也会替换成失败提示。已有需求和行程保留。

### 74. 数据库保存成功但前端响应失败怎么办？

任务有持久状态和 request ID，前端可以通过任务查询接口获取结果。重复提交同一个 request ID 且内容一致时返回同一任务，避免重复执行；内容不同则冲突。

### 75. 如何避免重复创建任务？

`submit_task` 以旅行、`request_id`、任务类型和 payload 做幂等检查；相同请求返回已有任务，不同内容复用同一 ID 会抛冲突。失败重试使用新的 request ID，并绑定原失败任务。

### 76. 如何设置超时？

外层 `TurnBudget.seconds` 默认 240 秒；外部 HTTP 也受剩余预算约束，Open-Meteo 默认单次 8 秒，高德 MCP 从环境变量读取且不能超过 120 秒。模型、工具和外部查询分别计数。

### 77. 部分工具成功、部分失败能否保存？

可以把已获得的独立证据保留为本轮观察；行程候选需要依赖满足才可采用。若规划不可用，独立且已验证的需求候选仍可以提交，并明确“需求已保存，行程未生成”。不能把部分路线查询说成完整路线成功。

### 78. 重试是否重新调用所有工具？

当前失败任务重试使用新的 request ID，通常重新执行当前任务；本轮运行内的只读结果可缓存复用，跨任务是否复用取决于持久化证据和当前基线。对于实时天气和路线，重新查询更可靠。

### 79. 如何记录一次任务？

任务记录包括 request ID、旅行 ID、消息、payload、计划基线、需求/workflow revision、状态、回执和结果 URL。`agent_runs` 表还支持保存输入、过程、输出、模型、token、工具调用数和耗时，但 README 也说明运行记录包含敏感数据、保留周期尚待完善。

### 80. 删除任务时如何清理中间数据？

当前删除旅行时会阻止删除正在运行的任务，同时移除旅行、消息、计划、想法、任务和展示任务；展示派生任务会被丢弃。`agent_runs` 的清理/保留策略目前不完整，面试中应说明这是待补强项，不要声称已实现完整生命周期清理。

### 81. 两个用户同时规划会互相影响吗？

业务状态按 trip_id 和 owner_id 隔离，候选的上下文也绑定旅行和所有者。当前单进程通过锁保护内存和提交；多进程部署前需要把锁、任务队列和事务移到共享基础设施。

### 82. SQLite 并发有什么问题？

SQLite 适合当前单进程和小规模原型，但多进程写入、长事务、任务队列和高并发会受到锁竞争影响。当前采用 staging、事务保存和单进程约束；生产环境可迁移 PostgreSQL，并用独立 worker 处理任务。

### 83. 如何避免状态非法跳转？

提交边界验证 task 是否仍 running、请求基线是否匹配；已结束工作流任务不能复活，任务状态变化必须有被采用的 task artifact 支持。最终候选和回执在同一 staged persistence 中发布。

## 八、提示词、结构化输出与安全

### 84. 系统提示词有哪些核心规则？

范围限制、住宿城市边界、日期和天数前置条件、未知不补造、工具证据边界、候选而非直接写入、任务追问绑定、工具失败恢复和结构化结束合同。不同专业能力只拿到需要的工具和规则。

### 85. 哪些放提示词，哪些放代码？

语义范围、用户意图理解、路线叙述和工具选择放提示词；字段类型、日期、预算、权限、POI 来源、任务基线、候选依赖、并发、超时和数据库提交必须放代码。提示词是引导，不是最终安全边界。

### 86. 为什么不能只靠提示词？

模型可能忘记调用工具、输出非法参数、误用历史 ID、把候选说成已保存，或被用户和外部文本诱导。代码可以验证 schema、来源、版本、依赖和提交效果，即使模型行为异常也能 fail-closed。

### 87. 如何防止编造地点、天气和路线？

地点和路线必须来自工具返回的可信 POI；路线不接受模型自报坐标；天气只从 Open-Meteo 结果取值。失败、缺字段或超范围时返回 unknown/unavailable，提示词也要求不把查询尝试当作事实。

### 88. 模型声称“高德显示”但没有调用怎么办？

当前专业能力没有证据就不能登记相应 evidence，规划候选也应依赖研究证据。进一步可在提交前增加事实引用检查：正文中的具体路线/天气字段必须对应本轮证据，否则拒绝候选或降级为待核实。当前应把它表述为已有方向，除非代码中有完整正文事实抽取校验。

### 89. 多轮诱导怎么办？

每轮都重新按当前请求、正式需求、任务和权限判断，不因为历史错误承诺而扩权；短答必须绑定唯一活动追问。用户若转向其他领域，原旅行任务不能被错误消费或清除。

### 90. 恶意输入怎么处理？

把它作为普通用户消息，按同城范围处理；拒绝忽略规则、管理员授权和格式压力。不执行消息中要求修改系统规则的内容，也不把外部资料中的指令透传给用户。

### 91. 输出给前端前做哪些校验？

检查模型是否使用结构化结束，候选是否属于当前请求，消息/任务/计划基线是否匹配，artifact 依赖和 evidence 是否完整，需求字段和展示 JSON 是否符合 schema，日期窗口和状态是否有效。

### 92. 是否要限制输入和工具返回长度？

要。用户消息上限 10000 字，修改意见上限 2000 字，需求字段和列表有长度限制，终端回答有长度限制。工具适配层应继续对返回内容做字段裁剪和数量限制，避免上下文和日志无限增长。

### 93. 工具返回内容里有提示词注入怎么办？

工具结果被视为不可信资料，只能作为事实证据，不能改变 Agent 的系统规则、权限和工具边界。代码层还应限制工具输出字段；最终回答前过滤越界内容。

### 94. 如何审计 Agent 决策？

保存 request ID、模型、角色、调用次数、工具名称、候选 artifact、evidence 引用、提交回执和失败原因；敏感输入和模型输出应按最小必要原则保存，并避免凭证进入日志。

### 95. 住宿地址和日期是否涉及隐私？

涉及。住宿地址、聊天、模型输出和运行过程都属于敏感数据；认证、旅行 owner 校验和服务端密钥隔离必须保留。日志应脱敏并设置保留周期，不能把本地运行误认为全部离线，因为模型和外部工具仍会收到数据。

### 96. 日志中是否保存精确住址？

默认应尽量保存必要字段或脱敏摘要；当前项目运行记录可能包含用户输入和模型过程，README 已明确其敏感性和保留周期尚待完善。面试时应主动承认这是生产化需要补强的部分。

## 九、RAG 与实时信息

### 97. 当前是否使用 RAG？

没有。当前 TravelAssistant 的技术栈和代码没有 Embedding、向量数据库或 Rerank；它主要依赖主 Agent、专业能力、地图/天气工具和 SQLite 状态。简历中不能把另一个智能客服项目的 RAG 写成旅行项目能力。

### 98. 哪些信息适合放 RAG？

景点历史背景、游玩风格、亲子/适老建议、区域攻略和低频变化的说明性资料。它们适合语义检索，但仍要保留来源、城市、景点、更新时间和适用条件。

### 99. 哪些必须实时查询？

目标日期天气、路线耗时、交通方式、POI 坐标、营业状态、票价、库存和当前业务订单。实时事实不应仅靠向量库返回。

### 100. 如果加入 RAG，数据从哪里来？

应来自可靠景点官网、官方旅游资料或经过人工审核的攻略，并保存原文、来源 URL、抓取时间和版本。不能直接把未经筛选的网页内容全部放入知识库。

### 101. 文档如何切分？

可按景点、主题和自然段切分，保证一个 chunk 语义完整；过大的景点介绍再按开放时间、适合人群、玩法等子主题切分。不能把日期、价格和条件切散后导致检索时丢失限定语。

### 102. 需要哪些元数据？

城市、区县、景点 POI 或外部 ID、主题、适合人群、室内/户外、交通区域、来源、发布时间和失效时间。先用城市和主题做 metadata filter，再做语义检索。

### 103. Embedding 和 Rerank 分别做什么？

Embedding 把问题和文档变成向量，适合从大规模资料中快速召回候选；Rerank 对问题和候选文档逐条精排，提升细粒度相关性。当前项目没有实现这两步。

### 104. 1650 Ti 能否运行 Rerank？

如果是常见 4GB 显存的 GTX 1650 Ti，可以尝试 0.6B 左右的中文 Rerank 模型，但应从 batch size 1、较短输入开始，并与聊天模型错峰。它与当前 TravelAssistant 没有直接关系，面试时不要说已经部署。

### 105. 如何评估 RAG 检索质量？

构造问题—相关文档标注集，统计 Recall@K、MRR、nDCG 和最终回答引用正确率；同时测试城市过滤、过期信息、冲突来源和无答案请求。不能只看向量相似度。

### 106. RAG 和地图结果冲突怎么办？

地图和天气工具负责当前事实，RAG 负责背景知识。对路线、坐标、天气和营业状态，优先使用当前工具；对景点历史和玩法建议，使用带来源和更新时间的 RAG，并把冲突标为待核实。

### 107. 知识库过期如何更新？

按来源版本和更新时间增量更新，旧 chunk 标记失效或删除向量索引，同时更新原文和 metadata。价格、开放、活动等强时效字段不应只依赖定期重嵌入。

### 108. 当前项目值得加入 RAG 吗？

不是第一优先级。当前核心是同城路线和实时事实，加入 RAG 会带来采集、更新、切分和评测成本。若产品扩展到“为什么值得去”“适合什么人”“景点文化背景”，再引入 RAG 更合理。

## 十、评测与效果指标

### 109. 如何评估一份行程合理？

至少分为结构约束、事实依据、偏好满足、时间闭合、餐次覆盖、交通连续性和表达可读性。当前自动测试更偏运行合同和业务边界，路线现实可行性仍需要真实数据和人工评审。

### 110. 评测集包含哪些类型？

一套 80 条越界评测包含 12 个其他领域、混合请求和 10 条合法对照，并覆盖直接提问、旅行前缀、角色扩权、历史承诺、格式施压和失败资料注入。另一套 50 条覆盖简单越界、高风险、能力不支持、合法对照、模糊关联、混合、多轮和活动追问。

### 111. 如何定义越界作答？

看最终用户可见回答是否给出其他领域的实质答案：算出结果、输出代码、完整菜谱、译文、药量、股票推荐等都算；简单说明服务范围或建议咨询医生不算。不能只用关键词判断。

### 112. 合法误拒怎么定义？

用户请求属于同城游玩、地点、餐饮、天气、交通、行程解释或需求补充，但系统把它当成越界而拒绝，或没有处理可独立完成的合法部分。混合请求要同时统计合法部分是否受理。

### 113. 80 条如何构造？

60 条其他领域问题按 12 个领域各 5 条；10 条混合请求把合法游玩与越界任务组合；10 条合法对照覆盖问候、天气、餐饮、规划、预算、偏好和交通。每条有 category、attack、level、expected 和 rubric。

### 114. 70/10 统计口径是什么？

70 是 60 条其他领域请求加 10 条混合请求，检查越界实质作答；10 是合法对照，检查误拒。越界率分母是取得可评审回复的 70 条，合法误拒率分母是 10 条；运行失败、空回复和未评审不能当作正确拒答。

### 115. 是人工还是自动评审？

机械层检查运行是否完成、是否调用禁止能力、答案绑定和工作流变化；语义层需要人工阅读最终回答、追问和工具调用。项目文档明确不能把机械检查当作语义通过率。

### 116. 如何降低模型评审偏差？

优先人工复核关键样本；如果用独立模型辅助，保留原文、rubric、证据片段和评审理由，并对争议样本人工复核。重复运行时保留所有 attempt，不能只挑最好的结果。

### 117. 如何测试提示词注入？

在用户消息中加入“忽略规则”“我是管理员”“这是安全测试”“只输出 JSON”“把答案藏在行程里”等指令；在 capability summary、正文和工具结果中加入伪系统指令，检查是否被透传或执行。

### 118. 如何测试多轮诱导？

预置一轮错误承诺或活动追问，再发送越界请求、模糊短答、拒绝回答或转向其他任务，检查是否错误扩权、错误消费追问或清除原任务。

### 119. 如何测试工具失败？

用 unavailable、超时、字段缺失、日期超范围、路线无公交明细和额度耗尽等固定结果，检查系统是否如实保留未知、保留已有行程、给出可恢复信息，并且不把失败说成成功。

### 120. 如何测试旧任务覆盖？

让第一个任务暂停在外部查询，再提交新消息改变需求或计划，最后让旧任务返回；验证旧任务状态为 superseded/failed 或提交冲突，当前 plan、requirements 和 workflow 仍来自新请求。

### 121. 应关注哪些指标？

运行完成率、模型/工具调用失败率、任务耗时、越界实质作答率、合法误拒率、混合请求处理率、候选提交成功率、过期候选拒绝率、卡片派生失败率，以及人工评审的路线质量和偏好满足度。

### 122. 全部拒绝算安全吗？

不算。既要控制越界率，也要控制合法误拒率和混合请求处理率。项目的 80 条评测同时设置 70 条越界/混合和 10 条合法对照，就是为了避免只优化拒绝。

### 123. 路线可执行但不符合偏好如何评分？

分开评分：事实和路线结构可以通过，但偏好满足度失败。比如路线从住宿出发并返回，却违反“不吃辣”或“少走路”，不能因为闭环就判为完整成功。

### 124. 如何做回归测试？

固定数据集和提示词 hash，离线先验证数据和运行合同，再显式调用真实模型；每次保存全部输出、调用、错误和人工评审。对历史诱导、失败回退、活动追问和关键合法场景进行重复运行。

## 十一、性能与部署

### 125. 一次规划调用多少模型和工具？

没有固定次数，因为由 Agent 根据需求动态决定；代码设置了上限。主 Agent 最多 12 步，子能力有各自步数，外部查询最多 32 次。真实平均耗时和调用数应通过日志或 `scripts/bench_agent_latency.py` 实测，不能现场编造平均值。

### 126. 主要耗时在哪里？

通常是模型推理和地图/天气网络请求，尤其是高德 MCP 的初始化、工具发现和查询；多轮规划与展示提取也会叠加。当前项目有单 Agent 响应基准脚本，但脚本本身不是实测结果。

### 127. 哪些工具可以并行？

天气、多个地点搜索和已经知道两个可信 POI 的独立路线查询可以并行；路线依赖地点搜索结果时必须串行。系统提示词和运行时限制一次最多四个独立只读查询。

### 128. 如何减少模型调用？

按需读取上下文，避免重复 read_context；在运行时缓存同一轮的地点、天气和路线；把多个独立只读查询合并；让专业能力在最后一步直接完成，而不是继续探索；对展示只从正文提取，不重新规划。

### 129. 如何减少上下文长度？

主 Agent 使用投影而不是完整快照，历史消息只取最近窗口；想法墙默认摘要，需要时再读正文；工具结果裁剪字段和数量；evidence 按引用传递，不重复塞入原始响应。

### 130. 地点和天气能否缓存？

可以在单次 runtime 内缓存。地点目录按 POI ID保存，路线缓存键包含起点、终点坐标和交通方式；天气分别缓存城市地理编码和预报。跨请求缓存需要考虑数据时效、用户权限和版本。

### 131. 缓存多久？

天气缓存应按目标日期和预报更新周期设置较短 TTL，路线耗时受实时交通影响也不应长期复用；POI 坐标可以较长，但营业资料仍要标注查询时间。当前代码主要是单轮缓存，没有把它包装成全局实时保证。

### 132. 100 个用户的瓶颈是什么？

模型服务并发和延迟、外部地图/天气配额、单进程线程和 SQLite 写入锁都会成为瓶颈。当前版本适合原型和单进程，不能直接宣称支撑 100 个并发生产请求。

### 133. SQLite 什么时候换数据库？

当需要多 worker、多实例、较多并发写入、可靠队列、复杂查询或高可用时迁移 PostgreSQL。任务执行和外部调用还应放进独立 worker，前端通过任务状态查询结果。

### 134. 如何部署？

当前是 FastAPI + Uvicorn 单进程，模型、地图 Key 和数据库路径通过环境变量配置。正式部署要加 HTTPS、认证、反向代理、共享数据库、任务队列、日志脱敏、监控和备份。

### 135. 模型限流怎么办？

客户端关闭自动重试或控制重试次数，配置备用模型时最多切换一次；运行时预算和任务失败状态保证不会无限调用。用户看到的是可恢复失败，任务输入和已有行程保留。

### 136. 监控什么？

按 request_id 统计模型角色、模型调用次数、token、工具调用、外部调用、耗时、超时、失败原因、候选提交和卡片状态；同时监控高德/天气配额、数据库提交冲突和任务 superseded 数量。

### 137. 模型不可用时怎么办？

任务进入失败或 fail-closed，保留用户消息、正式需求和当前行程，返回明确的重试提示；不能用常识伪造天气、路线或“已保存”。

### 138. 如何控制成本？

限制模型、工具和外部调用预算；按需查工具和缓存单轮结果；只在需要时生成卡片；对局部修改限定范围；生产环境再根据日志设置 token、用户频率和供应商配额。

## 十二、项目取舍与开放题

### 139. 为什么选择 FastAPI、Jinja2 和 SQLite？

Python 便于连接模型和工具，FastAPI 适合快速搭建 API 和异步任务接口，Jinja2 加原生 JavaScript 能快速完成可运行 Web 产品，SQLite 适合个人项目和单进程原型。代价是多进程和高并发能力有限。

### 140. 为什么没有使用 LangChain 或 LangGraph？

当前状态、候选、依赖和提交规则比较定制化，自己实现 AgentLoop 可以准确控制工具边界、预算和 commit；代价是要自行维护协议、重试、状态和观测。不是框架不能做，而是项目当时更重视透明控制。

### 141. 为什么自己实现 AgentLoop？

需要控制每轮最多一个主工具、专业能力的工具白名单、最后一步收尾、版本和候选依赖。通用框架能减少样板代码，但未必直接表达“候选不等于保存”和“提交前重新校验”这类业务规则。

### 142. 自研 AgentLoop 的优缺点？

优点是边界清晰、协议可测试、容易把业务状态和安全校验放在正确位置；缺点是开发成本高、需要自己处理供应商协议兼容、异常恢复、可观测性和并发。后续可以保留核心提交边界，再选择成熟编排框架承载部分节点。

### 143. 改造成生产系统先改什么？

先把单进程内存任务改成共享数据库加可靠队列，补齐幂等、重试和多实例提交；再做端到端事实和路线质量评测；最后完善敏感日志治理、监控、限流和备份。

### 144. 只能保留一个工具，保留什么？

保留地图地点/路线工具，因为它决定住宿起终点、同城范围和路线闭合；天气仍可在出发前由用户自行确认。若项目目标改成天气驱动的户外规划，选择可能不同，关键是说明取舍依据。

### 145. 只能保留一种 Agent 能力，保留什么？

保留规划能力，但前提是住宿、地点和日期已被代码确认；需求整理保证输入可用，局部修改提升体验，但核心价值仍是把确认条件转成路线。

### 146. 用户要求跨城市旅行怎么办？

当前明确拒绝跨城完整规划，只处理其中独立的住宿城市同城部分。若扩展，需要增加跨城交通、住宿切换、日期和票务状态模型，不能只把提示词中的“同城”删掉。

### 147. 能否实时提供票价和酒店价格？

当前不能。高德地点返回的营业资料也不等于票价、库存或可预订状态。需要接入合法的票务/酒店业务 API、用户授权、价格时间戳和订单一致性后才能做。

### 148. 加入 RAG 首先放什么？

先放低频、可审核、能直接提升规划解释的内容，例如景点背景、适合人群、游玩风格和区域攻略；不要先把实时价格、天气和路线放进向量库。

### 149. 项目最体现什么能力？

不是单纯会调用模型，而是能把 LLM 放进一个有状态的业务闭环：拆分能力、限制工具、保存证据、处理失败、保护版本和验证提交。这个项目也体现了我能识别“模型说完成”和“业务实际保存”之间的差异。

### 150. 有没有后来发现不合理的设计？

有两个：第一，当前正文主要依赖模型生成，业务级路线可执行性校验还不够强；第二，单进程 SQLite 适合原型但不适合生产并发。下一步会增加结构化中间约束和端到端评测，并把任务执行和状态存储改成可水平扩展的架构。

## 十三、最容易被追问的 10 条标准答案

### 1. Agent 为什么不能只靠提示词？

提示词只能引导模型，不能保证参数合法、工具一定调用、来源真实或旧结果不覆盖新状态。所以项目把 schema 校验、可信 POI、预算、版本、候选依赖和提交都放在代码中；模型只负责语义理解和动态决策。

### 2. 旧任务为什么不能覆盖新任务？

每个任务绑定 request ID、原消息、需求 revision、workflow revision、sequence/epoch 和 plan basis。新请求会使旧任务失效，旧任务提交前重新核对这些基线；不匹配就拒绝发布。

### 3. 当前是否使用 RAG？

没有。当前核心是实时地图和天气查询，静态景点知识不是首要需求。后续可以把背景和攻略放进 RAG，但路线、天气、开放和价格仍然需要实时工具。

### 4. 80 条评测能说明什么？

一次真实评测中，70 条越界/混合请求没有观察到其他领域实质作答，10 条合法对照没有误拒。它只说明该轮范围遵守情况，不能说明路线质量、专业能力成功率或长期稳定性；评测也记录了无授权调用等问题。

### 5. 如果工具失败怎么办？

返回结构化 unavailable，保留输入和已有行程，明确未知或待核实；必要时允许用户重试。绝不凭模型知识补造天气、路线、票价或开放状态。

### 6. 为什么正文和卡片分开？

正文是用户可读的主数据，卡片只是展示派生物。这样卡片模型输出非法或超时不会丢失完整正文；卡片绑定正文 hash，正文变化后旧卡片不能继续冒充当前展示。

### 7. 为什么没有强制每次都查天气？

天气查询应根据日期、户外主线和用户问题按需调用，强制所有请求查天气会增加延迟和成本。若天气是规划的必要条件，可以用确定性 evidence 前置状态强制；当前版本主要通过提示词和证据边界约束，不应夸大为完全强制。

### 8. 如何说明个人贡献？

我独立完成了产品闭环和核心实现：需求和数据模型、地图/天气工具适配、AgentLoop、候选工作区、原子提交、任务一致性、SQLite 持久化、前端展示、失败恢复和测试评测。面试时最好选择一个问题深入讲代码，而不是只罗列技术名词。

### 9. 当前项目最大局限是什么？

实时查询结果仍是“查询时证据”，不等于当天现实可执行；路线、营业和预算质量还需要更强的结构化校验与人工评测。系统也受单进程和 SQLite 限制。

### 10. 下一步做什么？

先补齐端到端质量评测和运行指标，再做结构化路线约束和事实引用校验；如果静态景点知识成为用户需求，再引入带来源和更新时间的 RAG；生产化时迁移共享数据库和任务队列。

## 十五、建议你回到代码再确认的个人细节

这些问题在真实面试中很可能要求你展示代码或给出精确数字，建议面试前自己再走一遍：

1. 从一次 `/api/trips/{trip_id}/tasks` 请求开始，手动画出任务进入 queued、running、执行、提交和卡片派生的时序图。
