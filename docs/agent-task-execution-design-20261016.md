# 从意图分流到任务执行：TravelAssistant 主 Agent 重构设计

- 日期：2026-10-16
- 状态：**设计提案，尚未实施**。用户已认可“取消单标签固定分流，main 通过统一工具循环按需调用专业能力”的方向；本文给出建议接口与落地步骤，具体协议仍需实施评审。
- 本次范围：只新增本文档，不修改业务代码、提示词、数据库或页面。
- 适用范围：现有 `city` 同城游玩与 `travel` 完整旅行模式；保留单进程部署、当前行程单份保存、正文先交付和后台展示。
- 相关背景：[当前架构](agent-architecture-current.md)、[角色实现](agent-role-implementation.md)、[历史讨论](agent-discussion.md)。其中现有实现与本文目标架构必须分开理解。

## 1. 决策摘要

**移除聊天入口的 `intent → 固定业务分支`，让 main 成为一个有界、可调用工具的任务执行 Agent。**

main 接收完整用户请求和可信业务状态，根据工具结果逐步选择下一步。需求整理、资料查询、规划、修改成为可调用能力，不再是彼此互斥的会话入口。程序管理候选变更、任务状态、执行预算、版本检查与最终提交。

关键原则：

1. **不要求一条消息属于一个意图，也不要求提前列出完整执行计划。**
2. **不维护“查询＋取消”“解释＋修改”等组合路由表。** 任务的顺序和条件由 main 结合结果判断，程序只约束基础能力的权限及输入输出。
3. **专业能力完成，不等于整条用户请求完成。** 结果先返回 main，由 main 决定继续、澄清或结束。
4. **模型可以提出操作，不能自行证明用户授权或宣称已经落库。** 程序绑定真实请求、验证可检查的条件，并执行唯一提交。
5. **跨轮保留的是未完成任务，不是某个 Agent 的分支状态。**
6. **不重做已有保护与页面。** 复用任务失效、共享预算、快照校验、需求验证、精确文字编辑、后台展示机制。

通用性来自“有限基础能力的动态组合”，而不是给每种自然语言组合增加一个新 action。

## 2. 为什么不继续扩展意图分类

### 2.1 现有实现的结构限制

当前 `app/agent_roles.py::INTENT_SCHEMA` 要求 main 输出一个 `intent/action/scope/user_quote/question` 对象；`app/agent_runtime.py::classify/execute_route` 随后选择固定角色。

这种结构把两个不同问题合并了：

- 用户这次到底希望完成什么？
- 程序下一步应该调用哪个能力？

例如“查明天天气，下雨就把第二天改成室内，其他安排别动”同时包含资料获取、条件判断、局部写入和范围约束。单标签必然丢失关系；多标签 `[query, modify]` 仍然丢失“下雨才改”的条件。

现有代码还把等待目标与角色绑定：`requirements` 结束就清空等待，`research` 结束就沿用等待。因此，业务诉求是否完成、旧目标是否有效，被间接交给角色名称决定。

### 2.2 本方案不做什么

- 不新增更多顶层意图，不枚举所有意图组合。
- 不新增一个独立分类器或 LLM 评审节点。
- 不让模型生成 Python、SQL、任意工作流代码或自由执行 DAG。
- 不要求所有消息先执行需求 Agent；闲聊可以直接回答，已有需求完整时可以直接规划。
- 不把所有专业能力合成一个无限权限、无限上下文的 Agent。
- 不承诺消除全部语义误解。模型依然可能误解假设、指代或范围，需要澄清和真实模型评测。

## 3. 目标架构与职责

### 3.1 一轮聊天的执行过程

1. HTTP/任务入口完成用户归属校验、幂等校验和旧执行失效处理。
2. Store 在锁内建立当前请求的业务快照，附入仍有效的未完成任务与当前追问。
3. main 基于快照和最新完整消息，直接回复，或调用一个基础能力。
4. Runtime 校验调用，执行能力，将结构化结果返回 main。
5. main 根据实际结果继续调用能力、处理独立事项、提出澄清，或结束本轮。
6. Runtime 将合法候选汇总为提交提案；Store 再检查请求有效性与业务版本。
7. Store 完成提交并形成最终对外回复。行程正文发生变化时，继续触发原有后台展示。

第 3～5 步构成有界工具循环，**中间没有必须先得到分类标签的关卡**。

### 3.2 三层职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| main 任务执行 Agent | 理解目标、条件、指代和约束；选择能力；管理未完成事项；组织最终答复 | 直接写数据库、伪造工具结果、自选其他用户数据、绕过版本检查 |
| 专业能力 | 完成范围明确的一项工作，返回结果、证据、候选或缺项 | 结束父任务、发布用户回复、决定全局等待状态、递归委派其他 Agent |
| Runtime / Store | 工具权限、参数与引用校验、候选管理、取消、预算、任务状态、提交和持久化 | 声称用字段校验就能证明自然语言被正确理解 |

专业能力可以是普通函数，也可以是现有 AgentLoop 的封装。main 选择“用什么能力”，不选择其内部模型、数据库连接或权限。

### 3.3 循环与委派限制

第一版采用串行执行，委派深度固定为一层：main → 专业能力。专业能力内部可以使用已有查询工具，但不得再次调用 main 或创建后台写任务。

所有层共享同一个 `TurnBudget`、父任务取消回调、证据目录和本轮缓存。调用专业能力不是新的一轮，不能重置模型调用数、外部查询额度或 deadline。

Runtime 为每次专业调用分配不超过剩余总量的子额度，并为 main 的一次终止决策与程序提交保留额度；时间保留量根据实测终止调用延迟配置。无法容纳下一次能力调用及收尾时，不再启动新调用。同参数、同依据且没有新信息的重复调用受次数限制。预留只是正常收尾措施，不能保证网络总会及时返回；超时还须有不依赖模型的失败终止路径（见第9节）。

## 4. main 可调用的基础能力

以下名称是建议接口，不是现有函数已经具备的能力。

| 能力 | 输入重点 | 返回重点 | 权限 |
| --- | --- | --- | --- |
| `read_context` | 区域、分页、服务器给出的引用 | 当前需求、行程、相关消息、任务或证据 | 只读；默认只允许当前 trip |
| `manage_task` | 建立任务、补充已完成事项、切换焦点、挂起、恢复、取消 | 程序生成的任务 ID、合法状态转换结果 | 只修改本轮任务候选，不直接落库 |
| `prepare_requirements` | 本轮原始请求引用、当前追问答案绑定、目标任务引用 | 校验后的需求候选，或无变更、字段澄清 | 只提出正式需求变更，不查询、不规划 |
| `research` | 具体问题、所需方案/证据引用、可用上下文 | 只读答案、来源、时间范围、失败或缺项 | 可查资料，不写正式需求或行程 |
| `draft_itinerary` | 目标任务、有效需求候选、生成目标与约束 | 完整行程候选及证据 | 只生成候选，可按需使用旅行查询工具 |
| `revise_itinerary` | 当前行程引用、修改范围与约束、有效需求候选 | 完整修改候选及证据 | 只修改候选，保留精确文字编辑保护 |
| `confirm_itinerary` | 用户已经看到的当前方案引用 | 绑定当前方案的确认候选 | 不修改正文；不确认用户尚未看到的新候选 |
| `ask_user` | 所属任务、一个具体问题、答案将用于何处、当前事项状态 | 本轮终止提案与结构化追问 | 不自行宣布未提交变更已保存 |
| `finish_turn` | 回答、完成/未完成事项、采用的候选引用 | 本轮终止提案 | 不是数据库写工具；仍需统一提交 |

设计补充：

- 不提供 `run_agent(role=任意值)`、任意 SQL、任意需求 patch 写入或模型自报坐标工具。
- main 不需要强行调用 `manage_task` 才能回答“谢谢”。只有需要跟踪多步、写入授权、条件或跨轮澄清的工作才建立任务。
- 方案解释由 main 读取正文后回答；需要外部核实时调用 research。取消独立的 `revision/explain` 路由，不因此强制增加一次专业模型调用。
- 需求字段只能由 `prepare_requirements` 提出并通过程序校验。规划/修改角色消费有效需求，不再拥有另一套可竞争的正式需求写入入口。
- 规划/修改仍可调用现有地图与天气工具，避免每一次资料查询都必须回到 main 再委派 research。
- 专业能力发现尚未处理的需求变更时，返回 `needs_requirements` 及依据，不自行保存，也不能按旧需求悄悄继续生成。

### 4.1 不是固定流程表

程序只规定基础能力的前置条件，例如“修改必须有当前方案”“写入必须有有效请求与依据”。它不规定“先查询后修改”或“需求后只能生成”。

main 可以先查资料再整理需求，也可以先记录明确偏好再查询；是否继续取决于用户目标及真实结果。新增基础能力时增加工具合同与验证器，而不是修改一张组合路由矩阵。

## 5. 统一的专业能力结果合同

现有 `run_role()` 常直接构造最终 `AgentReply`。目标架构需要把“专业工作完成”与“用户这一轮完成”拆开。

建议引入 `CapabilityResult`，所有专业能力使用同一种结果外壳：

```json
{
  "status": "ok",
  "summary": "已生成第二天室内替代候选，尚未保存",
  "artifact_refs": ["artifact-server-id"],
  "evidence_refs": ["evidence-server-id"],
  "completed_items": ["item-server-id"],
  "unresolved_items": [],
  "input_request": null,
  "error": null
}
```

`status` 建议限定为：`ok / needs_input / needs_requirements / conflict / unavailable / failed`。

- 所有 artifact/evidence ID 由 Runtime 创建；模型只能引用当前任务可见、仍有效的 ID。
- `ok` 只表示能力完成，**不表示数据库已经保存，也不表示全部用户诉求完成**。
- `needs_input` 携带结构化缺项或歧义，不能靠识别“需要补充：”前缀决定父任务状态。
- 专业能力返回 `needs_input` 时，控制权回到 main，不立刻结束父循环。main 可以先处理其他独立事项，再组织一个必要问题。
- 查询失败区分“没有数据”“来源不支持”“请求失败”，不能全部变成“条件不满足”。
- 行程正文保存在 artifact 中。给 main 返回候选引用、摘要与变更范围，避免全文在多个模型间重复传递；main 可按需读取。
- 专业能力不可信的自然语言说明不能覆盖程序给出的状态、版本和权限。

### 5.1 候选与本轮工作区

Runtime 建立 `TurnWorkspace`：保存原始快照、本轮有效需求候选、行程候选、证据和任务状态候选。

每份写入候选至少绑定：

- 来源能力与父执行任务；
- 原始用户消息引用和适用的授权任务；
- 基础需求 revision、当前行程身份与正文依据；
- 所依赖的其他候选/证据；
- 独立变更还是依赖某个条件的变更。

后续能力消费显式候选引用。需求候选改变后，基于旧候选生成的行程不能继续采用；Runtime 应标记失效并要求重新生成，而不是靠 main 记得版本变化。

本轮中间状态不等于持久业务状态。能力不得直接调用 Store 提交。

**引用生命周期必须明确：** `TurnWorkspace` 中未提交的 artifact 默认只在本轮有效，不能直接写入持久任务当作下轮可用引用。需要跨轮保留的只读证据或供用户选择的草稿，要随本轮提交保存有界、可校验的内容及依据；未保存的中间候选在下轮重新计算。任务依据中的当前行程引用指向已提交正文，不把临时草稿当成当前方案，也不借此恢复历史行程。

## 6. main 的输入、执行协议与结束规则

### 6.1 初始上下文

保留最近聊天窗口，但不能把它作为唯一的任务记忆。初始输入应包含：

- 最新完整用户消息及服务器生成的 message/request/trip 引用；
- 当前已保存需求、模式、真实缺项和住宿确认状态；
- 当前方案的 ID、标题、正文摘要/日期范围及可读取引用；
- 未完成任务摘要、当前焦点、当前追问与原始授权消息引用；
- 当前任务可使用的权限与剩余共享预算。

当前行程全文、较早消息和证据按需读取。未完成目标与当前追问不能因超过最近 8 条消息而被截断。摘要不能代替原始授权或精确编辑正文。

### 6.2 本轮事项记录

复杂请求建立一组轻量事项，例如“查询天气”“条件成立时替换第二天”“保留其他安排”。事项描述保留自然语言语义与必要依赖，不要求套进顶层意图枚举。

记录的作用是防止漏做，而不是要求模型先生成一份不可变计划。main 可以随结果修正未完成事项，但：

- 已取消事项不能无依据复活；
- 删除或放弃事项必须说明原因，不能靠删除清单伪装完成；
- 程序不能仅凭模型写了 `completed` 就认定发生了写入，必须存在对应有效 artifact/提交结果；
- 只读回答是否充分仍需语义评测，不能宣称清单校验就能识别所有漏答。

### 6.3 执行伪代码

以下是目标流程伪代码，不是现有可直接运行的 API：

```python
snapshot = store.capture_current_request()
workspace = TurnWorkspace(snapshot)
budget = shared_turn_budget(snapshot.cancelled)

while within_main_step_limit():
    budget.check_current()
    decision = main.decide(workspace.context(), tools=main_tools)

    if decision.is_terminal:
        proposal = runtime.validate_terminal(decision, workspace)
        break

    result = runtime.execute_capability(decision, workspace, budget)
    budget.check_current()
    workspace.observe(result)
else:
    proposal = runtime.fail_close_with_verified_independent_effects()

receipt, reply = store.commit_and_record_reply(proposal, snapshot)
publish_committed_reply(reply)
```

实施要求：

- 第一版 main 每次只执行一个有依赖关系的能力；不接受同一个模型响应内把“查询结果尚未知”和“条件性修改”并行执行。
- 无工具、无状态修改的简单回复可以由适配器直接视为 `finish_turn`，不强制多一次请求。
- 对有写入或未完成事项的请求，必须通过结构化终止合同；普通 prose 不能自动提交全部候选。
- 非法调用返回可恢复观察值，允许有限次数纠正；重复相同失败且无新信息时终止，不能无限循环。

## 7. 跨轮任务上下文：替代 awaiting_generation

### 7.1 必须区分两种“任务”

- **执行任务（execution task）**：现有 `tasks.py` 队列中一次请求的工作单元，新消息可将其标记为 `superseded`。
- **会话目标（conversation task）**：用户尚未完成的工作，可以跨越多轮消息，在等待用户时存在。

新消息使旧执行失效，不等于取消旧会话目标。反过来，会话目标仍存在，也不能使旧执行获得继续提交的资格。

代码中建议分别使用 `execution_task_id` 和 `conversation_task_id`，避免混用现有 `task_id`。

### 7.2 最小持久结构

先复用 `Trip.workflow_state` 存储有版本的结构，不新增独立服务。建议结构示意：

```json
{
  "schema_version": 2,
  "revision": 3,
  "focus_task_id": "task-server-id",
  "active_question": {
    "id": "question-server-id",
    "task_id": "task-server-id",
    "assistant_message_id": "message-server-id",
    "text": "酒店每晚希望控制在什么价位？",
    "answer_target": {
      "namespace": "research.hotel",
      "field": "nightly_budget"
    }
  },
  "tasks": [
    {
      "id": "task-server-id",
      "goal": "了解住宿附近的酒店候选",
      "status": "waiting_user",
      "source_message_ids": ["message-user-id"],
      "authorization_refs": [],
      "basis": {"requirements_revision": 7, "plan_ref": null},
      "progress": [],
      "unresolved_items": ["补充酒店每晚价位"],
      "evidence": []
    }
  ]
}
```

这是结构示意，不要求照抄字段命名。ID、revision、basis 和引用归属由程序管理，模型不能自由填一个 dict 替换整个状态。

- 任务状态使用通用生命周期：`active / waiting_user / suspended / completed / cancelled / failed`，不设置 `waiting_generation / waiting_weather` 等业务专用状态。
- 同时允许少量未完成任务，但一个时刻只有一个对外活动追问。旧问题可以随旧任务挂起，不同时消费同一句短回答。
- `answer_target` 表达回答用途；不是把查询参数自动写成正式需求。
- 模型提出状态转换，程序校验任务归属、状态合法性、引用与当前执行有效性。
- 已完成/取消记录可限量保留；压缩任务上下文时不能删除仍未完成任务的来源和约束。达到容量上限时明确提示整理或关闭旧任务，不能静默丢弃。

### 7.3 短回答与话题切换

main 先理解最新消息与当前活动追问的关系，再考虑其他未完成任务。活动追问提供优先依据，但不是无条件绑定。

例如：

1. 旧任务正在等整趟旅行预算。
2. 用户插问酒店，查询任务追问“每晚多少元”。
3. 用户回答“500”。

应绑定酒店价位，不更新旅行预算、不恢复旧生成。若用户说“不是酒店，我说旅行总预算500”，则根据明确纠正重新绑定。

消息可能是补充、纠正、插问、新目标或取消。这里由 main 语义理解，不在代码中堆关键词；任何绑定不明确、会影响写入的情况都应澄清。

### 7.4 恢复、取消、重启和清空聊天

- 只有用户新消息或明确页面操作触发执行，不因字段恰好填齐或旧目标仍存在而后台自动生成。
- 无关偏好更新不会隐式取消旧目标；插问也不会隐式恢复旧目标。
- 任务恢复前重新检查需求和行程依据。原方案已经改变时，旧局部修改不能自动应用到新方案。
- 重启后沿用现有 `recover_tasks` 使运行中的执行失败化；会话目标可以保留，但不得自动重启写入。
- 清空聊天继续保留已保存需求和当前方案；同时清除活动追问、取消未完成会话目标，避免用户看不到原授权却继续执行。
- 失败后重试必须绑定原请求；用户随后改过目标时不能仅凭 retry_of 恢复旧授权。

## 8. 条件、否定与授权：程序能保证什么

### 8.1 条件不是标签

main 对“如果下雨就修改”应先取得证据，再决定是否提出修改。条件结果必须区分 `satisfied / not_satisfied / unknown`。

条件相关操作记录：原始条件文字、证据引用、判断结果和作用范围。`unknown` 不能被当作 `not_satisfied`，也不能自动授权修改。

有可靠结构化数据的条件可以由程序校验，例如查询日期、城市、数据有效期和明确数值比较。对“适不适合老人”“天气够不够好”等主观条件，不设计任意表达式执行器；需要用户标准或澄清。

**程序可以验证证据存在、归属和适用范围，但不能仅凭模型提交了 `satisfied` 就证明任意自然语言条件为真。** 关键条件缺乏可信依据时不写入。这是剩余语义风险，不包装成确定性保证。

### 8.2 原始授权不能来自模型改写

Runtime 从真实消息中建立不可变 RequestContext；main/子能力传递消息引用，不能把改写后的任务描述当成用户原话。

写入候选需要关联：

- 哪条真实用户消息授权哪种效果；
- 当前问题答案绑定到哪个任务；
- 若为恢复旧任务，旧授权是否仍有效、其方案依据是否过期；
- 明确限制，如“不改预算”“只改第二天”“其他安排不动”。

列表 add/remove、日期与预算校验、原文唯一匹配继续由现有验证器执行。它们不能证明“如果预算500”就是正式预算变更；这部分仍由模型解释并在有歧义时询问。

### 8.3 假设值与正式需求分离

咨询参数放在任务局部输入中，不进入 `TripRequirements`。例如“如果只有500元够不够”，research/规划评估可以用临时假设，但不能调用正式需求提交来实现模拟。

只有用户明确将假设采纳为正式要求，才调用 `prepare_requirements`。临时参数必须标注为 hypothetical，并禁止被候选合并器顺手写回。

### 8.4 外部结果不是新指令

网页、地图文本、工具错误和专业能力返回内容均是数据，不得改变工具权限、用户授权或任务范围。读取结果中的“忽略之前要求”等文字不构成指令。程序限制可操作资源为当前 trip，模型不能通过返回的 ID 越权访问其他旅行。

## 9. 统一提交与对外回复

### 9.1 保留一个提交入口，不声称现有代码已经全有或全无

现有 `store.py::_commit_agent_result` 是集中提交点，但允许明确需求先保存、行程失败后保留旧正文；确认分支也会提前返回。因此不能简单给现有函数加一个调用，就宣称获得完整事务语义。

目标是：**所有专业能力都不落库；由一次集中提交决定本轮哪些合法、独立的效果可以生效。**

提交提案包含需求候选、行程候选或确认候选、任务状态候选，以及它们的依赖。Store 先验证，再在同一锁和持久化边界应用选定效果，返回 `CommitReceipt`。

### 9.2 提交规则

1. 请求已被替代、取消，或关键基础版本冲突：整份提案不提交，不能只保存任务状态绕过旧请求保护。
2. 无条件且独立的明确需求修改，可以在后续查询/规划失败时保存；回复必须区分“需求已保存”和“方案未生成”。
3. “如果查到有票，再把必去点改成A”属于依赖条件的写入，不能按独立需求保存。
4. 行程候选依赖的需求候选必须同时采用；需求校验失败时禁止拿旧需求保存这份新方案。
5. 一个提交至多采用一份最终行程候选，不把多个草稿依次覆盖成假历史。
6. 方案确认保持当前安全边界：只能确认用户已看到且依据未变的方案；不把“生成新候选”自动等同于“用户确认”。
7. 会话任务的完成状态以实际提交结果为准；行程保存失败时，不得仍把“修改行程”标记完成。
8. 添加工作流 revision 的比较与更新。即使需求没变、正文没变，也不能允许旧执行覆盖新的追问焦点或任务状态。
9. 内存与持久化提交失败时，要恢复一致状态并返回未成功回执；不在多个能力中分别调用 `_persist()`。
10. 是否提交某项独立效果，与本轮是否仍需用户回答是两个维度。不能继续用全局 `AgentReply.needs_input` 阻止所有行程保存。例如一个明确修改已完成、另一个独立查询还缺信息时，只提交前者，后者进入等待；若修改本身依赖该回答，则不得提交。

依赖规则面向所有候选，不为“取消＋天气”等自然语言组合新增提交分支。`AgentReply` 只作为页面兼容外壳，提交资格由候选依赖与回执决定，而不是由全局 failed/needs_input 推导。

### 9.3 用户回复只发布一次

main 的终止结果先是回复提案，区分只读答案、待问问题和效果引用，不让自由文本承担写入成功声明。程序根据 `CommitReceipt` 生成“需求已保存/行程未修改/任务已取消”等状态段，再组合最终消息：

- 不通过搜索替换“已保存”等关键词修正自由文本；这种办法不能覆盖所有成功措辞。
- 模型只读答案即使仍可能违规夹带状态宣称，也不能成为程序判定成功的依据；约束输出合同并在评测中检查，不宣称可完全验证自然语言。
- 查询失败、条件未知、未完成事项必须可见；全局版本冲突时，采用程序失败回复，不发布可能失真的效果描述。
- 专业能力交付的行程正文直接采用，不由 main 再重写一遍，以免丢失证据、限定词和精确编辑结果。
- 保持当前页面输出兼容，通过适配器映射卡片、正文、needs_input 等字段，不沿用这些字段决定提交资格。

消息 ID 在提交前由程序预分配；消息正文、active_question、任务 revision 及选定业务变更进入同一持久化边界。提交成功后才通知页面读取。不能先保存指向未来消息的追问，再另行保存消息，否则进程中断会留下用户从未看到的活动问题。所有消息组装在锁内使用已完成的提案，不在数据库事务中等待模型。

### 9.4 失败终止不依赖最后一次模型调用

为避免“取消旧目标后查询超时，又把取消丢了”，Runtime 在执行每个能力后记录已验证候选的依赖和采纳状态。无条件、独立且明确选定的效果可以进入 `ready_to_commit`；模型生成过的任意草稿不自动进入此状态。

若主循环超时、预算耗尽或模型传输失败，Runtime 可不调用模型，直接形成保守失败终止提案：仅采用已经通过校验、依赖满足且已选定的独立效果；未确认草稿、条件未知效果和悬空候选全部舍弃。仍需经过完整的当前任务/版本校验与统一提交，以回执说明“哪些已完成，哪些未完成”。若请求已被新消息替代，则不提交任何效果，包括旧任务的取消候选。

这样，普通查询失败不吞掉独立取消；同时也不会因为运行过某个能力，就把它的所有输出当作已获授权写入。

## 11. 页面入口与现有产品边界

聊天是通用任务执行入口；页面“生成”“修改站点”等明确操作可以继续走服务器绑定的能力快路径，不为已经明确的按钮额外做一次 main 判断。

但两种入口必须共享候选、预算、授权依据、版本检查和提交服务，不能维护两套写入规则。页面的 `display_target` 继续由程序从当前正文绑定的展示提取，不接受模型自由构造。

继续遵守：

- 同城住宿文字与可信地图位置分开，换住宿后须通过现有地图确认；日期、人数、预算仍为可选。
- 完整旅行的必要字段继续由原规划验证器判断。
- 只保留当前行程，不恢复已被替换的旧版本；未完成任务不成为历史方案仓库。
- 后台展示只整理已保存正文，失败不丢正文。
- 不新增预订、支付或自动外部写入能力。
- 不改变底栏、默认入口、行程信息顺序、卡片样式等用户认可布局。

## 12. 示例：同一套执行机制处理不同请求

以下用于说明组合能力，不是实现时新增的六条特殊路由。

### 12.1 简单闲聊

用户：“谢谢。”

main 直接回复；不调用专业能力，不建立持久任务，不影响旧目标。

### 12.2 取消原任务并查询

用户：“先别生成了，查一下杭州天气。”

main 提出取消对应会话目标，调用 research，再结束本轮。取消和查询结果同时反映在提交回执中；查询失败也不妨碍一个独立、明确的取消生效。

### 12.3 补充偏好后继续原任务

旧任务：“生成路线”，正在等必要信息。用户：“我不吃辣。”

main 调用 prepare_requirements，采用饮食候选，保留旧任务。它可以简短提醒仍缺什么，但不能把“偏好已保存”当成生成完成。后续真正补齐必要信息时，再在有效授权下继续。

### 12.4 假设咨询

用户：“如果只有500元，还能这么玩吗？”

main 读取当前方案，必要时 research 使用任务局部假设评估。正式预算和当前行程都不变。用户之后说“那就按500元改”，才提出正式写入和修改候选。

### 12.5 有条件修改

用户：“查一下明天天气，下雨就把第二天改成室内，其他安排别动。”

main 先确认“明天”与第二天的日期关系，必要时澄清；查询结果适用且条件明确满足时，调用 revise_itinerary；条件不满足则不修改；结果未知则报告未知，不执行条件性写入。

局部范围通过当前行程引用、修改约束和既有精确编辑/差异检查约束。开放式改写不能宣称保证其余字符逐字不变；若用户明确要求逐字保留，应使用可验证的精确编辑或停止澄清。

### 12.6 查询插问后的一句短答

旧生成任务等待旅行预算；用户转问酒店，系统询问酒店每晚价位；用户说“500”。

main 依据 active_question 将其用于酒店查询，旧生成任务保持挂起。不能以“旧目标也缺预算”为由同时消费这句回答。需要恢复旧目标时再明确上下文。

## 13. 分阶段实施与切换

### 阶段 A：基础合同与候选工作区

- 定义 CapabilityResult、TurnWorkspace、终止提案、CommitReceipt 和任务状态 v2。
- 从现有 Runtime 分离专业结果与最终 AgentReply；业务结果保持兼容。
- 建立离线、无网络、独立内存/临时数据库测试。
- 先验证一次提交、候选依赖、版本冲突、supersede 和失败回执，再接真实模型。

验收门槛：专业能力没有直接落库路径；陈旧执行不能保存需求、正文或任务状态。

### 阶段 B：主执行循环与全部现有基础能力

- main 使用工具调用替代 INTENT_SCHEMA；接入任务管理、需求、查询、生成、修改和结束工具。
- 专业能力遇到缺项返回 main，不再结束整轮；正式需求写入口统一。
- 本阶段仅在隔离环境覆盖现有能力，不开放生产聊天新链路；至少完成阶段 C 的跨轮状态后，才能在阶段 D 切换。不要只迁移某几个语句、其他语句临时交回旧分类器。
- 现有页面显式操作使用相同提交服务，不增加不必要的 main 调用。

验收门槛：复合请求无需新增组合 action；简单请求无多余需求前置；输出仍适配现有页面。

### 阶段 C：跨轮任务与持久化

- 接入追问绑定、多个未完成目标、恢复前依据检查、重启/清空策略。
- 旧 `awaiting_generation` 缺少可靠来源时迁移为待重新确认的挂起目标，不编造授权，不自动生成。
- 加入 workflow revision 防止仅任务状态变化时的旧写入。

验收门槛：插问不误消费旧缺项，需求更新不误删旧目标，跨轮恢复不依赖最近8条聊天仍包含原请求。

### 阶段 D：真实模型评测与可回滚切换

- 保留旧实现作为测试基线；按同一批样例比较完成率、误写率、调用次数和时延。
- 通过服务端配置选择每个执行任务的运行策略，并在提交任务时固定策略；同一执行中不得新旧循环互相回退。
- 真实服务不双跑有副作用的请求。对照只在独立快照、冻结工具或只读环境执行。
- 回滚保留已保存需求/正文；v2未完成任务归档或挂起，不直接转换为旧的自动生成等待标志。
- 验收通过并完成回滚演练后，删除聊天入口的旧分类与角色状态清理逻辑。

各阶段是实现顺序，不代表可以提前宣称新架构已完整上线。依赖阶段完成前，只在隔离环境运行。

## 14. 验证方法与验收标准

### 14.1 离线确定性验证

至少覆盖：

- 能力白名单、跨 trip ID 拒绝、伪造 artifact/evidence 引用拒绝；
- 子能力的 needs_input 不误终止父循环；
- 查询结果 unknown 不授权条件写入；
- 需求候选变化后行程候选失效；
- 独立需求部分成功与依赖需求禁止部分提交；
- confirm 与任务完成状态一致，不能确认未见草稿；
- 新消息 supersede、表单变更、方案变更、仅工作流版本变更时拒绝旧提交；
- 同 request_id 重试、重复工具调用不重复保存；
- 重启恢复、清空聊天、v1/v2迁移与回滚；
- 预算耗尽、传输失败、持久化失败时原状态与回执一致；
- 旧展示 job 不覆盖新正文。

这些测试使用假模型响应验证程序边界，不宣称评估了自然语言理解。

### 14.2 真实模型任务集

建议首批不少于50个场景，每场景独立重复3次；固定提示词、模型配置、源码版本与工具条件，并保留原始失败记录。首批覆盖：

- 单诉求及多诉求；顺序、条件、否定、假设、转述；
- 新需求与局部修改的边界；解释与事实查询；
- 补充、纠正、短回答、插问、取消和多个未完成任务；
- 超出最近8条消息的任务续接；
- 外部工具不支持、空数据、失败和证据过期；
- 同城与完整旅行、已有方案与无方案；
- 用户明确不允许外查、明确只记录、明确不改其他日期；
- 提示注入式外部内容和专业结果中的越权建议。

使用冻结工具先评任务理解与编排，再以少量真实工具验证连接链路。不得把模型引用了假工具结果当作现实事实已核实。

### 14.3 指标与发布门槛

分别统计：

1. **完整任务完成率**：所有明确诉求是否完成，或是否诚实说明阻塞；不能只计JSON合法。
2. **未授权写入率**：假设值写正式需求、取消后继续生成、查询误改方案、范围扩大。
3. **跨轮绑定正确率**：答案是否进入正确任务/字段，旧任务是否被误删或误恢复。
4. **条件执行正确率**：未知、否定和证据不适用时是否错误写入。
5. **事务与隔离正确性**：过期任务写入、版本冲突、重复提交。
6. **成本和时延**：各角色调用数、token、外部请求数、p50/p95、超时率。

建议发布门槛：确定性保护测试全部通过；验收样本中未授权写入和旧任务越权提交为0，一旦发现即阻断发布；其余任务质量不低于旧实现，并明显改善复合/跨轮样例。样本零失败不等于生产错误率为零。具体质量目标与时延预算在基线测量后冻结，不能为了通过测试事后放宽。

当前已有专项测试曾运行36项通过，但分类结果为脚本预设；它们只作为迁移回归资产，不能作为本方案真实语义质量的验收证据。被删除的历史测试不视为当前可运行覆盖，需要按实际文件清点补建。

## 15. 成本、风险与最终边界

### 15.1 main 能否使用无思考模型

**可以。工具调用和多步任务执行不以显式思考模式为前提。** main 每次读取当前状态、选择下一步能力，Runtime 执行后提供新观察值；这种外部工具循环与模型是否开启可配置的思考模式是不同层面的机制。

需要区分：

- “无思考”可以是模型没有独立思考模式，也可以是当前服务关闭显式 thinking；这不意味着模型完全没有推理能力。
- `reasoning_effort=low` 不等于关闭思考，具体开关需遵循当前模型和服务的参数协议。
- 输出中看不到 reasoning 字段，也不能证明服务没有使用内部思考或额外 token；应核对服务支持和真实 usage。

**建议将支持可靠工具调用的无思考配置作为优先测试方案，而非直接宣称足够上线。** 专业规划和修改保留独立配置；main 用较轻配置，不要求所有角色一起关闭思考，也不要求为实现本设计更换提供方。

main 必须实际通过以下能力验证：理解条件与否定、在多个工具中选择下一步、从工具错误中有限纠正、绑定跨轮短回答、区分假设与正式写入、知道何时询问或结束。JSON 格式合法与简单分类准确不代表通过这些验证。

对照方法：固定任务集、上下文、工具结果和预算，比较同一模型关闭/开启思考（服务支持时）；如比较不同模型，单独记录模型差异，不把结果全归因于思考开关。记录完整任务质量、误写、模型/工具调用总数和端到端p50/p95，不能只比较一次main请求的耗时。无思考单次更快，但若导致更多错误调用和重试，整轮未必更快。

第一版不增加“判断复杂度的分类器”，不做未验证的按语句关键词切换模型。使用一种经过验收的 main 配置；未达质量门槛时再评估更强的无思考模型或启用有限思考。程序校验失败时允许有界纠正、澄清或安全停止，但这些保护不能保证发现所有语义错误。

上述为选型建议，尚未决定具体 main 模型或开关，也没有修改当前运行配置。此前简单意图延迟基准不能替代新主 Agent 的完整任务评测。

### 15.2 可能增加的成本

main 在专业能力返回后可能需要再调用一次模型，这比“分类后直接结束”更贵、更慢。通过以下措施控制，而不是假设新架构一定更快：

- 简单回复直接结束；已有需求完整时不重复调用需求能力；
- 行程全文保存在 artifact 中，不重复读写与重写；
- 复用本轮事实缓存，限制重复工具调用；
- 共享现有总预算，另设 main 步数上限，不能叠加为每个子 Agent 各16次调用；
- main 的思考强度通过任务质量/延迟对照决定，不直接照搬原分类节点参数。

### 15.3 不把控制权全部交给模型

main 可能漏掉某个诉求、误解条件或错误选择能力。通用架构减少的是固定分支造成的结构性遗漏，而不是赋予模型完美理解能力。

程序可以可靠约束资源、权限、版本、候选依赖与提交次数；对任意自然语言的含义与答案充分性，仍需要良好上下文、澄清机制、评测和持续观察。不要用“已通过 Schema”替代“已正确理解用户”。

### 15.4 设计完成标准

当一种新的复合表达出现时，优先问：现有基础能力能否组合完成？

- 能完成：调整 main 的理解与评测，不新增业务组合分支。
- 缺少能力：增加一个边界明确、可验证的基础工具。
- 授权/数据不足：返回有上下文的澄清或未完成状态，不猜测写入。

**最终目标不是让意图分类覆盖所有句子，而是让系统理解完整任务，使用受限能力逐步完成，并在不确定时保留正确的上下文与业务状态。**
