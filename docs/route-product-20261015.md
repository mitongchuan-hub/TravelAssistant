## 本轮方向

从“在聊天中获得一篇行程”调整为“在路线页理解、调整并使用方案”。以一天同城游为首要验证场景，多天、旧完整旅行、想法和聊天继续保留。沿用现有雾蓝样式和手机优先布局，不新增 Agent、不接入地图 SDK、不增加预订或支付。

目标用户（已订住处、来到陌生城市、希望少做路线拼接）仍为待验证假设，不宣称已完成市场验证。

## 用户可见行为

1. 同城创建完成和旅行列表默认进入路线页；旧完整旅行默认聊天不变。
2. 没有方案时先展示可信住宿和已保存设置，可直接生成；可选日期、人数、预算不成为前置问卷。
3. 正文先保存与交付；后台卡片独立整理。卡片未就绪或失败时，完整原文仍可阅读并可单独重试卡片。
4. 路线卡片先展示逐日顺序，再展示准备信息。每站保留原文时间、时长、费用、提醒，不把建议时段变成已确认预约。
5. 地点能与可信证据唯一对应时才提供地图、地址；缺证据、同名、冲突或区域建议保持待核实。
6. 只有连续可信端点才能提供高德“两点重新规划”链接。历史耗时必须与记录的方向、方式和端点一致，否则不展示数字。外部规划与应用已查询到路线是两件事。
7. 站点调整面板展示当天、标题、时间和地点；换一站/少停留只是预填要求，仍需提交。服务器按当前方案解析目标，不信任浏览器自报标题或 POI。
8. 设置变化保留旧路线并提示更新，不把当前新住宿接到旧方案。旧数据缺住宿坐标快照时不回填导航。
9. 任务使用真实等待/处理中/失败状态，支持恢复与重试，不显示虚构完成百分比。页面过期时保留输入并要求查看最新路线。

## 数据与安全边界

- 新增 `TripPlan.lodging_snapshot` 保存本方案的住宿依据，旧记录缺省空对象，不批量迁移或修改原正文。
- `route_view` 是纯派生视图：不外查、不写入卡片、不接受模型或用户提交的导航 URL/坐标。原 display 仍是展示协议数据。
- plan/revision 新界面带 `expected_plan_id`、`source_hash`、`expected_requirements_revision`；站点增加零起始的 `display_target.day_index/item_index`。重复请求先按原 request_id 找回，过期基线不能静默重试到新方案。
- 查询成功只证明查到相关资料；不证明开放、预约、价格、遮雨设施或整条路线可执行。导航链接会在用户点击后交给高德重新规划。
- 开放式修改仍由既有模型交付完整文字，程序不保证未修改段落逐字不变；用户明确指定字句的精确编辑保留既有严格规则。

## 用户验收清单

建议先用隔离合成应用检查功能，再用真实业务环境自行核对内容：

- [ ] 只填住宿，确认后进入路线，不先强制聊天。
- [ ] 不填日期、人数、预算仍可生成，不出现默认人数或今天的日期。
- [ ] 能看懂住处 → 各站 → 回住处的顺序，正文和卡片都可达。
- [ ] 每站的时间建议、费用与未知事项可见；地图链接仅对可信地点出现。
- [ ] 逐段高德链接的起终点正确，查询失败不显示编造的分钟数。
- [ ] “调整此项”显示正确天数与站点，关闭后草稿保留，提交后更新路线。
- [ ] “轻松一点”“早点返回”先展示调整要求，不点击即自动重排。
- [ ] 生成/修改失败保留旧路线和输入，可以重试；仅卡片失败可只重试卡片。
- [ ] 设置换住处后显示旧方案提示，新住处不会混入旧路线。
- [ ] 在两个页面分别修改，旧页面提交被拒绝，不覆盖新方案。
- [ ] 320/390/430px和桌面可使用；键盘能关闭调整面板、焦点回到触发按钮。
- [ ] 多天、旧旅行、聊天和想法仍可访问。
