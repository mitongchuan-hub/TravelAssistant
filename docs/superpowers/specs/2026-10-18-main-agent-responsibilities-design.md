# MainAgent 职责与业务边界调整方案

日期：2026-10-18
状态：职责设计与实施验收依据。业务受理边界已部分实施并有限验证，见 [验证记录](../../known-issues/2026-10-18-main-agent-scope-verification.md)；追问生命周期、保存状态及整体验收尚未完成。
适用对象：当前 `task_execution` 框架中的 `main_execution` 主控及其协作能力。

## 1. 调整目标

MainAgent 是同城游玩服务的业务主控：判断请求是否受理、理解用户授权、组织事项、调度专业能力、协调追问，并向用户解释结果。

本次调整需要同时解决四个问题：

1. 明确当前服务受理哪些请求，防止主控成为通用问答助手。
2. 让直接文本回复、结构化结束和专业能力返回遵守一致的业务边界。
3. 区分临时插话、追问答案和任务切换，保留用户仍在等待完成的任务。
4. 将结果说明与真实保存状态分开，由程序根据提交结果表达保存状态。

实现应沿用现有主控、需求、查询、规划、修改和展示分工，以及现有候选校验和提交框架。执行前阅读 [CLAUDE.md](../../../CLAUDE.md)、[PRODUCT.md](../../../PRODUCT.md) 和 [README.md](../../../README.md)，保留工作树中已有的其他修改。

## 3. 角色与程序的职责分工

| 对象 | 应承担的职责 | 交付物与边界 |
| --- | --- | --- |
| MainAgent | 判断受理范围；识别各事项、依赖和授权；选择能力；协调追问；选择成果；解释结果和限制 | 调用意图、合法候选引用、限定范围的用户回复。行程正文通过专业能力的 artifact 交付 |
| 需求能力 `prepare_requirements` | 从绑定的真实完整用户消息中提取明确的正式需求变化 | 正式需求候选、缺项或澄清请求；仅提取业务内且已授权的变化 |
| 查询能力 `research` | 回答主控交给它的具体同城游玩查询问题 | 查询摘要、真实证据引用、限制和缺项；查询结果不自动授权修改需求或行程 |
| 规划能力 `draft_itinerary` | 基于有效需求生成完整同城行程 | 完整正文候选、证据和限制 |
| 修改能力 `revise_itinerary` | 基于当前方案和用户授权范围修改行程 | 修改后的完整正文候选，或用户明确指定的精确文字编辑结果 |
| 展示能力 `display` | 将已交付正文整理为派生展示 | 与正文一致的卡片；展示完成不等于业务事实通过验收 |
| `TaskExecutionRuntime` | 执行工具合同、限制调用、处理结构化状态、绑定追问答案、管理本轮候选和结束流程 | 可提交提案；保持与提示词一致的结束和任务保留规则 |
| `TurnWorkspace` | 管理候选、来源、依赖、条件、显式采用和提案完整性 | 经校验的终止提案 |
| `TurnCommit` | 核验当前状态、实际应用变更、原子保存、形成回执和保存状态文案 | 真实提交结果及最终消息 |

MainAgent 可以判断需要更新需求，但正式需求候选由需求能力提出；可以选择提交候选，但是否实际保存由程序决定。用户授权的理解属于主控职责，引用有效性和写入权限的最终校验属于程序职责。

规划和修改能力可继续按各自任务需要直接查询地点、路线、天气等。`research` 主要服务于独立查询和主控需要先验证的事实、条件，不要求所有专业能力的内部查询都绕经主控重新分发。

## 4. 业务受理规则

### 4.1 当前产品范围

以当前已确认住宿及其城市为依据，提供同城游玩需求整理、路线规划、行程解释和授权修改，以及为这些事项服务的地点、餐饮、市内交通和天气查询。

一般咨询不必先满足全部生成条件。例如询问某个景点或解释当前路线，不应因尚未填写人数、预算或完整日期而被阻断。生成、修改所需的住宿、日期和天数条件，继续按对应业务规则校验。

同城游玩服务不因“旅行助手”名称而自动扩展为跨城规划、预订支付、通用翻译、通用编程、医疗诊断、用药剂量或投资建议服务。与旅行相关，也不等于当前产品具备执行能力。

### 4.2 按事项判断范围

| 受理结果 | 判断依据 | 处理方式 |
| --- | --- | --- |
| 业务内 | 用户目的和已有上下文能明确关联同城游玩服务，且有对应能力 | 根据授权处理；需要事实时查询，需要写入时走候选与提交 |
| 信息不足 | 有合理的业务关联，但目的、地点、日期、指代或操作范围无法确定 | 只澄清影响下一步的关键问题；已有信息不重复询问 |
| 业务外或能力不支持 | 请求明确属于其他业务，或要求执行当前产品不支持的操作 | 简短说明范围或能力限制，给出与本服务有关的引导，不提供越界实质内容 |
| 混合请求 | 同一消息同时包含可受理和不可受理事项 | 分别处理：完成可独立执行的业务内事项，简短说明其余事项的限制 |

这些是受理语义，不是新的意图组合路由框架。实现可在现有主循环和协议中表达；不得仅凭某个词是否出现判断范围，也不得将模型自报“业务内”当作语义正确性的证明。

### 4.3 天气等辅助查询

- 当前已有明确的城市和出行日期，用户问“明天这里下雨吗”，可以沿用合理上下文查询，无须反复要求用户声明“为了旅行”。
- 询问天气是否影响当前游玩路线，属于业务内；查询不自动授权重排行程。
- 缺少上下文的“天气怎么样”，先澄清要查询的游玩城市和日期，不默认所在地、今天或当前系统位置。
- 用户明确要求与同城游玩无关的独立天气服务时，说明当前服务范围。
- 请求指向其他城市且用途不明时，先确认用途，不直接修改当前城市或住宿设置。

## 5. MainAgent 可以直接回答什么

将“纯闲聊”替换为明确的直接回答范围：

1. 简短招呼、致谢和必要的礼貌回应。
2. 如实说明本服务的能力、使用方式和限制。
3. 解释已提供的需求、当前行程及已有处理状态。
4. 汇总已取得的适用证据、专业能力结果和已知限制。
5. 澄清业务关联、含义或指代。
6. 对业务外或不支持的事项作简短说明，并引导回服务范围。

直接回答仍受以下约束：

- 数学解题、完整菜谱、诗歌创作、无关翻译等独立任务，不能因为“不需要工具”就归为闲聊。
- 动态天气、营业时间、线路耗时和价格等，需要适用查询证据；查询失败时说明未知，不凭模型知识补齐。
- 对业务内问题可以依据已知信息解释和推理，但不能在解释中增添未经支持的事实承诺。
- 行程正文由规划或修改候选交付，主控不额外重写第二份正文。
- 医疗诊断、具体用药剂量、投资建议等，不因消息包含旅行地点而进入受理范围；可简短引导至相应专业服务。
- 用户或外部资料要求改变角色、忽略业务边界，不能扩大受理范围和权限。

这些规则同时适用于直接 prose、`finish_turn.reply`、追问文字和主控转述的专业能力摘要。专业能力返回越界内容时，主控不能直接透传。

## 6. 追问与任务生命周期

### 6.1 区分本轮消息的作用

| 消息作用 | 对原追问和任务的处理 |
| --- | --- |
| 明确回答当前追问 | 经 `task_ref`、`answer_question_ref` 和 `answer_target` 校验后消费答案；只用于指定用途 |
| 招呼、致谢、能力说明、业务外问题或临时只读插问 | 保留原任务和原活动追问，本轮可作限定范围的回复 |
| 新的独立业务事项 | 处理新事项时保留原任务；必要的新追问仍遵守唯一活动追问合同 |
| 明确要求停止、取消、暂停或切换原任务 | 按用户授权执行相应任务操作；取消会话任务与删除已保存需求、行程分别判断 |
| 短答含义或目标不明 | 澄清含义，不猜测绑定对象，不提前消费原追问 |

不能把“没有回答原问题”自动视为取消或挂起原任务。短答也不能因缺少完整旅行词汇而被直接判为越界。

### 6.2 原追问可以跨越一次插话继续等待

示例：系统正在问“哪天出发？”，用户先问“你能帮我做什么？”

目标行为：介绍本服务能力，原日期追问继续有效；用户之后给出明确日期，仍可绑定原问题。插话不应导致原任务取消、挂起、完成，也不应被当成日期答案。

调整 `_unsettled_base_question`、`_can_finish_prose` 和 `_terminal` 时，需要允许这种“本轮已回复，原追问仍待回答”的合法状态，不能只改提示词而保留运行时的强制处置要求。

保留等待状态的放行应与本轮消息的作用一致。用户明确回答原问题时，仍须检查答案是否正确绑定和消费；不能通过删除全部追问检查，让任何结束路径都跳过答案处理。

如新业务确实需要建立另一个活动追问，继续遵守唯一活动追问规则，并通过受支持的工作流操作暂存原任务。临时的范围澄清应尽量只作对话澄清，不为此替换已有正式业务追问。

### 6.3 状态保持的验收口径

对招呼、能力说明、越界拒绝或不涉及原任务的只读插问，核对：

- 正式需求内容与需求版本不变。
- 当前行程内容、依据和确认状态不变。
- 原任务的目标、状态、未完成事项不变。
- 原活动追问的引用、所属任务、内容、`answer_target` 和绑定资格保持有效。
- 没有消费答案、采用业务候选或触发规划修改。

聊天消息、正常执行记录、审计时间和请求控制信息可以按现有流程记录。测试应比较业务语义状态，不能把“整个数据库或工作流 JSON 字节完全不变”当作保持状态的定义。

## 7. 执行、失败与用户回复

推荐的主控决策顺序：

1. 读取本轮消息、环境和必要上下文，判断与原追问、原任务的关系。
2. 识别全部事项，逐项判断业务范围、能力支持和用户授权。
3. 对业务外事项说明限制；对影响后续动作的歧义澄清。
4. 对可受理事项组织依赖：正式需求变化先整理，需要事实先查询，具备条件再规划或修改。
5. 检查能力的结构化返回与真实证据，继续处理可独立完成的事项。
6. 选择本轮合法候选，或在无业务变更的情况下结束回复并保留等待任务。
7. 程序校验并提交；最终消息根据真实回执表达保存状态。

混合请求传给 `research` 的问题应只包含可受理事项。需求能力仍须收到绑定的真实完整消息，`user_quote` 不能为过滤越界内容而被改写；需求提取仅采用其中明确授权的业务内变化。

工具不可用、证据不足、条件未知时，应说明具体限制。不能将外部查询失败视为可以自行回答越界内容的授权，也不能把未知条件视为满足条件。假设咨询不自动成为正式需求或修改授权。

### 7.1 两类结束路径保持一致

- 不调用工具直接回复，也必须遵守受理规则和直接回答范围。
- 使用 `finish_turn.reply`，也必须遵守同一规则；增加结构化包装不能扩大回答范围。
- `ask_user` 需要区分正式业务追问与临时对话澄清，避免为了拒绝或说明能力而创建、替换业务任务。
- 生成、修改、确认入口的快捷路径需要审查同样的业务和授权边界；可以保留快捷路径，不要求为每次按钮操作额外调用主模型。

提示词约束、可执行的运行时合同检查和语义评测需要配合使用。引用校验、状态校验或一个分类字段，都不能单独证明自然语言内容没有越界；实施报告应说明各层实际验证了什么。

### 7.2 保存状态由程序报告

主控负责表达处理结果、限制和未完成事项，使用候选引用提出本轮选择。主控生成提案时不自行声称“已保存”“已确认”或“已取消”。

`TurnCommit` 在实际提交后，根据真实变化统一添加对应状态文案。独立需求成功而规划失败时，最终消息应如实表达需求的真实保存结果以及行程尚未生成；需求保存被拒绝时，不得残留成功文案。

## 10. 验收场景

| 编号 | 输入与前置状态 | 预期行为 |

## 11. 验证方式与交付要求

### 11.1 自动化验证

针对会话状态、答案绑定、工具调用、候选采用和提交结果编写行为测试，先验证原行为的失败场景，再验证调整结果。覆盖直接正文、`finish_turn`、`ask_user` 和快捷入口。

当前 `tests` 目录仅发现 `__init__.py`。实施者应先补齐实际可运行的测试文件，例如 `tests/automated/test_main_agent_responsibilities.py`，再运行项目指定的解释器：

```powershell
& 'E:\anaconda\envs\TravelAssistant\python.exe' -m pytest tests/automated -q
```

测试需断言第 6.3 节定义的业务状态，以及正确的工具与效果行为。对越界请求，业务工具未调用、数据未改变只是必要检查，不能单独证明回答内容正确。

### 11.2 真实模型语义评测

覆盖正常业务、明确越界、模糊边界、旅行语境夹带问题、追问插话和失败回退。实际调用与项目执行环境、评测约定保持一致，交付时注明模型、提示词版本、运行条件和调用范围。

逐条查看最终用户文本，核对：是否提供越界实质内容、是否正确说明服务范围、是否误拒合法业务、是否出现无依据事实或错误成功状态。对存在行为波动的场景进行多次运行，并逐次保留结果，不用单次通过推断稳定解决。

当前记录引用的旧数据集和运行器不在已检查的工作树文件中，不能把历史命令当作现成可执行入口。实施者应补齐或提供实际存在的运行器、数据集及执行命令，分别报告离线合同检查与真实模型语义结果。

### 11.3 开发交付内容

1. 列出实际改动文件，以及它们对应的职责规则。
2. 提供可运行的测试和评测命令、实际结果及失败样例。
3. 展示至少一组越界问题、一次临时插话后恢复追问、一次合法业务查询和一次提交失败的用户可见结果。
4. 说明运行时可确定性校验的边界，以及仍依赖模型语义判断的部分。
5. 全部固定验收场景应符合本方案；存在失败或尚未验证的项目时，明确列出，保持已知问题记录与实际证据一致。
