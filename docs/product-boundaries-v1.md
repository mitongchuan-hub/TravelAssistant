# TravelAssistant 首版产品边界

确认日期：2026-10-10。用户确定专注国内旅行，在17项建议中仅将第5项默认交通改为“地铁优先”，其余采用建议。本文件是后续开发与验收的产品依据；已确认的目标与现有代码实现状态分别列出。

## 已确认的范围与默认行为

| 编号 | 产品边界 | 首版规则 |
| --- | --- | --- |
| 1 | 目的地范围 | 中国大陆目的地，金额统一人民币；港澳台及境外旅游以后再评估。超出范围的旅行请求说明支持范围，不当作已支持场景交付。 |
| 2 | 城市范围 | 一趟旅行以单城为主，允许当天可返回的近郊。多城行程、跨城游线以后单独支持。 |
| 3 | 旅行长度 | 明确支持当天往返至7个自然日，日期含抵达日和离开日。 |
| 4 | 目标用户 | 普通个人、家庭、朋友自由行优先，大型团体以后评估。带儿童或老人时，在规划中补问年龄、步行限制、午休与房间需求；不增加创建页必填组数。 |
| 5 | 当地交通 | **默认地铁优先**，首版覆盖地铁、公交、步行和打车。地铁不可用或不符合用户限制时，结合预算、步行能力、时间和实际资料选择其他方式，不为了地铁优先绕远或违反硬约束。自驾及停车、充电、驾驶强度以后单独支持。 |
| 6 | 抵离时刻与预留 | 时间按火车到站/发车、飞机落地/起飞等交通工具的抵离时刻填写，出站、取行李、候车和安检另留时间。返程默认火车提前60分钟到站、国内航班提前120分钟到机场；这是规划预留，具体车站、机场、承运方要求与用户限制优先。 |
| 7 | 预算范围 | 按用户填写的费用范围拆住宿、餐饮、当地交通、门票及机动额度；提供“含当地费用，不含往返大交通和购物”的快捷选项。费用范围仍须明确，用户可修改。拆分为分配额度，不冒充报价。 |
| 8 | 住宿建议 | 首先给住宿区域、房型和预算额度。用户已订酒店时围绕它安排，具体酒店候选有查询依据后再给；不强行指定酒店。 |
| 9 | 餐饮建议 | 可以给用餐区域、菜系和预算；取得可用门店资料时提供候选。不要求每顿饭都绑定具体店铺。菜名、评分或菜系不能证明过敏安全。 |
| 10 | 要求与偏好 | 明确“必须去”“不能做”和禁忌是硬约束；一般“想去”“最好”“可选”属于可取舍的偏好，取舍说明原因。硬约束冲突先询问，不擅自放宽。 |
| 11 | 固定安排 | 已订酒店、已预约门票和明确不可移动的活动时段属于固定安排，全局重排仍保留；只有用户明确要求才可改变。用户提供的“已订”信息保留来源，不当作系统独立核实的结果。 |
| 12 | 默认节奏 | 未指定时以轻松为默认，每天约2—3个主要活动，留出用餐、交通及休息。按时间块表达，抵离和预约时刻明确；不机械凑活动数量或填满每个时刻。用户明确偏好与固定安排优先。 |
| 13 | 行前复核 | 用户主动要求复查；变化时说明影响，调整仍需要用户授权。主动通知和自动重排暂不纳入首版。 |
| 14 | 交付体验 | 完整文字生成后即可阅读，卡片随后补齐。卡片转换只处理当前原文，不重新规划；迟到展示不得覆盖后续新方案。 |
| 15 | 行程确认 | 去掉人工“确认当前行程”状态及操作，只维护当前方案和待核实事项。首版不增加“已采用”替代标记。 |
| 16 | 出行功能 | 首先做好规划、修改和地点查看；一键导航作为下一项，分享与导出后置。 |
| 17 | 使用与数据 | 先小范围内测。删除旅行应覆盖其需求、聊天和当前行程；调试日志、备份保留期限在公开使用前明确。既有日志保留，本次边界确认不触发业务数据删除。 |

“地铁优先”是默认选择，不等于地铁可用性、无障碍设施、首末班车或实际运行时间已经核实。缺少资料继续说明未知；用户明确指定交通方式时优先遵守用户要求。

## 延续的约定

- 第一层只有闲聊、查询、规划、修改四类意图，需求补充放在规划内部。
- 创建页五组必填：城市、起止日期、抵离时间与地点、人数、预算金额/总额或人均口径/费用范围。错误保留输入，不创建半成品。
- 规划范围是抵达旅行城市到离开旅行城市，时间按当地时间。当天往返不住宿，不查询具体火车班次。
- 需求独立持久化；只补充需求不授权生成。回答此前已授权规划的缺项可以承接，含糊确认不产生未来授权。
- 每趟旅行只保留最新版，生成/修改覆盖当前方案。新消息作废未完成旧轮，迟到写入不能覆盖当前数据。
- 事实依据来自实际资料。POI匹配不证明开放、价格或预约，未知保持未知；人为预留标估算，预算额度不等于报价。资料不足可以交付附条件草案，不能保证整份方案已核实或费用必然在预算内。
- 完整文字是业务交付，展示JSON是当前原文的派生数据。转换须保留条件、未知和估算，失败回退原文；结构与hash通过不能代替语义忠实度验证。

## 当前实现与待办

本次完成产品约定落档。代码现状以[当前架构](agent-architecture-current.md)为准，以下项目是后续工作，不能按本文件宣称已经在应用启用。

| 项目 | 现状与下一步 |
| --- | --- |
| 大陆、单城、1—7天范围 | 现有城市输入没有统一的产品范围核验，日期校验允许更长跨度。后续在创建、需求更新及规划入口统一检查支持范围，目标不明确时询问。 |
| 地铁优先 | 路线工具支持transit，当前没有统一的地铁优先策略。后续让规划/修改默认遵循此选择，并核对具体工具结果的交通方式，不能把公交结果直接叫作地铁。 |
| 抵离含义与返程预留 | 当前抵离字段已有，预留时间依赖模型。后续明确字段说明、旅行方式与60/120分钟默认预留，保留特定要求和老人等限制所需余量。 |
| 预算快捷范围、家庭信息、轻松节奏 | 现有预算范围、人数、节奏和备注可保存。后续补齐快捷选择及规划提问规则，预算上限与实际报价继续分开。 |
| 软偏好和固定安排 | 目前没有独立的软偏好与固定安排保护协议。后续建立保存与修改规则，不把已有硬要求静默改成软偏好，也不把“打算订”当成“已订”。 |
| 文字先读、卡片后补 | 已实现：主业务先保存原文并完成，独立后台展示任务绑定计划ID、原文指纹和计划需求快照，卡片完成局部更新；业务运行期间延后卡片发布，旧结果与重启中断有保护。 |
| 去掉确认操作 | 当前仍有页面与聊天确认功能。后续移除入口、确认路由/动作和对应测试，不引入新的采用状态。 |
| 地点查看、删除旅行 | 旅行列表删除已实现，覆盖需求、聊天、行程、任务与展示任务；主业务活跃时拒绝，独立卡片不阻塞删除。新文字卡片尚未完整绑定可信地点详情，导航/分享/导出仍后置。 |

## 后续验收调整

现有[v1.1测试结果](travel-agent-evaluation-latest-only-20261010.md)是本次边界确认前的代码与输入结果，保持原始成绩。

后续更新数据集并使用新版本号：将东京规划从核心支持场景移出，用国内机场抵离和两晚预算场景接替相关时间/夜数检查；增加超出目的地/城市/天数范围的处理、地铁优先及其受约束替代、固定安排保护、软偏好取舍、文字先读与迟到卡片保护。人工确认案例改为验证确认功能移除，旧版本请求不恢复及最新方案保护继续保留。

未落地的新规则不能通过重新解释旧输出算作通过；输入、实现和验收协议变更后另跑新一轮。日志与备份期限依第17项在公开使用前制定，不在此虚构保留天数。
