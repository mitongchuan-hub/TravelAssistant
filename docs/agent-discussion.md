### 讨论范围

我们只讨论 **Agent 部分**，暂不展开前端、数据库和部署，也先不改代码。

讨论范围收敛为这条链路：

```text
用户输入 + 当前需求 + 必要上下文
                ↓
         main：识别意图
                ↓
     ┌──────────┼──────────┬──────────┐
     闲聊       查询       规划       修改
     chat     research   planning   revision
                └──────────┴──────────┘
                           ↓
                  共用 AgentLoop
                  模型决策 ↔ 工具调用
                           ↓
                     回答 / 行程正文

已保存的行程正文 → display：整理展示数据
```

说明：这是聊天入口的概念链路。`main`、`chat` 和 `display` 是无工具节点；`research`、`planning`、`revision` 共用 AgentLoop 框架，不是每次依次执行三个角色。页面明确的生成或修改操作可以直接进入对应业务角色。只有生成或修改了行程正文，才涉及后续的展示整理。

### 五个重点问题

1. **角色分工**：为什么分这些角色，各自该做什么、不该做什么？
2. **意图路由**：如何区分查询、记录需求、生成和修改，如何承接上一轮？
3. **上下文管理**：每次给模型什么，哪些信息通过 `read_context` 按需读取？
4. **工具循环**：模型如何选择工具、利用结果、结束任务，失败时怎么办？
5. **输出与约束**：如何限制越权修改、事实编造，以及正文与卡片不一致？

### 核心问题

> 哪些决策交给模型，哪些必须由程序控制？

先从 **“一条用户消息进入后，Agent 到底如何一步步处理”** 开始，把实际执行机制讲透，再判断现有角色划分是否合理。

### 2026-10-16 · 是否将需求补充独立为 Agent

#### 问题与背景

用户说明：另一个窗口正在将需求补充功能从规划 Agent 中移出，单独实现一个 Agent，并询问对这一做法的看法。

本次未检查另一个窗口的具体实现，以下是架构建议，不是对该实现的评审或验收。本文前面的链路保留为建立讨论时的基线，不能据此判断并行改造是否已经完成。

#### 助手判断

方向合理，倾向支持：**把需求理解与规划职责拆清，但将其实现为按需调用的轻量需求处理角色，而不是每条消息都必须经过的额外工具循环。**

需求处理的目标是准确理解和维护用户约束；规划的目标是在约束下选择地点、安排路线与时间。二者可以独立配置提示词、权限和测试，但拆分本身不保证质量或速度提升，需要对照评测。

#### 预期收益与代价

- 需求角色专注提取、纠正与澄清，不需要同时考虑路线安排，有机会减少遗漏或把未知补成默认值的问题。
- “只记住新需求”和“按新需求重新生成”更容易分别约束，避免更新需求就擅自重排。
- 规划与修改可以共享同一个需求处理入口，减少两套提取和更新逻辑。
- 可以单独评测需求提取、否定、删除、指代与多轮承接，定位失败原因。
- 代价包括额外模型调用、延迟、失败点，以及角色之间的交接损失。如果两个角色都继续提取或修改需求，职责反而更混乱。

#### 建议的职责边界

| 部分 | 建议职责 | 不应承担 |
| --- | --- | --- |
| 意图识别 / 编排 | 识别本轮需要的操作组合，结合有效的待补充目标选择流程 | 将需求补充简单当成只能与生成、修改二选一的意图 |
| 需求角色 | 根据最新原话、当前需求和必要对话上下文提出结构化补丁或澄清问题，保留原话依据 | 编造未知值、自行查路线、生成行程、直接决定持久化或重新规划 |
| 程序 | 校验补丁、合并需求、检查版本与授权、判断必填条件、决定后续动作 | 把模型提取成功等同于事实正确或用户授权生成 |
| 规划 / 修改角色 | 使用校验后的需求和原始请求生成或修改行程；遇到歧义交回澄清 | 再保留一套可独立写入需求的竞争入口 |

需求角色不一定需要完整 AgentLoop。若主要工作是自然语言提取与澄清，优先考虑单次结构化输出；有明确的按需读取上下文需求时，再提供受限的只读工具。独立角色可以继续使用同一模型客户端，不意味着独立服务或更换模型。

#### 建议流程

```text
用户消息 + 当前需求 + 有效的待补充状态
                    ↓
           识别本轮需要的操作组合
                    ↓
       是否需要提取或澄清需求？
          ├─ 否：进入原有回答 / 查询 / 规划 / 修改路径
          └─ 是：需求角色提出补丁或澄清
                           ↓
                 程序校验与版本检查
                           ↓
                  根据有效授权继续
                    ├─ 只记录：保存合法变更并回复
                    ├─ 查询：将新需求交给查询角色
                    ├─ 生成：将新需求交给规划角色
                    ├─ 修改：将新需求交给修改角色
                    └─ 有歧义：追问，不越权执行后续动作
```

这是一条建议流程，不是当前代码的已实施状态。只发送一次对外回复，不让需求角色和业务角色各自向用户重复答复。交给后续角色的不应只有压缩摘要，还应包含原始用户消息、校验后的需求、补丁和明确的操作目标，避免遗漏限定条件。

#### 需要覆盖的典型场景

| 用户输入 / 状态 | 期望行为 |
| --- | --- |
| “预算改成 500 元，先别改路线。” | 更新需求，不修改当前行程。 |
| “预算改成 500 元，按这个重新安排。” | 同一轮先处理需求，再执行已授权的重排。 |
| “如果预算只有 500 元，够不够？” | 识别为假设性咨询，不直接覆盖正式预算。 |
| “把第二站删掉。” | 属于当前行程修改，不自动上升为永久偏好或禁忌。 |
| “500 元。”且上一轮正在追问预算 | 结合待补充状态理解；只有仍有效的生成/修改授权才可继续执行。 |
| 需求已经完整，用户仅说“生成路线” | 不为重复提取已保存字段而强制增加需求模型调用。 |

同城模式仍应只以已确认住宿及可信地图位置作为生成必要条件，不因独立需求角色而强制追问全部可选字段。住宿变更仍须走程序的可信地图确认，不能接受模型自报坐标。

#### 验证标准

与拆分前使用相同案例比较：需求提取准确性、无授权状态修改、复合请求完成率、澄清后的承接、模型调用次数、总延迟和失败率。特别验证新消息使旧轮作废后，迟到的需求补丁不能覆盖新状态。不能只看新增角色的单独提取成绩，也不能以 Agent 数量判断架构优劣。

#### 已确认结论与待确认事项

- **用户提供的状态**：另一个窗口正在进行需求 Agent 拆分；本次未核实具体代码与进度。
- **助手建议**：支持轻量、按需、共享的需求角色；程序负责状态写入与授权；需求处理与后续操作可以在同一轮组合。
- **尚未确认**：角色接口、调用时机、工具权限、复合意图表达以及实际实现是否符合上述边界。
- **本窗口实现状态**：仅追加讨论文档，未修改业务代码，也未要求另一个窗口改变实现。

### 2026-10-16 · 补充需求后如何直接进入规划

#### 用户问题

如果意图识别之后分为闲聊、补充、规划和改行程，用户输入需求、补充完成后，如何在不要求用户重复发出生成指令的情况下直接规划？本节聚焦这四个分支的衔接，不代表已决定删除原有查询能力。

#### 助手建议：区分处理阶段和最终目标

分支可以保留，但“本轮先进入哪个角色”不应等于“只能执行这个角色”。由 Runtime 保存本次最终目标并编排衔接：需求角色只处理需求，完成后返回程序，程序在满足条件时调用规划角色；不要求需求角色自己调用其他 Agent，也不必将其回复重新送进意图识别。

```text
识别本轮目标：只记录 / 生成 / 修改 / 其他
                    ↓
          本轮是否需要处理需求？
          ├─ 是 → 需求角色 → 程序校验并合并候选需求
          └─ 否 → 使用已有需求
                    ↓
          根据目标与必要条件选择后续
          ├─ 只记录 → 提交合法变更并回复
          ├─ 生成且已就绪 → 规划角色 → 统一校验提交
          ├─ 修改且已就绪 → 修改角色 → 统一校验提交
          └─ 缺必要条件或有阻塞歧义 → 追问并保留有效目标
```

图中的需求合并不要求在两个角色之间提前落库；规划应读取本轮校验后的候选需求，最终继续遵守统一提交与过期写入保护。只有合法的明确需求变更可按业务规则在后续生成失败时保留，不能先回复“保存成功”再跳过实际提交。

#### 两种直接续接

1. **同一条消息含需求和生成请求**：“两个人，预算 500 元，帮我安排一天。”识别到最终目标为生成，先处理需求，再规划，同一个业务任务内完成，不要求用户再发一次消息。
2. **跨轮补充先前生成请求的缺项**：第一轮用户已要求生成，但必要条件缺失；程序保留有效的待生成目标并追问。下一轮补充完成后恢复该目标。若缺的是住宿地图确认，应等待程序取得可信位置，不能把地址文字或模型坐标当成已完成确认。

可用 `pending_action=generate` 表达这个概念，但这只是说明字段，不是在要求新增同名字段；实施时应先复用现有等待生成状态。状态需要绑定相应旅行和授权上下文；撤销、只记录、旧轮作废后不得误续接，生成成功后应消费目标，避免后续补充重复触发。

#### 自动续接的条件

> 存在本轮明确的生成请求或此前仍有效的生成目标，并且必要条件满足、没有阻塞歧义、本轮没有撤销授权、请求仍有效，才直接规划。

“字段已填好”本身不等于用户要求生成。“预算改成 500 元，先记着”只记录；“如果预算 500 元够不够”仍是咨询。可选字段不应因拆分变成必填，也不需要为了内部角色交接额外询问“是否开始规划”。如果希望所有纯需求输入都默认生成，那是另一项需要明确讨论的产品规则，不是角色拆分必然带来的行为。

#### 与已记录第一步实现的关系

依据上节实施窗口写入的记录，第一步仅拆出纯需求处理；混合生成及已授权生成的缺项回答仍由 planning 处理，并非已经实现统一的 requirements → planning 链路。本窗口本次未检查最新业务代码，不将文档中的实施与测试状态当成独立验证结果。

#### 讨论状态

- **助手建议**：保留角色分支，由程序以“最终目标 + 当前处理阶段”衔接，支持同轮组合与跨轮恢复。
- **尚未确认**：是否将上述衔接作为下一步统一实现，以及具体接口和状态生命周期。
- **本窗口变更**：仅追加讨论记录，未修改 Agent 代码。

### 2026-10-16 · 需求前置阶段的具体实现方案

#### 本轮范围与代码核对

用户询问上节结构如何实现。本轮只读核对当前工作区并提出实现方案，没有获得或执行业务代码变更指令；其他窗口仍可能继续修改，以下不是冻结版本验收。

核对到的基础：

- 路由 Schema 当前包含 `intent/action/scope/user_quote/question`，严格限制额外字段；尚无独立需求前置标志。见 `app/agent_roles.py`。
- `requirements` 已独立，但混合生成、修改和更新后查询仍由原业务角色同步需求。相关专项测试也明确断言混合请求不经过 requirements。
- 同一 `TravelAgentRuntime` 持有本轮 trip 候选、需求补丁、证据、缓存和共享预算；`run_role()` 每次建立独立的模型消息与 Loop，适合作为串行阶段的执行基础。
- 需求工具更新本轮候选快照，不直接写 Store。Store 在模型调用前取快照，返回后检查原需求修订号、计划快照与任务有效性，再统一提交。
- `awaiting_generation` 已存在，但当前纯需求分支会清空生成等待状态。因此不能直接把纯需求完整处理入口当作生成流程的前置入口调用。

#### 建议一：扩展路由，而不是增加管理 Agent

在现有路由合同中增加 `prepare_requirements` 布尔字段，表示完成最终操作前是否需要运行需求整理阶段。字段名是本轮建议，尚未实现。

示例：用户说“两个人，总预算 500 元，帮我安排一天”，路由输出可为：

```json
{
  "intent": "planning",
  "action": "generate",
  "scope": "",
  "user_quote": "两个人，总预算 500 元，帮我安排一天",
  "question": "",
  "prepare_requirements": true
}
```

`intent/action/scope` 表示最终业务操作，前置标志只说明处理步骤。main 不负责同时提取整份需求。路由模型也不输出任意 Agent 列表；程序按白名单映射允许的组合。纯需求仍映射到一次 requirements，不能因标志重复运行。

例：“生成路线”且不含新需求，标志为 false；“修改预算并重排”是 revision/modify 加 true；“只记住不吃辣”只执行 requirements；假设咨询不创建需求补丁。原有 query、解释和确认语义继续保留，不因本轮聚焦四分支而删除。

严格 Schema、主提示词、路由校验及测试必须一起更新。旧格式混合路由不能无条件补 false 后同时撤掉业务角色的需求工具，否则会静默遗漏变更；迁移阶段应保留明确的旧流程适配，直到各入口完成转换。

#### 建议二：在 Runtime 中增加有限的阶段编排

在分类和最终业务执行之间加入编排方法，例如 `execute_workflow()`。这是建议名称，不是已存在的方法。它负责：

1. 保存最终路由、原始用户消息、原需求版本与计划快照，不被前置阶段覆盖。
2. 按需在同一个 Runtime 中运行 requirements；使用现有校验及候选补丁机制。
3. 需求处理失败或需要澄清时停止，不把未理解的变更忽略后继续规划。
4. 前置处理完成后，对需要生成的操作执行程序化的必要条件检查；requirements 阶段完成不等于可以生成。
5. 通过检查后调用 planning 或 revision，向其提供原始请求、最新候选需求和本次操作目标；不把需求 Agent 的自然语言回复当作新的用户指令。
6. 整轮只形成一次对外结果，交回 Store 按原边界提交。两个阶段之间不写一条“已保存”的聊天回复，不创建第二个业务任务。

仅说明职责的伪代码，以下辅助方法不是现有接口：

```python
def execute_workflow(route, turn):
    target = resolve_authorized_target(route, turn.workflow_state)
    check_cancelled_and_budget()

    if target.is_requirements_only or route.prepare_requirements:
        step = run_requirements_phase(turn)
        if step.failed or step.needs_input:
            return finalize_turn(target, step, turn)

    if target.is_requirements_only:
        return finalize_requirements_turn(turn)

    gate = check_action_prerequisites(target, turn)
    if gate.needs_input:
        return finalize_turn(target, gate, turn)

    check_cancelled_and_budget()
    result = run_business_phase(target, turn)
    return finalize_turn(target, result, turn)

# Store 在 Runtime 返回之后统一检查并提交；不是以上阶段直接写库。
```

阶段结果至少要区分完成、待澄清和失败；可复用现有 `needs_input/failed` 等字段的语义，不需要引入通用多 Agent 消息总线。是否完成由结构化状态和工具校验共同判断，不通过扫描自然语言中的“完成”判断。技术失败不能当成缺信息；最终结果为过期或取消时不得提交。

#### 建议三：分开阶段结果和整轮结果

现有纯需求流程包括结束整轮、处理等待状态等逻辑，不能简单执行两次完整 `execute_route()`。需求作为前置阶段时只返回阶段状态，不清理最终生成目标、不触发保存或展示。

统一结束逻辑以最终目标决定：

- 生成目标因必要信息或阻塞歧义暂停：保留 `awaiting_generation` 与澄清上下文。
- 生成成功：消费等待目标。
- 本轮明确“只记录/先别生成”或撤销：清理生成授权。
- 单纯闲聊、假设咨询或无关查询：不能因为字段已齐就恢复生成；是否保留等待状态沿用明确的业务规则。
- 失败：保留可恢复结果并提示，不自动重跑；合法独立需求补丁能否保存继续遵守原规则。

跨轮续接应同时检查“本轮在回答哪次澄清”“原目标是否仍有效”和“本轮是否撤销”。不以 `awaiting_generation=true` 一项条件强制规划。已有状态可以先用于生成；将来如需修改流程跨轮续接，还须绑定待修改的计划目标，不能借用生成标志冒充修改授权。

#### 建议四：共享候选状态和预算，隔离角色权限

- 同一业务任务、同一 Runtime、同一共享预算与取消回调；换角色不重新获得一整份调用次数或时间。
- 原始用户消息、原需求版本和预期计划快照不可变；候选需求可以由需求阶段更新，供后续角色读取。
- 每个角色有自己的提示词与模型消息，不共享另一角色完整的内部对话或推理内容。
- 在已迁移的新组合流程中，planning/revision 不再获得独立需求写权限，避免重复提取；程序直接标明需求审阅状态并调整原来的检查/补查规则。仅删提示词或仅删工具都不够。
- 规划发现新的冲突时返回澄清，不擅自修改需求，也不形成 requirements 与 planning 之间无限往返的循环。
- 需求变更保存在候选状态；原始版本标记仍用于最终并发检查，不能被候选版本覆盖。需求成功而规划失败时，保持旧行程，仅按现有规则提交合法独立需求变更，回复须反映实际提交结果。

#### 建议的最小实施顺序

1. 先统一“聊天生成 + 需求前置”路径，验证纯生成、混合生成和待补充续接；暂不同时重写所有角色。
2. 复用到混合修改，覆盖局部行程意见不写成全局偏好、修改范围绑定及原文精确编辑。
3. 处理更新后查询等已有组合语义，保留只读查询、解释、确认、取消及页面直达入口。
4. 全部入口迁移并测试后，再撤掉遗留的业务角色需求写入分支；不长期维持两套无区分的写入入口。

主要改动位置：`agent_roles.py` 的路由 Schema/权限、`prompts/agents/main.txt` 的目标识别、`agent_runtime.py` 的阶段执行和结果封装、需求/规划/修改提示词及相关测试。Store 以复用统一提交为主；若阶段结果暴露出需要补充的传递字段，再做最小适配，不另建持久化通道。

#### 最低验证清单

- 同一消息更新需求并生成：顺序为 main → requirements → planning；规划读到新需求，只有一次最终提交。
- 已保存需求下纯生成：不多跑需求角色；页面直达生成维持明确入口。
- 只补充、假设咨询、只改某站：不误生成、不越权改变全局需求。
- 需求有阻塞歧义或处理失败：不运行规划；已明确且合法的独立部分按既有规则处理。
- 补充此前的生成缺项：恢复正确目标；撤销、无关消息、过期任务不误续接。
- 两阶段共享调用预算；超时、新消息替代、计划或需求版本变化都阻止旧结果提交。
- 规划失败保留旧方案；纯需求不触发展示，成功生成才沿用原有后台展示链路。
- 单独统计离线程序正确性与真实模型的路由准确率、调用次数和耗时。

### 2026-10-16 · 重新设计路由输出：先明确本轮操作合同

#### 用户目标与本轮范围

用户提出重新规划路由输出。继续使用现有意图识别节点，不新增分类器或管理 Agent。本轮先提出容易理解的核心字段草案，尚未确定实施，也不是覆盖所有跨轮控制的最终上线协议。

#### 助手推荐的四个核心字段

```json
{
  "action": "generate",
  "prepare_requirements": true,
  "scope": null,
  "question": null
}
```

- `action`：用户本轮最终希望完成的操作，不是要调用的 Agent 名称。
- `prepare_requirements`：本轮是否需要需求角色理解、校验明确或待澄清的需求变更。它不表示“字段已补齐”或“补丁已经保存”。
- `scope`：仅行程修改使用 `item` / `all`，其他操作为 `null`；不让模型输出计划 ID 或自创目标。
- `question`：操作意图或目标含糊时给出的澄清问题；没有则为 `null`。非空时暂停业务执行。意图已知而仅需求字段含糊时，交给需求角色澄清，不由 main 提取字段。

建议将原先 `intent + action` 合并为一个最终动作字段，减少相互矛盾的组合。候选动作保持现有能力：`chat / query / record / generate / modify / explain / confirm / cancel`。确实无法选择动作时可令 action 为 null，但必须提供 question，程序不能默认补成 generate。

`record` 表示只整理和记录需求，prepare_requirements 必须为 true；该组合仅运行一次需求角色。`generate/modify/query` 可按任务需要选择是否前置需求。`chat/explain/confirm/cancel` 不夹带需求写入；遇到复合操作应使用已明确支持的组合或澄清，不能悄悄丢弃其中一部分。

#### 程序映射

| 输出 | 对应执行 |
| --- | --- |
| chat，前置为 false | 闲聊节点 |
| query，前置为 false | research |
| query，前置为 true | requirements → research，替代混合查询借用 planning 的表达 |
| record，前置为 true | requirements，完成后结束 |
| generate，前置为 false | planning |
| generate，前置为 true | requirements → planning |
| modify，前置为 false | revision |
| modify，前置为 true | requirements → revision |
| explain，前置为 false | revision 的只读解释 |
| confirm，前置为 false | 程序绑定当前计划执行确认 |
| cancel，前置为 false | 程序取消待生成目标，不删除需求或当前行程 |

映射不是模型提供的步骤列表，由 Runtime 固定控制。前置阶段失败、需要澄清或生成条件不满足时，不进入后续业务阶段。

#### 三个核心示例

- “两个人，总预算500元，帮我安排一天”：generate + true。
- “两个人，总预算500元，先记着”：record + true。
- “按已经保存的设置生成路线”：generate + false。

“预算改成800元并整体重排”为 modify + true + scope=all。假设咨询不写入需求；某站的局部调整不自动变成全局偏好。

#### 原字段的去留

- `intent`：在本草案中移除，角色由最终 action 和前置标志映射。
- `action`：保留并展平为业务操作。
- `scope`：保留，但不再使用空字符串或 explain 作为范围。
- `question`：保留。
- `user_quote`：建议不再由路由模型重复输出整条原话，而由程序从本轮真实消息附入不可变请求上下文。这不取消需求工具或精确编辑的原话依据校验；改变的是可信来源的传递方式，不是删除授权保护。

#### 尚需单独确定的跨轮控制

四字段能表达本轮主操作及需求前置，但不是完整的跨轮状态协议。待生成目标的恢复、撤销、保留及绑定必须在实施前明确定义，尤其是“先别生成，查一下天气”这种取消旧目标并执行查询的复合请求，不能仅凭 query 动作推断是否撤销。

下一步应决定如何给出受限的等待目标控制信号（例如独立的 keep/resume/cancel 字段），以及程序如何根据已有目标、当前原话与版本状态校验；不将其隐藏进自然语言回复，也不依赖第二次意图识别。本轮先讨论主操作的字段设计，未决定最终字段数量。
