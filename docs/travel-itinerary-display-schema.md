# 行程展示字段 v1

本协议已接入结构化 LLM、当前行程保存与前端。核心布局为按天时间线与活动卡片。规划、修改仍先输出完整文字，后面的无工具 LLM 从原文提取 JSON，程序校验并与原文绑定到当前行程。

- [合成示例原文](travel-itinerary-display-example.txt)

## 每日行程

| 字段 | 类型 | 含义与展示 |
| --- | --- | --- |
| `date` | 日期字符串或 `null` | `YYYY-MM-DD`，用于日期导航。原文只有“第N天”时，程序可依据当前行程依据的日期窗口映射；不能由模型猜年份 |
| `label` | 字符串 | “第1天”等标签，保持原文顺序 |
| `theme` | 字符串或 `null` | 当天主题，没有则不显示 |
| `items` | 卡片数组 | 按原文顺序展示活动；没有明确安排时为空数组，不编造活动补齐 |

## 活动卡片

| 字段 | 类型 | 含义与展示 |
| --- | --- | --- |
| `time_text` | 字符串或 `null` | 原文时刻、时段或相对时间，如“14:00–15:00”“午后”“抵达后”。为空时显示“时间待明确” |
| `title` | 非空字符串 | 活动名称 |
| `category` | 枚举 | 决定卡片图标与样式：活动、用餐、交通、住宿、休息、其他 |
| `location` | 字符串或 `null` | 地点、区域或原文明示的起终点文字；不自动绑定真实 POI |
| `duration_text` | 字符串或 `null` | 原文明示的时长，保留“约”“估算”等措辞；时段不等于交通耗时 |
| `description` | 字符串或 `null` | 活动说明、交通方式、路线文字或用餐安排 |
| `cost_text` | 字符串或 `null` | 费用说明，保留人均/总额、预留、估算、分配上限或待确认等口径 |
| `notes` | 字符串数组 | 预约、开放、饮食与其他备注；没有则为 `[]` |

卡片类别：

| 值 | 展示类型 |
| --- | --- |
| `activity` | 景点与活动 |
| `meal` | 用餐 |
| `transport` | 交通路段 |
| `accommodation` | 住宿安排 |
| `rest` | 午休、休息或自由活动 |
| `other` | 无法明确归类的其他安排 |

交通、用餐和住宿也使用同一套卡片字段，由类别切换图标和样式。交通路线、交通方式及推荐菜可以放在 `description`，原文中的时间、地点和费用放在相应字段。v1 不要求模型输出不同类别的嵌套对象。

示例卡片：

```json
{
  "time_text": "午后",
  "title": "午休 / 自由活动",
  "category": "rest",
  "location": null,
  "duration_text": null,
  "description": "午休或自行活动，不安排额外景点。",
  "cost_text": null,
  "notes": ["具体地点与时长未明确。"]
}
```

“午后”保持为原文表达，不转换成猜测的14:00。没有时长就使用 `null`，不能根据页面时间范围声称已经核实交通耗时。

## 外层展示块

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| `schema_version` | 固定字符串 `1.0` | 展示协议版本，不是行程版本 |
| `title` | 非空字符串 | 行程标题 |
| `overview` | 字符串或 `null` | 原文整体安排说明 |
| `budget_note` | 字符串或 `null` | 原文预算安排说明，保留费用范围与估算口径 |
| `days` | 每日行程数组 | 日期与活动卡片 |
| `preparation.clothing` | 准备事项数组 | 衣物与装备建议，每项为 `title` 和可空的 `body` |
| `preparation.accommodation` | 准备事项数组 | 住宿说明，保留“建议区域”“酒店待确认”等原文状态 |
| `pending_items` | 字符串数组 | 原文明示的待确认事项 |
| `risks` | 字符串数组 | 原文提醒与风险 |

Schema 中每个字段的键都需要输出；未提供的文本为 `null`，没有内容的列表为 `[]`。固定键有利于模型约束与前端读取，不意味着模型可以补齐未知内容。

预算金额、人数和抵离信息属于程序保存的需求数据；工具证据属于原始查询记录。结构化 LLM 只输出上述展示块，不负责生成或改写这些主数据。

## 程序负责的原文与依据

- 行程ID、需求依据、卡片ID、原文指纹、转换状态和工具证据由程序管理，不接受结构化 LLM 自行生成。
- 概览中的人数、预算和抵离信息应与行程依据的需求快照对应。当前需求变化时，保留已有的“行程尚未按新需求更新”提示，不把新需求伪装成旧行程的依据。
- 原文与有效展示 JSON 一起替换当前行程；确认保持对应关系，修改产生新原文后重新转换。只保留最新版，不保存历史行程。
- 转换结果必须属于本次原文；新消息作废旧轮、需求或行程快照变化时，不能回写迟到的原文或 JSON。
- 转换失败或结构校验失败时展示原文，仍可保留有效文字行程；待补充、业务失败回复不进入转换节点。
- 地点文字不等于可信 POI。地图与路线数据只能来自实际工具记录及程序校验后的绑定。

## 转换与验收规则

结构化 LLM 只接收本次完整文字及程序提供的必要日期依据，不读取旧聊天恢复需求，不查询外部资料，也不重新规划。保持日期、活动顺序、用户限制、估算与待确认事项；信息不明确就保留未知。

程序先检查 JSON、字段、类型和原文关联。日程内容与原文是否一致属于后续验收；JSON Schema 通过不代表事实、费用、时间或修改范围已经被完整证明。

本稿准备了一个两天、五张卡片的合成原文与对应 JSON，包含三种常见转换边界：模糊“午后”不补具体时刻、预留时段不冒充交通耗时、费用预留不冒充真实报价。

## 创建页的已确定规则

创建行程只填写五组必填信息：旅行城市；起止日期；抵达及离开时间与地点；总人数；预算金额、总额/人均口径和费用范围。时间按旅行城市当地时间填写。

程序检查必填与格式、日期顺序、当天离开晚于抵达、人数为正整数、预算金额有效。创建后保存为有效需求。偏好、忌口、必去和其他限制在聊天中补充。规划 Agent 检查这五组是否完整与一致；齐全不等于预算与现实安排必然可行，仍需在规划中判断。
