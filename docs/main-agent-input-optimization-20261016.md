# Main Agent 输入精简设计

- 日期：2026-10-16
- 状态：**第一阶段已实施：`task_execution` main 使用确定性六块决策投影；legacy、专业能力完整快照、工具合同和提交链不变。真实模型对照尚未运行。**
- 范围：新 `task_execution` 策略下的 `main_execution`，不改旧 `legacy/main` 的分类合同。
- 本次第一阶段交付：新增 `app/main_input.py` 确定性投影并接入 `task_execution` 的 `_initial_context()`；新增8项纯离线投影测试；不修改模型配置、执行策略默认值、工具参数、提交协议或页面布局。
- 关联：[主任务执行架构设计](agent-task-execution-design-20261016.md)、[主任务执行实施记录](task-execution-implementation-20261016.md)。新任务执行架构已有实现，本文讨论的是在此基础上的输入优化，不应混淆两者状态。

## 1. 结论与目标

**Main 不需要完整执行上下文，只需要足够做下一步决策的上下文。**

当前输入同时包含语义信息、存储结构和提交校验元数据。应该把它们分开：

- **决策上下文**：给模型，用于理解请求、关联目标、选择能力、处理结果和结束本轮。
- **执行上下文**：留在 Runtime，包含身份、版本、授权来源、完整需求、完整行程、候选、证据和预算。

```text
完整执行快照（服务器保留）
        │
        ├── 确定性投影 → 紧凑决策上下文 → main
        │                                   │
        ├── 完整上下文 → 专业能力 ←──────────┤
        │                                   │
        └── 校验、候选管理、提交 ←───────────┘
```

这里的“投影”是程序选择和整理字段，不新增摘要模型，不新增按问题分类的上下文路由器。

优化目标不是单纯减少首包 token，而是：

1. 减少重复、无决策价值的信息。
2. 保留条件、否定、指代、跨轮追问和授权范围所需的信息。
3. 不削弱 Runtime 的校验和提交保护。
4. 在任务质量不下降的前提下，降低整轮输入量、成本或耗时。

## 2. Main 的职责决定它需要什么

Main 主要回答五个问题：

1. 用户这轮想完成什么？
2. 这句话在回答哪个问题，或者继续、取消哪个目标？
3. 下一步调用哪个能力？
4. 能力返回后，应该继续、换方法、澄清还是结束？
5. 哪些候选是用户授权范围内应当采用的结果？

因此，不能把输入退回“用户原话 + 工具列表”。城市、住宿、当前方案、未完成目标和活动追问，仍然可能直接影响上述判断。

但 main 通常不需要理解 `workflow_revision=17` 或某个正文哈希。模型只要引用服务器提供的对象，版本和权限由服务器检查。

**隐藏校验字段不等于删除校验；减少模型可见数据也不等于缩减专业能力的可用上下文。**

## 3. 当前输入基线

以下描述以编写本文时的工作区源码为准，不代表某个运行实例已启用新策略。

### 3.1 请求由四部分构成

1. `system`：`main_execution` 提示词；city 模式追加同城规则。
2. 首条 `user`：JSON 字符串形式的初始上下文。
3. `tools`：九个工具的完整描述和参数 Schema，作为请求参数发送。
4. 后续 `assistant/tool`：本轮工具调用和观察结果，逐步追加。

首次动态上下文有八个顶层键：

```text
request_context
current_date
requirements
missing_requirements
plan
recent_chat
workflow_state
budget
```

核心构造在 [task_runtime.py](../app/task_runtime.py) 的 `_initial_context()`；工具在 [agent_roles.py](../app/agent_roles.py) 的 `EXECUTION_TOOLS`。

### 3.2 当前值得优化的部分

- `request_context`、需求 `basis`、需求自身字段等位置重复携带 revision 和行程身份。
- 需求同时包含规范化字段与 `trip.destination/date_range/budget/style` 等兼容或展示字段。
- 当前原话既在 `request_context.body`，也可能出现在 `recent_chat`。
- 当前行程只截取正文前 600 字；这不是可靠的行程摘要，可能只有准备事项和第一天内容。
- `workflow_state` 发送完整规范化任务记录，包含模型不必理解的序列、版本和内部引用数组。
- `budget` 是首包快照，同轮不会自动刷新。
- 初始 JSON 同轮不重建；后续只追加观察结果，累积消息没有自动摘要压缩。

当前子能力向 main 返回摘要、候选引用和证据引用，不返回全部内部消息。这个方向应保留。

## 4. 字段取舍

| 当前信息 | 处理建议 | 原因与边界 |
|---|---|---|
| 本轮完整原话、消息引用 | 保留一份 | 不截掉否定、条件和范围；引用用于定位来源 |
| 日期、city/travel 模式 | 保留 | 影响相对日期解释和需求规则 |
| 已保存需求 | 合并为单一规范化视图 | 保留有意义的值，不重复发送展示包装 |
| 生成所需缺项 | 保留 | 程序计算；明确不限制闲聊和只读查询 |
| 行程引用、标题、状态 | 保留 | 用于判断有无当前方案、选择修改或确认 |
| 行程前 600 字 | 替换 | 优先可靠目录；没有则只给元信息，详情按需读 |
| 最近聊天 | 先保留窗口，按消息 ID 去重 | 第一阶段不同时激进缩短历史，以免失去指代 |
| 活动追问 | 保留问题、任务引用、答案用途 | 防止“500”被误写成总预算 |
| 未完成目标 | 保留语义投影 | 目标、状态、阻塞项、约束和必要进度不能丢 |
| 终态任务完整记录 | 默认不发送 | 可按需读取；最近取消/失败等必要结果不能因此消失 |
| revision、hash、sequence、epoch | 留在服务器 | 模型不负责并发控制和真实性判断 |
| owner、内部执行身份、完整引用链 | 留在服务器 | 只向模型暴露完成操作需要的对象引用 |
| 精确预算计数 | 默认不发首包 | 程序强制限额，临近上限时给简短收尾反馈 |

### 4.1 需求规范化规则

- 以当前有效的 `TripRequirements` 为主要来源，保留必要的 `note`、模式和住宿语义信息。
- 去掉重复展示字段前，先确认其含义是否已被规范化字段覆盖；不能因为名称相似而丢掉独有信息。
- 空值可省略，但 `0`、`false`、明确清空等不能按通用“假值”规则删除。
- 初始状态可约定“省略表示未记录”；增量更新必须显式表达设置与清空，不能使用同一省略语义。
- 列表如必去、避开、忌口，不能未经验证截取前几项。
- 住宿通常向 main 提供名称、地址、城市和位置确认状态；坐标、POI 元数据由专业能力使用。需要精确细节时仍可读取。
- 不为需求生成另一份 LLM 摘要，避免把用户限定条件改写丢失。

### 4.2 任务投影规则

默认提供未完成目标，即 `active / waiting_user / suspended` 任务的紧凑视图：

- 任务引用、目标、效果类型、状态；
- 尚未完成的事项、必要进度；
- 挂起或等待的语义原因；
- 条件、否定和授权范围中的关键限定。

活动追问单独保留 `question_ref / task_ref / text / answer_target`。

以下信息不得因压缩而丢失：

- “只有下雨才修改”，不能只剩“修改行程”；
- “只查询，不保存”，不能只剩“查询酒店”；
- “原需求已变化，需要重新确认”，不能只剩“继续生成”。

程序依据版本得出的失效状态，可投影为 `requires_reconfirmation` 及简短原因，而不暴露原始哈希。

任务 goal 如果缺少必要限定，应保留对应来源片段或按需读取原消息；不能让摘要凭空补足。取消、失败等终态中的重要结果，应由最近对话或简短结果记录保留；涉及部分完成时，不能把整个目标粗暴地从上下文删除。

## 5. 建议的目标结构

首包收敛成六块。以下是**建议接口示例，不是当前已有 Schema**；示例值为合成数据。

```json
{
  "message": {
    "ref": "message-current",
    "text": "500，只查酒店，先不生成行程"
  },
  "environment": {
    "current_date": "2026-10-16",
    "mode": "city"
  },
  "requirements": {
    "known": {
      "city": "杭州",
      "dietary": ["不吃辣"],
      "lodging": {
        "name": "当前住宿",
        "address": "已保存的住宿地址",
        "location_confirmed": true
      }
    },
    "missing_for_generation": []
  },
  "current_plan": {
    "ref": "plan-current",
    "title": "杭州同城游玩",
    "status": "草案",
    "outline": null
  },
  "conversation": [
    {
      "ref": "message-question",
      "role": "assistant",
      "text": "酒店每晚预算是多少？"
    }
  ],
  "task_context": {
    "focus_task_ref": "task-hotel",
    "open_tasks": [
      {
        "ref": "task-hotel",
        "goal": "查询住宿附近的酒店候选，不保存为正式旅行需求",
        "effect_kind": "read",
        "status": "waiting_user",
        "unresolved_items": ["酒店每晚预算"]
      }
    ],
    "active_question": {
      "ref": "question-hotel-budget",
      "task_ref": "task-hotel",
      "text": "酒店每晚预算是多少？",
      "answer_target": {
        "namespace": "hotel.search",
        "field": "nightly_budget"
      }
    }
  }
}
```

说明：

- 引用仍由服务器生成和验证，模型不能靠编造引用获得权限。
- `current_plan` 无当前行程时可为 `null`；是否有效由服务器判断，不靠标题猜测。
- `outline` 只使用与当前正文匹配的可靠结构；不是必须字段，不为补齐它新增模型请求。当前实现优先结构化 `TripPlan.days`，无合法计划日期时不使用 display 衍生目录。
- 活动追问和焦点可以为空；多个未完成目标不能仅因不是焦点就全部隐藏。
- 任务可按需要包含必要进度、限制、挂起原因；示例不代表只允许展示这些少数字段。
- `message` 与 `conversation` 按消息 ID 去重，不按相同文本去重。用户两次发送相同内容仍可能是两次独立请求。
- 最近聊天第一阶段继续沿用现有窗口；更短窗口是否可行，单独评测，不与字段精简混在一起归因。

## 6. 行程信息与按需读取

### 6.1 替换固定正文截断

当前“正文前 600 字”不保证覆盖所有天，也不保证包含对用户问题有用的信息。

建议优先提供：

```text
标题：杭州三日游
状态：草案
目录：
- 第一天：西湖周边
- 第二天：灵隐寺及附近街区
- 第三天：市区慢游
```

目录来自与正文版本匹配的现有结构，或可靠的确定性标题提取。不匹配、正在生成、结构不完整时回退为“引用 + 标题 + 状态”，而不是猜测内容。

不等待异步 display，不用旧 display 冒充当前行程，不在 main 前增加摘要 Agent。用户涉及具体安排、理由或精确修改时，读取完整正文。

### 6.2 保留现有 read_context 作为补充入口

可按需读取需求、较早消息、当前行程、想法、证据和任务。模型能看到的精简首包，不改变专业能力可使用的完整快照。

需要注意当前实现边界：

- `read_context("plan")` 获取当前行程快照，不是新候选全文。
- 当前没有通用 `read_context("artifacts")` 接口。
- 当前 `read_context("evidence")` 不是按 workspace 的任意 evidence_ref 展开全部原始结果的接口。

本次精简不能假定这些能力已经存在。如果评测表明 main 必须查看某份新证据，应另行定义受引用校验、范围和长度约束的读取接口，而不是直接暴露整个工作区。

为防止按需读取又把冗余全部带回，可对 main 的读取结果做独立投影；不要直接删改专业能力共用的底层 `read_context()` 返回合同。

## 7. 工具定义和增量观察也要精简

### 7.1 工具 Schema

九个工具的 Schema 每次都会参与输入，仅压缩初始 JSON 不代表已经解决全部输入开销。

第一阶段保留现有九个工具和参数合同，先精简说明文字：

- 通用授权、候选不自动保存、单步单工具等规则放在系统指令。
- 工具描述集中解释用途、何时调用和特有约束。
- 参数保留类型、必填和枚举等可验证约束，不因省 token 删除校验。
- 任务引用、修改范围、候选选择和条件语义仍由模型明确表达。

服务器可唯一确定的机械参数可以不暴露给模型，但改变参数 Schema 属于后续独立变更，需更新校验和测试。不能把存在歧义的任务或授权目标改成服务器盲猜。

不新增“复杂问题给多工具、简单问题给少工具”的分类层，不枚举复合意图组合。

### 7.2 能力结果

继续使用 `status / summary / artifact_refs / evidence_refs / completed_items / unresolved_items / input_request / error` 这一结构化方向，不回传子 Agent 完整内部对话。

摘要必须足够支持下一步决策。例如“降雨概率超过 60% 才修改”，结果至少应表达查询日期、城市、实际概率和证据引用，不能只有“查询完成”。

条件写入依然由程序根据原始证据和适用范围验证，模型摘要不是事实或授权证明。`unknown` 不能压缩成“不满足”，也不能因此授权修改。

### 7.3 同轮状态变化

当前首包是固定快照，不能在提示词中把它描述成始终实时。

建议维持“首包 + 增量观察”的结构：

- 需求候选返回必要的变更结果，区分候选与已保存状态。
- 任务操作反馈更新后的目标状态，不能只有模糊的成功标记。
- 新证据返回支持下一步决策的事实。
- 必要时按需重新读取，最新有效工具结果优先于旧首包。

精确预算留给 Runtime；临近上限时通过简短程序反馈要求收尾。超过限制后仍由确定性失败收尾逻辑处理，不能依赖模型自觉遵守。

## 8. 实施顺序与代码落点

### 阶段一：只做上下文投影

主要落点：[task_runtime.py](../app/task_runtime.py) 的 `_initial_context()`、main 专用读取投影，以及 [main_execution.txt](../app/prompts/agents/main_execution.txt)。

- 拆分模型可见视图与完整执行状态。
- 去掉机械版本元数据、重复需求包装和当前消息重复。
- 提供任务语义投影，完整保留活动追问和必要限制。
- 调整行程预览策略。
- 保留原工具数量、参数合同、专业能力输入、提交逻辑和历史窗口。

第一阶段不需要数据库迁移，不改持久化 workflow Schema。新增投影函数应为无网络、无模型调用、不修改原对象的确定性函数。

### 阶段二：精简重复说明和观察结果

落点：[agent_roles.py](../app/agent_roles.py)、主提示词、`_result_output()` 及对应测试。

- 减少重复说明。
- 补齐会影响后续决策的事实和状态反馈。
- 如果确需减少工具参数，单独提交合同变更并验证，不与纯文字精简混在一起。

### 阶段三：隔离对照评测与启用

- 在相同 `task_execution` 执行链内比较“原输入视图”和“精简视图”。
- 固定模型、思考设置、专业能力提示词、工具数据和代码版本；本轮不同时切换 main 模型。
- 先离线检查，再经单独批准运行真实模型评测。
- 如需切换，版本固定在一次执行任务内，不在同轮中途来回更换输入合同。
- 回退只恢复原输入投影，不回退到 legacy 意图分类，也不删除新任务状态和提交保护。

## 9. 验收标准

### 9.1 确定性测试

至少覆盖：

- 原消息只去掉同 ID 的重复项，相同文本的不同消息仍保留。
- 空值省略不丢 `0 / false`，增量清空有明确表达。
- 条件、否定、假设、授权范围和未完成事项没有被投影丢失。
- 活动追问保留唯一任务和字段绑定，“酒店 500”不变成正式总预算。
- 已变化的依据被表达为需要重确认，不恢复旧授权。
- 取消、挂起和部分完成的目标不会被简化为仍可自动继续。
- 当前行程没有可靠目录时安全回退，不使用过期展示数据。
- main 输入不暴露无用内部元数据，但服务器版本、权限、幂等、提交校验全部仍执行。
- 专业能力仍获得需要的完整快照，旧 legacy 合同不受影响。
- 工具观察足以说明状态变化，初始快照不会被当作始终最新。

实施时增加输入投影专项测试，并覆盖主执行、跨轮任务及 Store 集成链路。具体可复用的测试以实施时工作区为准；本文校验时未找到此前对应的测试文件，不将它们视为当前已有覆盖，也不自动恢复用户删除的文件。

### 9.2 真实模型对照

依据[主任务执行实施记录](task-execution-implementation-20261016.md)中的评测覆盖要求，准备冻结的对照场景，重点观察多诉求、条件、取消、短答、指代以及超出最近聊天窗口的目标恢复。此前记录的 `main_execution_v1` 数据集在本文校验时未找到；实际运行前须核实或重新准备评测资产，不能把历史记录当成当前可直接运行的数据集。

分别记录：

- 首包各部分大小：system、上下文 JSON、工具 Schema；
- main 各次调用及整轮所有角色的输入/输出 token；
- 额外 `read_context` 次数、模型调用数、工具调用数；
- 整轮任务完成率、漏办/误办、错误绑定、条件判断、未授权写入；
- 端到端 p50/p95、超时和失败率。

发布判断：

1. 确定性保护测试全部通过。
