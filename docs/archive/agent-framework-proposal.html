设计结论：小内核，强业务，单一提交口

主 Agent 与四个专业能力共享一套运行引擎；模型提出行动，工具生成候选，程序决定哪些结果可以正式保存。

不重写成一个通用聊天机器人，也不建立固定的多 Agent 流水线。用户只问交通时，按需查询；用户补需求再要求规划时，按依赖串行执行。复杂度应放在真实的业务约束，而不是两套重复的循环与分发逻辑里。

从 Pi 学什么

  • 模型协议、Agent 循环、会话管理分层。
  • 工具定义、参数 Schema 与执行函数集中注册。
  • 应用消息与模型消息分离，显式构建上下文。
  • 用统一事件驱动进度，而不是解析日志文案。

不直接照搬什么

  • 不开放任意 shell、SQL 或网络请求。
  • 不默认所有工具调用都并行。
  • 不删除 Workspace / Commit 的业务保护。
  • 不为扩展性先造插件市场或分布式调度。
关键区分：“通用内核不懂旅行”，不等于“旅行没有规则”。权限、住宿闭环、条件授权、证据有效性和保存冲突全部保留，只是从循环细节中分离。

整体架构：每层只回答一个问题

应用入口Application Service

谁在对哪趟旅行发起什么请求？
鉴权、请求幂等键、任务创建、当前业务版本捕获。Web 只调用应用服务，不直接操作 Agent 内部对象。

本轮会话TurnSession

这次执行使用什么状态？
不可变请求权限、脱离存储的快照、预算、取消令牌、消息轨迹、候选工作区与事件通道。

通用执行内核AgentRunner

怎样完成一轮模型与工具协作？
上下文准备 → 完整模型响应 → 工具预检 → 工具执行 → 结果回填 → 继续/结束。只依赖接口，不导入 Trip、住宿或天气规则。

旅行领域能力Travel Domain

什么行动符合这次授权？
需求、查询、规划、修改四种配置；旅行工具、候选校验、地点证据、条件判断与范围保护。能力可复用 Runner，但没有直接数据库写权限。

模型执行到此结束 · 业务候选不等于已保存
工作区终结器Workspace / Finalizer

本轮究竟选择哪些结果？
先校验完整采用集合、依赖和追问，再一次性封装不可变 TerminalProposal；无效选择不能留下半采用状态。

原子提交服务CommitService

这些结果现在还能保存吗？
重新校验 owner、请求代次、计划/需求版本和授权；同一事务写业务效果、消息、任务状态及提交回执。提交失败不发布半成品。

一个 Session，不是一个巨大的全局对象

TurnSession  # 每次用户请求独立建立
├── authority       # owner / trip / request / sequence / 业务版本
├── snapshot        # 本轮读取基线，与实时存储隔离
├── transcript      # 本轮模型消息、工具调用与结果
├── budget          # 整轮额度；子能力领取受限子额度
├── cancellation    # 取消与新消息替代信号
├── workspace       # 候选、依赖、证据和选择
└── events          # run_id / parent_run_id / sequence

子能力获得受限 CapabilityContext，不把整个 Store、密钥或主 Session 的任意修改权交给工具。Session 的“执行状态”与跨轮“业务任务状态”分开。

一套引擎，多个能力：复用机制，不混用权限

保留主 Agent 的决策职责和四个专业能力，但抽出相同的模型调用、参数校验、协议配对、异常归一化与预算检查。不是把所有提示词合并，也不是让一个模型无边界处理所有事。

目标角色配置；不是当前代码已完成的重构
角色主要工作工具范围合法结束结果
Main理解任务、委派、取舍、选择结果11 个主工具，见下一节答复/追问 + 最终候选选择
Requirements整理当前授权的正式需求上下文、需求变更、前提检查需求候选或结构化缺项
Research回答具体事实问题上下文、地点/天气/路线/餐饮查询证据、未知或服务不可用
Planning形成完整同城安排上下文、前提检查、只读查询行程候选或缺项/冲突
Revision在授权范围内修改当前方案上下文、只读查询、受限精确编辑修改候选或缺项/冲突

通用循环的目标形状

# 目标伪代码：表达职责，不是可直接运行的实现
while policy.may_step(session):
    request = context_builder.prepare(session, profile)
    response = model_adapter.complete(request, budget=session.budget)
    transcript.accept_complete_response(response)

    if response.tool_calls:
        plan = executor.preflight(response.tool_calls, context)
        results = executor.execute(plan, context)
        transcript.append_tool_results(results)
        decision = finalizer.after_tools(results, session)
    else:
        decision = finalizer.after_answer(response, session)

    if decision.ends_run:
        return decision.outcome

return finalizer.stop(reason="budget_or_step_limit")

Runner 处理模型轮次，Finalizer 决定领域合法的结束条件。Main 必须明确候选采用和追问；专业能力必须交结构化完成结果。不能因为模型输出了普通文字，就默认任何角色都成功结束。

两种循环，两个结束合同

Main Runner
  └── draft_itinerary 工具
        └── Planning Runner（同一个引擎，不同 profile）
              ├── search_places
              ├── query_route
              └── complete_capability → 返回行程候选
  └── finish_turn → 返回本轮终止提案

之后：CommitService → 业务提交回执
不会固定跑完五个角色。“需求 → 查询 → 规划 → 修改”不是流程模板。能力由当前任务按需选择；子能力默认不能递归创建任意 Agent，避免无限委派与预算失控。

工具注册：名称、Schema 和实现直接关联

现在工具定义与实现分散，靠 if name == 'read_context' 人工对应。目标不是消灭所有条件判断，而是把“注册一个工具”变成单一动作，避免 Schema 与执行逻辑漂移。

# 目标接口示意：绑定规则与实现
registry.register(ToolSpec(
    name="read_context",
    description="读取当前旅行的受限上下文",
    parameters=ReadContextSchema,
    execute=read_context,
    effect="read_only",
    execution="parallel_safe",
    allowed_roles={"main", "requirements", "research", "planning", "revision"},
))

# 执行链：预检必须通过，才可执行
spec = registry.require(call.name)
args = spec.validate(call.arguments)
policy.authorize(spec, args, capability_context)
budget.claim(spec.cost)
result = spec.execute(args, capability_context)

Schema 检查形状；Policy 检查身份、引用和授权；领域服务检查业务约束。三者不能互相替代。read_context 对不同角色仍使用不同投影，不因共享注册就暴露同样的数据。

完整主工具清单，不漏“补充需求”

主工具目标职责效果边界
read_context按需读取需求、消息、想法、计划、任务、证据只读、按角色投影与分页
manage_todos更新本轮事项清单本轮进度，不等于业务完成
manage_task管理跨轮任务、采用效果引用工作区变更，需最终提交
prepare_requirements委派需求能力，生成正式需求候选以本轮原话为授权，不直接保存
research委派查询能力，返回证据与未知外部只读查询，不写需求/行程
draft_itinerary按有效需求生成完整行程候选显式依赖需求与证据
revise_itinerary按当前计划引用和范围生成修改候选未授权内容不能顺手重排
confirm_itinerary为已交付的当前方案生成确认候选不是事实核验，也不能确认本轮未提交草稿
restyle_itinerary兼容现有纯展示调整入口仅 presentation；目标逐步改为有限主题参数
ask_user绑定任务与答案目标，关键追问并结束不在原地等输入；下一条消息开启新轮

专业层的 update_requirements / search_places / query_weather / query_route / complete_capability 不因此全部暴露给 Main。注册统一，角色工具白名单仍分离。

├── status             # ok / needs_input / unavailable / failed ...
├── model_content      # 模型可读的有界摘要
├── details            # 程序消费的结构化数据
├── artifact_refs      # 业务候选引用
├── evidence_refs      # 查询证据引用
└── error              # code / retry_policy / safe_message

# 把 recoverable=False 写给模型看，却仍允许相同调用无限重复。

可并行

同一批次起始快照上的独立只读查询。例：查 A 地点、查 B 地点、查天气。先串行预检与预占预算，允许的请求再有界并行；结果按源调用顺序入轨迹。

必须串行

需求整理后规划、地点选择后查路线、候选采用、工作流变更、确认和终止。混有状态变更的批次不自动并行；依赖结果的调用拆到下一步。

会话、上下文与事件：一份业务状态，多个受限视图

不要把“发给模型的消息”当业务数据库

持久化业务状态与本轮快照
          ↓ ContextBuilder
筛选 / 权限投影 / 分页 / 必要摘要 / 来源标记
          ↓ ModelAdapter
供应商消息、工具协议与完整响应归一化
          ↓ Model

UI 展示消息、内部诊断、密钥和数据库对象
不直接进入模型上下文。
  • 本轮原话：保留精确消息引用，旧聊天不是新授权。
  • 上下文压缩：必须保留任务目标、当前版本、授权依据、关键未知和完整工具调用/结果配对。
  • 证据：完整记录留在受控存储，模型默认读摘要，必要时凭引用读取详情。
  • 模型适配：不同接口的消息形状在适配层统一，不让业务能力直接访问供应商 SDK 对象。

新消息：首版只采用“取消旧轮，启动新轮”

不一开始同时支持复杂的 steering、follow-up 与执行中改写授权。新用户请求递增 sequence/epoch，旧轮合作式取消；外部请求无法及时停止时，迟到结果也不能提交。未来若增加排队消息，必须给每条消息自己的请求身份和授权边界。

统一事件，但关键处理与遥测分开

run_started
  model_started → model_delta* → model_completed
  tool_started → tool_progress* → tool_completed
  artifact_created
run_finalized        # 已产生提案，还没承诺保存
commit_succeeded     # 数据已保存，带 receipt_id
# 或 commit_rejected / commit_failed

每个事件包含 run_id / parent_run_id / sequence / event_index / timestamp；子能力可见其父运行。UI 直接订阅，不从“正在规划”一句话猜状态。trace 默认脱敏，不记录密钥；原始对话和输出设定保留策略。

不要让日志故障改变业务结果。UI 与遥测订阅失败只记录诊断，使用有界队列合并流式更新；真正影响提交的校验与持久化必须显式等待，不能藏在可选事件回调中。

候选工作区：模型有建议权，没有直接保存权

registered 已登记→ready 可提交→selected 最终选择→committed 已保存

需求候选、行程候选、确认候选、展示候选和任务候选采用统一引用机制。证据是支持材料，只能引用，不能作为正式业务写入 adopt。

终结器先校验整个集合，再一次性变更选择

  1. 验证引用与所有权

    候选属于当前请求，没有被新需求或新计划失效；引用来源由服务器生成，模型不能自报。

  2. 验证依赖与授权条件

    依赖新需求的行程必须同时选择该需求；hypothetical 不写入，unknown/not_satisfied 不写入。条件证据必须与城市、日期和判定一致。

  3. 验证组合与工作流

    最多一份最终行程；新行程不能与确认混合；展示与业务改写不混合。活动追问要消费、取消、挂起或明确替换。

  4. 封装不可变提案

    完整集合通过后，再更新选择状态并密封提案。任何验证失败都不留下半采用的新状态。

  5. 提交层重新验证并事务保存

    在状态锁/事务内复验请求代次和业务版本；计划、需求、消息、任务与回执一起保存。持久化失败则不发布新的内存业务状态。

部分完成必须是显式结果

例如：需求已整理，规划因地图超时未完成。

仅保留已经授权且明确标记为可独立保留的需求候选；不提交半份行程。返回 partial，用户看到“需求已保存，行程未生成”。只有收到提交成功回执后才能说“已保存”。

目标终止合同明确声明 on_failure=keep_if_independent 的保留策略；临时注册候选默认不保留。失败保留仍复验依赖和请求版本，不能让旧轮的独立需求覆盖新轮状态。

幂等不是“重复点一次再做一遍”

同一 owner/trip/request_id 返回同一任务或已保存回执，不再次执行提交。新意图使用新 request_id。进程重启后未完成模型轮标记 interrupted，不自动重放未知是否已经计费或执行完毕的调用；确定性状态可以从已提交快照恢复。

预算与终止：明确结束，不隐藏再调用

保留整轮共享预算，但把“预检”和“占用”做成不同操作，并把当前代码里分散的退出语义统一成 RunOutcome。

动作目标语义失败后的动作
check()只检查剩余时间、取消状态与可用额度停止新工作，不扣计数
claim()实际请求开始前原子占用次数与并发槽没取得额度就不能执行
child_lease()为子能力限定预算，隔离父级终止额度归还未用额度；已消费计数不清零
可选回复复核在进入终止前显式申请；界面和 trace 能看到必需复核失败则不发布未经复核答复，不暗中超额
本地终结/提交不需要再次调用模型；独立有界处理时限明确失败/冲突回执，不伪装成成功

额度至少覆盖模型尝试次数、工具执行次数、外部请求次数、时间与可选 token 限制。供应商兼容重试/限流备用也计入模型请求预算。截止时间应传递到网络层；取消不及时生效时仍禁止发布迟到结果。

终态与提交状态是两个维度

RunOutcome.status
  completed | needs_input | partial | failed | cancelled

RunOutcome 内容
  reply / question / selected_artifacts / unresolved_items / usage

CommitReceipt.status
  committed | rejected | persistence_failed

# 不能把 completed 直接显示成“已保存”。
# cancelled 也不能继续提交旧轮候选。

纠错次数必须真正约束程序

  • Schema/参数错误：有界反馈模型修正；相同无效调用重复达到阈值后，由程序停止，不只返回一句 recoverable=False。
  • 权限拒绝：当前操作禁止执行；不得通过改写相同请求绕过策略。
  • 网络失败：只按显式 retry policy 进行有限重试；不得重试会产生不明副作用的提交。
  • 预算耗尽：程序构造 partial/failed，不再要求模型“最后总结一次”。
  • 清单 needs_input：必须产生问题；pending 不能被改名成 done 来结束。
目标变化：结束工具也需要额度；父级终止调用、必需复核与结束工具必须一起规划预算。若没有足够额度，就使用确定性失败/部分完成模板。不存在“最后一次调用之后，再偷偷复核一次”。

走通一次请求：补充需求，再生成方案

合成示例 · 不代表真实执行

用户：“改成两天，不吃辣，按这个生成路线。”
前提：当前旅行已具备经地图确认的住宿和完整合法日期窗口。

  1. 应用入口创建请求

    校验用户拥有旅行；生成 request_id/run_id，捕获计划与需求版本。新请求使旧轮不能再发布结果。

  2. Main 看见受限上下文

    本轮原话、已知需求、当前方案和有效任务。模型决定先调用 prepare_requirements，不直接更新 Store。

  3. 需求工具委派同一 Runner

    Requirements profile 仅能读取和整理需求。用户“两天、不吃辣”经本地校验后形成 requirements 候选 R1；日期派生由业务规则处理，有歧义则追问。

  4. 候选回到 Main

    返回 R1、摘要与缺项；没有宣称“需求已保存”。Main 选择 draft_itinerary(requirements_ref=R1)。

  5. 隔离应用新需求，启动规划

    在能力快照中应用 R1，并将其标为符合条件时可独立保留。领取子预算，数据库仍保持旧需求。

  6. 规划按依赖查询

    独立地点/天气查询可以并行；地点确认后才能查询对应路线。证据由程序记录，未知营业、价格、预约仍保持未知。

  7. 返回完整行程候选 P1

    P1 依赖 R1，携带证据引用与想法处置结果。目标 guide 数据与可读正文同源；展示渲染不属于 Agent 内核。

  8. Main 请求结束

    完成本轮清单；finish_turn 选择 R1、P1 和必要任务效果。终结器先校验完整集合，再封装提案。

  9. 提交服务确认版本未变

    原子保存两天/饮食需求、完整方案、答复和任务回执。成功回执之后，UI 才显示“需求与行程已更新”。

情形运行结果保存结果
日期不明确needs_input，绑定具体问题与答案目标仅保存允许独立采用的内容与追问；不编造日期规划
规划中地图超时partial，说明未生成完整方案R1 符合保留策略时可提交；旧行程保留，依据变化可见
用户中途发送新要求旧轮 cancelled旧轮整份提案被代次检查拒绝；不借“部分保留”覆盖新状态
用户只问“去这个景点大概多久”，还需要全套流程吗？

不需要固定经过需求和规划。Main 可读取当前地点依据，委派一次 research 查询，基于实际结果答复；没有业务写入时最终选择集合为空。若起终点不明确则追问，而不是自动重排方案。

纯“把攻略字号变大”呢？

属于展示偏好，不是旅行内容修改。保留独立 presentation 边界，目标使用有限字号/主题配置与确定性渲染，不启动规划能力，不改需求、计划身份和确认状态。这项 UI/导出演进可与框架重构分开验收。

TurnCommit版本复验、原子提交和回执保留唯一提交口，不随“极简”一起删除

迁移顺序与每一步的退出条件

  1. 建立行为基线

    锁定现有需求授权、候选采用、旧结果拒绝、精确编辑、确认与失败保留测试。记录已知差异，不把现有测试通过当新模型能力通过。

  2. 统一工具注册与结果协议

    先让旧运行器通过 Registry 分发，保持既有角色行为。验收：11 个主工具逐项可追到定义、实现、权限与测试。

  3. 抽出共享 Runner

    先迁移只读 Research，再迁移其余能力，最后迁移 Main。用 profile 控制工具和终止合同，禁止长期保留两套分叉循环。

  4. 收敛终止、预算与事件

    移除隐藏复核调用，确定性处理不可恢复错误，关键与非关键事件分流。验收最后一次调用、工具额度耗尽、取消与迟到结果。

  5. 收紧工作区与提交合同

    采用集合验证失败不改变选择状态；版本/幂等/原子持久化回归通过。使用同一业务库格式的独立测试副本，不改写正式数据库。

  6. 清理旧路径，再评估上线

    移除重复循环、字符串分发和失效配置；文档同步。真实模型与地图验证需要单独明确授权和费用边界；不自动切生产。

不是免费重构：先承认代价，再决定是否做

收益假设真实代价 / 风险控制方式
只有一套执行机制，更容易学习与测试抽象过度会把业务流程藏进 hook只保留准备请求、工具预检、回合终结等少数显式接口
独立查询可并行，可能降低查询等待预算竞态、限流和事件乱序原子预占、有界并发、统一快照、结果按源顺序记录
工具定义与实现一致迁移时遗漏角色权限或参数消费每个工具的注册/权限/错误/副作用契约测试
失败状态更清楚历史消息和任务状态存在兼容成本内部新协议，边界适配旧状态，不批量改历史记录
核心代码更小总文件数可能增加，模型质量不会自动提高用依赖清晰度、重复机制和行为验证衡量，不以文件数量或 Agent 数量为目标

必须通过的验收门槛

  • 需求候选只能来自合法授权；历史原话、工具结果、想法卡片不能扩大写权限。
  • 主/子循环复用同一 Runner，但各自工具白名单、上下文和结束合同不混淆。
  • Schema 验证失败零外部执行；请求尝试与实际外部调用分别记录，不把计数含义混用。
  • 重复不可恢复错误由程序停止；预算耗尽后零新增模型请求。
  • 终止集合验证失败不改变已采用集合；假设、未知条件和错误依赖不能提交。
  • 新消息、计划变化、需求变化、超时与重启后，旧结果都不能覆盖当前状态。
  • 存储故障注入时，需求、行程、消息和回执不得部分发布；同一幂等键不重复提交。
  • trace/UI 订阅失败不能覆盖正常业务提案；关键提交失败必须明确返回。
  • 离线契约/回归测试与真实模型语义评测分开；通过结构检查不宣称路线现实可行。
  • 聊天布局不变；HTML/guide 渲染作为下游独立任务，不绑进 Agent 内核重构。
首版明确不做：动态插件加载、第三方任意 hook、分布式多 worker、自动多 Agent 群聊、任意代码执行、复杂执行中 steering、模型自建工具，以及为了“更智能”无限增加复核 Agent。

我推荐的不是更复杂的框架，
而是更少的执行机制，配上更清楚的业务边界。

第一步最值得做的是 Tool Registry + 一致的 ToolResult：它能直接解决你读代码时遇到的“定义在哪、操作在哪、怎么绑定”的困惑。共享 Runner 随后迁移，Workspace 与 Commit 则始终作为安全底座保留。
