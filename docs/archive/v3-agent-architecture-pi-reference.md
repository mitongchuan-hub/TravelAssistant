# V3 旅行 Agent 架构讨论：借鉴 Pi，减少不必要的复杂度

> 历史架构讨论：下文旧 `agent_client.py/task_runtime.py/main_input.py/agent_roles.py` 已删除。当前分别使用 `backend/app/agents/entrypoints.py`（请求入口）、`travel_runtime.py`（主循环）、`inputs/context.py`（输入投影）和 `roles.py`（角色）；模型请求与轨迹位于 `model_client.py`、`trace.py`。

- 日期：2026-10-28
- 工作分支：`v3.0.0`
- 状态：研究与讨论稿，尚未批准实施
- 目的：解释 Pi 的架构经验、当前旅行 Agent 的复杂度来源，以及 V3 值得验证的简化方向。
- 非目标：本文件不是全量重写计划，不表示已经决定删除子 Agent 或替换现有提交机制。

## 1. 核心结论

当前系统的问题不只是代码长，也不只是子 Agent 多，而是模型循环、上下文构造、领域规则、运行状态、供应商协议和候选提交在不同层交叉出现。

Pi 最值得借鉴的不是 coding 工具，而是以下原则：

1. 一个通用的模型—工具执行循环。
2. 会话持久化、运行态和模型上下文各有明确边界。
3. 工具定义、校验和执行使用统一流水线。
4. 模型供应商差异不泄漏到业务运行时。
5. 保持执行核心小；有需要再增加能力，不预先建立复杂编排框架。

V3 建议以“单旅行 Agent + 领域工具 + 独立业务提交”为验证基线。只有在质量、上下文隔离或并行任务上证明有收益时，才增加子 Agent。

**单 Agent 是待验证的架构假设，不是本次研究已经证明的质量结论。**

## 2. 研究依据与范围

### 2.1 Pi 版本

本次研究使用官方仓库固定快照：

```text
仓库：earendil-works/pi（原 badlogic/pi-mono 入口重定向至此）
提交：a92283056d915c758799fcd904948ff0cb42628c
提交日期：2026-10-27
```

应避免将经典 pi-mono 的接口与当前实现混用。例如，当前实现采用 transcript-first 上下文，工具默认支持并行，不能直接照搬旧版本的独立 systemPrompt 结构或串行调度印象。

以下 Pi 说明基于官方源码与文档。当前项目说明基于只读架构梳理；未进行性能基准、模型效果对照或完整死代码分析。

### 2.2 项目现状的准确表述

当前主链路是 task execution，但其专业能力执行仍依赖保留旧接口和兼容角色视图的 `TravelAgentRuntime`。

不宜简单说成“legacy 和 task_execution 两套完整产品链路仍在并行运行”，也不宜说成“四个子 Agent 各有一套独立运行时”。更准确的是：

> 主执行循环与专业能力循环分别实现，新编排器依赖一个职责较多、保留兼容逻辑的能力运行时。

## 3. Pi 的整体架构

```text
交互入口
TUI / print / JSON / RPC / SDK
                 │
                 ▼
           AgentSession
      会话级执行、恢复与应用协调
          ┌──────┴───────────┐
          ▼                  ▼
        Agent          SessionManager
  内存状态、队列、中断    持久化会话树、活动分支、
  与执行生命周期         权威上下文重建
          │
          ▼
      Agent Loop
 模型调用 → 工具执行 → 结果回填
          │
          ▼
         pi-ai
   统一消息、流协议、供应商适配
          │
          ▼
       模型供应商
```

### 3.1 各层职责

| 层 | 主要职责 | 不应混淆的边界 |
| --- | --- | --- |
| `Agent` | 内存消息与运行状态、steering/follow-up 队列、中断、事件 | 不是磁盘会话数据库 |
| `agent-loop` | 请求模型、执行工具、推进 turn 与队列 | 不负责 coding 业务持久化 |
| `AgentSession` | 将执行与会话记录、扩展、压缩、重试、界面生命周期连接 | 不是另一套 provider 实现 |
| `SessionManager` | JSONL 会话树、分支和上下文重建 | 不等于无限增长的模型输入数组 |
| `pi-ai` | 供应商适配、统一消息和流式结果 | 不解释具体业务规则 |

### 3.2 会话历史与模型上下文分离

Pi 会话持久化采用 JSONL 树形记录，条目包含 ID 和父节点关系，当前节点决定活动分支。

- 继续旧节点可以形成分支。
- 会话可以恢复或复制为新会话。
- 压缩插入摘要，后续模型上下文使用摘要替代较旧消息。
- 原始历史条目仍保留，不因压缩被物理删除。

因此：

```text
持久化历史 ≠ Agent 内存消息 ≠ 当前模型请求上下文
```

`AgentSession` 在准备请求时可以从 `SessionManager` 重建最终上下文。直接修改 `agent.state.messages` 不等于修改持久化历史。

当前 CLI 仍使用 JSONL `SessionManager`；新增的 `durable` 是独立实验性 harness，不能据此认为会话存储已被替换。

### 3.3 通用执行循环

以下是概念流程，不是 Pi 源码的逐行翻译：

```text
接收用户消息
    ↓
准备本次请求上下文
    ↓
供应商适配与模型流式调用
    ↓
收集完整模型回复
    ↓
存在工具调用？
    ├─ 是：校验并执行工具，追加工具结果
    └─ 否：按结束策略判断是否完成
    ↓
处理继续、队列、中断或错误
```

当前上下文是 transcript-first：系统指令、工具声明也通过结构化消息表达。对旅行项目的借鉴重点是“可重建上下文与统一执行”，不是必须复制它的全部消息协议。

### 3.4 工具流水线

Pi 工具不仅有名称和 Schema，也绑定执行器及运行时策略。概念上执行顺序为：

```text
解析工具名
  → 参数准备与 Schema 校验
  → 前置策略检查
  → 执行与进度更新
  → 结果后处理
  → 工具结果消息
```

未知工具、参数错误和部分执行错误会成为可供模型处理的工具错误结果。中断、权限拒绝和不完整模型输出不能因此被当成可随意重试的普通业务失败。

Pi 当前默认支持并行工具执行，但并不意味着所有业务操作都适合并行。旅行项目需要单独定义副作用和依赖规则。

### 3.5 事件与完成边界

需要区分：

1. 模型层：文本、思考、工具参数的流式增量。
2. Agent 层：消息、turn、工具执行的生命周期。
3. 会话层：自动重试、压缩恢复、最终静止。

Pi 的低层 `agent_end` 后仍可能发生恢复工作，`agent_settled` 才表示会话不会继续自动推进。

旅行项目对应也应区分：

```text
模型停止生成 ≠ 工具执行结束 ≠ 业务保存成功 ≠ 后台任务完成
```

事件订阅也不天然提供事务或顺序保证：需要等待持久化完成的步骤，应使用明确的 awaited 调用或屏障，而不是依赖普通 UI 监听器。

### 3.6 扩展与安全

Pi 扩展是进程内 TypeScript 模块，可以注册工具、命令、事件处理器和 UI 行为。它不是自动提供权限隔离的沙箱。

对我们而言：

- 可以借鉴工具注册和生命周期边界。
- 当前不需要照搬完整插件平台、热加载、终端 UI 或分发机制。
- 工具可扩展不等于工具安全，服务器权限和业务授权仍需独立执行。

## 4. 当前旅行 Agent 架构

### 4.1 主调用链

```text
HTTP / Store 建立可信请求
    ↓
后台任务捕获业务快照
    ↓
generate_task_proposal
    ↓
TaskExecutionRuntime
    ↓
TravelAgentRuntime 执行专业能力
    ↓
TurnWorkspace 收集并选择候选
    ↓
TurnCommit / Store 校验与提交
```

逻辑角色包括：

- `main_execution`：理解任务、选择能力、管理任务和追问、采用候选。
- `requirements_capability`：整理需求。
- `research_capability`：查询外部数据并形成证据。
- `planning_capability`：生成行程。
- `revision_capability`：修改行程。
- `display`：将已保存正文转为展示 HTML。

### 4.2 值得保留的设计

#### 模型候选与正式保存隔离

```text
register ≠ adopt ≠ commit
```

模型生成成功不代表已保存，候选被选择也不代表可以绕过提交校验。

#### 服务端维护权威边界

已有机制检查用户归属、请求代次、需求版本、行程版本、授权和依赖等。模型运行时不直接持有 Store 写权限。

#### 展示与事实隔离

HTML 是行程正文的派生展示。样式修改不应变成事实修改，展示生成失败也不应破坏已保存行程。

#### 模型输入投影

`main_input.py` 已体现“给模型所需视图，不直接暴露整个存储对象”的正确方向。问题是其他读取路径尚未完全统一。

### 4.3 主要复杂度来源

| 问题 | 现状 | 简化方向 |
| --- | --- | --- |
| 两套执行循环 | 主循环与能力循环分别处理模型、工具和终止 | 统一执行器 |
| 可变状态耦合 | 能力调用保存、恢复多项 runtime 字段 | 显式传入上下文，减少共享可变状态 |
| 供应商协议泄漏 | 业务运行时访问供应商响应对象 | 统一内部模型结果 |
| 上下文读取重复 | 投影模块和能力 runtime 各自构造读取结果 | 统一读取与模型可见投影 |
| 领域规则混入循环 | 天气、路线、需求、编辑和展示与调度混杂 | 规则放到领域工具或服务 |
| 工具规则分散 | Schema、分发、权限、候选种类定义在多处 | 统一工具定义，明确校验层职责 |
| 兼容接口负担 | 多种角色命名和旧接口仍被保留 | 追踪调用后删除无用兼容层 |
| 主子调用转换 | 工作单、上下文、摘要和终止合同反复包装 | 验证单 Agent 能否直接完成 |

不能把不同层的校验全部认定为重复：Schema 校验、工具权限和提交并发校验解决的是不同问题。应消除规则漂移，而不是取消纵深防护。

## 5. V3 建议的最小目标

```text
HTTP / 后台任务入口
          │
          ▼
     TravelSession
加载状态、准备上下文、记录会话
          │
          ▼
       AgentLoop
统一模型—工具执行循环
          │
          ▼
       旅行工具
 ├─ read_context
 ├─ query_weather
 ├─ search_places / search_food
 ├─ query_route
 ├─ propose_requirements
 ├─ propose_itinerary
 └─ 必要的确认与展示操作
          │
          ▼
    业务校验与提交
权限、版本、范围、数据有效性、原子保存
```

`TravelSession`、`AgentLoop`、`propose_requirements` 和 `propose_itinerary` 是建议的概念或名称，不表示已经存在这些实现。

这张图是职责边界，不要求每个方框都增加一个类、一个包或一套抽象接口。

### 5.1 为什么以单 Agent 为基线

当前行程生成近似为：

```text
主 Agent 理解用户
  → 调用 draft_itinerary
  → 规划 Agent 再接收工作单和上下文
  → 查询工具并生成正文
  → 包装能力结果返回主 Agent
  → 主 Agent 选择候选
```

待验证的新路径：

```text
旅行 Agent 理解用户
  → 读取需求和行程
  → 查询必要资料
  → 生成正文
  → 提交行程候选
  → 服务器校验与保存
```

提交工具不再隐式启动另一个 LLM，而是处理结构化业务输入。

预期可以减少任务转述、重复输入、能力结果包装和跨 Agent 引用传递。但单 Agent 也可能带来上下文变大、工具选择困难或规划质量下降，必须通过测试评估。

### 5.2 何时保留子 Agent

只有具备明确收益时保留，例如：

- 独立研究任务需要隔离大量上下文。
- 可并行的研究工作显著降低耗时。
- 专用规划上下文经过对照测试确实提高质量。
- 权限或输出合同需要独立隔离。

即使保留子 Agent，也复用同一个执行循环，使用显式输入输出，不通过保存和恢复共享 runtime 字段模拟隔离。

## 6. 多轮对话状态设计

### 6.1 三类状态

| 状态 | 示例 | 生命周期 |
| --- | --- | --- |
| 会话历史 | 用户/模型消息、工具调用和结果 | 跨轮保留，可压缩模型视图 |
| 旅行业务状态 | 正式需求、当前行程、确认状态、版本 | 由业务存储维护 |
| 执行状态 | 预算、取消信号、工具进度、临时候选 | 当前运行期间 |

原则：

- 对话摘要不能覆盖正式需求。
- 模型声称已保存不能代替提交回执。
- 工具结果被折叠不能导致授权信息丢失。
- 运行失败不能损坏已经保存的行程。
- 恢复对话不等于自动重放有副作用的工具。

### 6.2 上下文构建

每轮提供有限的决策信息：

```text
当前用户消息
+ 当前有效需求
+ 当前行程标识与必要内容
+ 最近对话或摘要
+ 与本轮相关的未完成事项
```

大对象通过有权限检查的 `read_context` 按需读取。首包、详情读取和工具结果应遵循同一套身份与版本语义。

无需首版就实现 Pi 的完整会话树。先明确历史保存、当前上下文和业务状态的关系；分支、fork 等功能有产品需求再增加。

## 7. 工具与模型接口建议

### 7.1 最小工具定义

```python
Tool(
    name="query_weather",
    schema=...,
    handler=...,
)
```

先使用显式注册表。只有重复需求出现后，才增加复杂的策略元数据和插件机制。

### 7.2 模型结果归一化

业务循环只接收类似以下内部结构：

```text
ModelTurn
  ├─ text
  ├─ tool_calls
  ├─ usage
  └─ stop_reason / completion_status
```

供应商对象、Chat Completions/Responses 差异、流式参数拼接和协议重放留在模型适配层。

不完整或被截断的工具调用不得执行。工具参数解析成功不代表整个模型响应完整。

### 7.3 并行与写入

- 独立、只读查询可以考虑并行。
- 需求变更、行程修改、确认和保存按依赖排序。
- 是否已产生副作用必须影响重试策略。
- 初版优先清楚的执行顺序，而不是复杂调度器。

候选是在工具调用内提交，还是在本轮结束时统一提交，属于后续合同设计事项。本研究不默认取消现有本轮原子提交语义。

## 8. 保留、合并、待删除清单

### 保留

- 权限与旅行归属校验。
- 需求和行程版本校验。
- 修改范围限制。
- 候选与正式状态分离。
- 取消、超时、失败关闭与原子提交。
- 正文事实与展示样式隔离。
- 外部数据证据和来源可追踪性。

### 合并

- 模型—工具循环。
- 工具参数校验和执行流水线。
- 模型可见上下文读取与投影。
- 供应商协议转换。
- 预算扣减与执行终止语义。

### 验证后删除

- 无调用方的旧角色视图和兼容接口。
- 无质量或隔离收益的子 Agent。
- 同一信息的多层摘要与包装。
- 依靠共享字段保存/恢复的能力切换。
- 描述同一进度、却无不同生命周期价值的重复状态。

以上是目标清单，不是已经确认可直接删除的符号清单。删除前仍需追踪调用方和测试覆盖。

## 9. 建议的验证路径

### 第一步：固定现有基线

保留当前工作区修改，记录现有功能与模型调用轨迹。不要一边重写一边改变需求规则和页面排版。

### 第二步：实现一个最小闭环

```text
提供需求
  → 查询天气/地点/路线
  → 生成行程
  → 下一轮提出修改
  → 保存新版本
```

先接已有领域服务与提交边界，不同时重写 Store、展示系统和所有协议。

### 第三步：对照测试

至少覆盖：

| 场景 | 检查重点 |
| --- | --- |
| 需求完整，生成行程 | 日期、地点、节奏与约束是否正确 |
| 需求不足 | 是否只问关键问题，不无依据生成 |
| 单项修改 | 未授权内容是否保持不变 |
| 多事项请求 | 查询、需求和修改是否遗漏 |
| 条件或假设咨询 | 是否错误写入正式状态 |
| 精确文本编辑 | 是否保持其他原文 |
| 外部工具失败 | 是否如实告知，不编造事实 |
| 取消和超时 | 是否停止后续副作用 |
| 并发修改 | 是否拒绝过期版本覆盖 |
| 仅改展示风格 | 是否不改变行程事实与确认状态 |
| 恶意网页或工具文本 | 是否被当成数据而非授权指令 |

对比指标包括：功能正确率、规划质量、模型调用次数、token、总耗时，以及核心代码是否实际减少。

### 第四步：依据结果决定子 Agent 去留

单 Agent 达到质量与安全要求后再迁移。如果某一类任务退化，保留该专业 Agent，并让它复用统一执行器，而不是为了追求数量少而强行合并。

### 第五步：删除旧路径

在调用方迁移、回归测试通过后，再删除旧循环和兼容接口。迁移过程不应永久演变为第三套运行时。

## 10. 不建议做的事

1. 不为了学 Pi 引入全部包或更换项目语言。
2. 不先搭建通用插件平台、EventBus、热加载或 durable 工作流框架。
3. 不将所有数据塞入一个巨型 Session 对象。
4. 不把复杂度从两个大文件搬成几十个没有清楚边界的小类。
5. 不只新增统一执行器，却永久保留所有旧循环。
6. 不因为 Pi 工具可直接修改本地文件，就让模型直接写业务数据库。
7. 不把子 Agent 数量减少当成质量提升的证据。
8. 不在架构重构时擅自调整现有页面排版。

## 11. 后续实施前仍需明确的事项

- 单 Agent 提交的行程合同：纯文本、结构化内容，还是沿用现有 artifact。
- 复合请求的事务边界，以及独立成果如何在部分失败时保留。
- 会话历史如何与现有聊天消息、模型运行记录关联，避免双份权威来源。
- 主模型同时理解、查询和规划时的质量与成本。
- 展示任务的完成状态是否与正文保存状态分别呈现。
- 旧接口的实际调用方及可删除范围。

这些问题影响具体实现，但不妨碍先通过最小闭环验证架构方向。
