# 四意图工作流与当前行程

意图只有闲聊、查询、规划、修改，需求收集放在规划内部。每趟旅行只有一份当前行程，生成和修改覆盖当前方案。已删除PlanVersion、历史保存、历史上下文、恢复接口及版本工具。

| 配置名 | 执行方式 | 默认思考 |
| --- | --- | --- |
| main | 无工具意图识别LLM | low |
| chat | 无工具闲聊LLM | low |
| research | 查询Agent Loop，只读及资料查询 | low |
| planning | 规划Agent Loop，需求整理/检查及查询 | medium |
| revision | 修改Agent Loop，读取当前方案、需求整理及查询 | medium |
| revision/explain | 只读解释Loop | low |
| display | 无工具LLM，将当前原文转换为展示JSON | low |

聊天确认属于修改意图，识别后直接通过程序确认当前快照，不再请求业务模型或让它填写目标ID。确认只改变状态，原文、JSON和依据保留；后续修改形成当前草案。用户要求旧方案恢复时说明仅保留最新版。

五组必填创建信息保存到独立需求档案。规划/修改调用需求工具整理本轮原话，生成前检查完整性。只补充需求不自动生成；等待补充目标独立持久化。清空聊天保留需求和当前方案，作废未完成任务。

规划提示词按共同原则、动作流程、规划方法、查询策略和交付核对组织。页面的有效需求检查、本轮update_requirements返回的ready结果可复用；只记录、记录后查询和生成分别遵守授权。规划明确抵离/接驳与人为预留、主线/备选、天气和入住条件、房间数与预算单位，不靠结尾声明代替具体条件。共同规则同时用于查询与修改；文字仍没有自动语义验收，模型自检不等于程序检查。见[提示词重组与实际验收](planning-prompt-redesign-20261013.md)。

完整文字先通过Store的需求revision及完整计划快照检查，保存原文/需求快照/工具依据并完成主任务。独立后台display任务随后检查结构、日期和原文绑定，空闲时只补齐展示字段；业务处理期间延后发布，转换失败保留原文并可单独重试。旧任务或不同方案的迟到结果不能回写。

SQLite快照schema_version=5，保存独立展示记录，旧快照升级前自动备份；当前plans仍只保留最新版，不维护plan_versions。原数据迁移和最新行程验证见[简化验收](latest-itinerary-only-20261010.md)，流程与限制见[当前架构](agent-architecture-current.md)。
