# 五意图工作流与当前行程

> 策略状态（2026-10-16）：本文主体是当前默认 `legacy` 角色实现。目标 `task_execution` 的 A–C 已实现并通过当前离线回归，未通过真实模型质量、误写、时延和回滚验收，也未默认启用。统一配置名是 `TRAVEL_AGENT_EXECUTION_STRATEGY=legacy|task_execution`，默认 `legacy`，execution task 提交后策略固定。阶段 D 的离线基础设施见[实施记录](task-execution-implementation-20261016.md)。

2026-10-15：`main` 新建同城行程，住宿地址是唯一必填。`roles(mode)`按旅行模式加载提示词：同城使用 `city_planning.txt`、`city_rules.txt`、`city_examples.txt` 和 `city_revision.txt`，完整旅行继续使用原文件。同城需求工具不要求车站抵离字段，允许日期/人数/预算未知；已确认住宿进入每个节点的当前需求上下文及可信地点目录。详见[同城游玩](city-outings-20261015.md)。以下五组需求与旧少样本说明适用于保留的完整旅行模式，意图及保存权限两者共用。

2026-10-16：意图为闲聊、查询、纯需求整理、规划、修改。纯需求整理独立为 `requirements`，仅接管新增、修改、撤销需求及必要澄清；混合更新并查询、生成、修改仍在 planning/revision 中同步需求，不让所有消息串行增加一个角色。每趟旅行只有一份当前行程，生成和修改覆盖当前方案。已删除PlanVersion、历史保存、历史上下文、恢复接口及版本工具。

| 配置名 | 执行方式 | 默认思考 |
| --- | --- | --- |
| main | 无工具意图识别LLM | low |
| chat | 无工具闲聊LLM | low |
| requirements | 纯需求Agent Loop，仅读取上下文、更新/检查需求 | low |
| research | 查询Agent Loop，只读及资料查询 | low |
| planning | 规划Agent Loop，需求整理/检查及查询 | medium |
| revision | 修改Agent Loop，读取当前方案、需求整理及查询 | medium |
| revision/explain | 只读解释Loop | low |
| display | 无工具LLM，将当前原文转换为展示JSON | low |

上表是 legacy 配置，不是新 main 执行 Agent 的最终模型/思考配置。新链的 main 将使用受限工具和共享预算；具体模型与思考强度须由50×3真实模型任务集对照质量、误写、调用数和端到端p50/p95后决定，当前没有真实语义验收结论。

聊天确认属于修改意图，识别后直接通过程序确认当前快照，不再请求业务模型或让它填写目标ID。确认只改变状态，原文、JSON和依据保留；后续修改形成当前草案。用户要求旧方案恢复时说明仅保留最新版。

五组必填创建信息保存到独立需求档案。新旅程欢迎消息根据实际保存值确认城市、抵离安排、人数与预算；必填完整时提示可直接生成，必去地点、忌口和节奏属于可选补充。缺项判断复用规划的required_information，不用固定补充清单。

意图识别、闲聊及业务Agent都接收当前需求档案和旅行备注，需求revision标明快照依据。意图识别与闲聊同时接收实际缺项列表，近期聊天仍限制为8条；长对话或清空聊天不移除需求输入。询问已有需求进入无工具闲聊，需求变更、生成、修改和外部查询继续遵守原有业务权限。已保存需求优先于历史值、欢迎文案和旧缺项提示；字段未记录时如实说明。

纯补充需求直接路由到 `requirements/update_requirements`，旧 `planning/update_requirements` 输出在分类边界兼容归一。新角色使用独立短提示词，不附加要求交付行程的规划规则；工具仅有 `read_context`、模式对应的 `update_requirements` 和 `check_requirements`。没有实际需求审阅时不能直接结束并声称已保存；明确澄清可直接返回 `needs_input`。最终文本不写入行程，工具候选变更仍经 Store 校验保存。不得猜测未知信息，也不因缺少可选信息要求填齐问卷。

规划/修改仍调用需求工具处理混合请求，生成前检查完整性。已授权生成的缺项回答继续走 `planning/generate`；明确只记录、先不生成的需求消息清除旧等待目标，纯需求澄清不创建生成授权。等待补充目标独立持久化。清空聊天保留需求和当前方案，作废未完成任务。

规划按需求与授权、关键查询、主线和时间、餐次与预算、自然交付组织。`planning_examples.txt`保留2个合成少样本：接驳成功后的正常生成、路线失败与未知酒店的条件草案。纯需求示例改由 `requirements.txt` 的简短场景说明承担。示例不代表当前旅行事实；最新需求和查询结果优先。各角色继续共用本轮预算和取消检查，不重置预算或增加重复抽取。

页面需求检查和本轮工具ready可复用。生成时已匹配的抵达点/核心必去点与离开点分别检查接驳，遗漏允许一次补查；餐饮候选查询等待关键接驳优先完成。路线失败、预算不足与尚未查询分别记录，重名候选不猜测，局部修改不强制重查全部路线。

生成和整体修改直接返回完整原文，经需求与计划快照检查后保存。独立的review模型、语义检查Schema、按审阅结果重新生成和失败拦截已删除，配置中不再有review角色。规划提示词中的事实边界、餐次覆盖与预算分配规则继续使用；自然语言预算不再由复核模型提取金额后计算上界，不能把保存成功当作预算或事实验证。删除前实验保留用于追溯；见[交付改进与当前状态](planning-delivery-20261014.md)。

新方案先写简短主线、预算判断及关键条件，再用Markdown分隔线衔接完整逐日安排。聊天仅提取原文开头作预览，完整文字不截断、不重新摘要；不符合概览结构时沿用完整段落预览。历史提示词及验证保留在[此前提示词重组记录](planning-prompt-redesign-20261013.md)。

完整文字先通过Store的需求revision及完整计划快照检查，保存原文/需求快照/工具依据并完成主任务。独立后台display任务随后检查结构、日期和原文绑定，空闲时只补齐展示字段；业务处理期间延后发布，转换失败保留原文并可单独重试。旧任务或不同方案的迟到结果不能回写。

当前代码的 SQLite 快照 schema_version=6，保存版本化会话目标、请求代次与独立展示记录；旧快照升级前自动备份。代码已实现迁移，不表示当前实际运行库已经重启或完成迁移。当前 plans 仍只保留最新版，不维护 plan_versions。原数据迁移和最新行程验证见[简化验收](latest-itinerary-only-20261010.md)，流程与限制见[当前架构](agent-architecture-current.md)。

## 任务执行角色边界（已实现，通过当前离线回归）

`task_execution` 不再把 main 限制为无工具意图分类器。目标 main 只选择受限基础能力和终止提案；`prepare_requirements` 是正式需求候选的唯一专业入口，research 只读，draft/revise 只产生候选，confirm 绑定用户已看到的方案。专业能力的 `ok` 不代表整轮完成或已保存，`needs_input` 也先回到 main，使其可以完成其他独立事项后再追问。

跨轮保留的是通用会话目标和活动追问，不是 requirements/planning 等角色分支状态。Runtime/Store 校验引用、权限、条件、依赖、预算和版本，并由 `commit_turn` 形成真实回执；自然语言充分性仍需真实模型评测，不能靠 Schema 自证。A–C 代码已经实现并通过当前离线回归，但默认仍为 legacy，以上不能解释为生产新链已经启用或完成真实语义验收。
