# TravelAssistant 一天学习计划

目标：用一天掌握项目的完整流程、核心设计和真实边界，能应对旅行 Agent 项目的主要面试追问。

适用范围：当前仓库中的 TravelAssistant。当天先集中学习现有实现，RAG、DeepSeek Harness 和具身 Agent 留作后续扩展。

建议时间：09:00—21:00，约 8 小时有效学习，其余时间用于吃饭、休息和整理。

### 14:00—15:15：攻克任务一致性

这是当天优先级最高的技术模块。

阅读：

- [app/agents/agent_protocol.py](../../app/agents/agent_protocol.py)：`RequestContext`、`PlanBasis`、`Artifact`。
- [app/workflow/turn_workspace.py](../../app/workflow/turn_workspace.py)：`register_artifact`、`adopt`、`finish`。
- [app/workflow/turn_commit.py](../../app/workflow/turn_commit.py)：`_turn_conflict`、`commit_turn`、`_persist_staged_turn`。
- [app/workflow/tasks.py](../../app/workflow/tasks.py)：新请求、幂等和旧任务替代。

先理解这句话：

> 模型产生候选，主 Agent 选择候选，服务端验证当前状态后才保存。

手动推演：

1. 任务 A 开始查路线，捕获当前请求和业务基线。
2. 用户发送新聊天消息，形成任务 B，旧活动任务被替代。
3. A 的网络请求较晚返回。
4. A 检查取消状态，或在提交前发现当前基线不匹配。
5. A 的过期结果不能发布为当前方案。

注意真实行为：同一旅行已有活动任务时，新的页面 plan/revision 请求通常会被拒绝；新聊天请求可以替代旧活动任务。不要笼统说所有修改都并行运行。

需要理解的检查：

| 检查项 | 主要作用 |
| --- | --- |
| request ID、原消息、任务状态 | 确认还是同一次有效请求 |
| requirements revision | 确认需求没有在执行期间改变 |
| workflow revision、sequence、epoch | 确认会话和请求代次仍然有效 |
| PlanBasis | 确认当前行程业务内容和状态没有变化 |
| artifact 来源、依赖和证据 | 防止采用无效或不属于当前请求的候选 |
| staged persistence | 保存成功后再发布内存状态，避免半提交 |

**产出：** 用具体例子完成 3 分钟“旧结果保护”讲解。

- [ ] 理解候选与已保存效果的区别。
- [ ] 理解基线检查。
- [ ] 能脱稿解释旧任务场景。
