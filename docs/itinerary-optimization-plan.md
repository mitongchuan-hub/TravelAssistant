# 行程页面优化计划

> 文档状态：2026-10-02
>
> 目标：让手机端用户更快看懂当前行程、当天安排和需要处理的事项。计划只涉及行程页展示与交互，不改变旅行数据、模型生成协议和版本保存逻辑。

## 已优化

| 项目 | 当前状态 | 现有表现 |
| --- | --- | --- |
| 每日行程时间线 | 已优化 | 已按 Day 分组，并按时间展示游览、用餐、交通、住宿和休息。 |
| 行程类型标识 | 已优化 | 每条安排显示“游览、用餐、交通、住宿、休息”等类型。 |
| 餐食信息展示 | 已优化 | 用餐项目显示餐食推荐、菜系、预算和预约状态；有真实门店信息时可以继续展示来源和门店细节。 |
| 旅行准备区 | 已优化 | 衣物与装备、住宿已经从每日时间线中独立出来，单独展示。 |
| 单项调整入口 | 已优化 | 每条安排都有“让 Agent 调整这项”的折叠入口和修改表单。 |
| 版本历史 | 已优化 | 版本记录放在行程内容之后，可以展开查看并恢复历史版本。 |
| 顶部摘要卡 | 已优化 | 已集中显示“行程概览”、旅行日期、实际已安排天数和行程安排数量。 |
| 计划状态与版本信息 | 已优化 | 摘要卡不展示内部版本编号、版本数量或确认功能；历史版本仍保留在页面底部。 |

## 未优化

| 优先级 | 项目 | 当前问题 | 计划调整 |
| --- | --- | --- | --- |
| 高 | 计划说明折叠 | 计划概览、已满足需求、待确认和风险目前连续展开，占用较多手机屏幕空间。 | 默认显示简短概览，详细内容用折叠区域展开。 |
| 高 | 行程详情层级 | 每条安排的原因、备注、对应偏好和调整表单默认全部可见，长行程阅读成本高。 | 默认保留时间、标题、地点、时长和类型；原因、备注、偏好和调整表单改为点击后展开。 |
| 高 | 待确认事项操作化 | 待确认目前只是文字列表，用户需要自己返回聊天页寻找补充入口。 | 每条待确认事项提供“去聊天确认”入口，并带上对应问题。 |
| 中 | 每日标题增强 | 当前有 Day、日期和主题，但没有当天安排数量、待确认数量等快速信息。 | 增加当天安排数量和必要的提醒，同时保持标题简洁。 |
| 中 | 用餐视觉层级 | 已有餐食字段，但餐食项目与普通安排的视觉区分还不够明显。 | 突出餐食类型、菜品、预算和真实门店来源，避免把街区级推荐误认为已预约门店。 |
| 中 | 交通和休息弱化 | 交通、休息与景点的视觉重量接近，长时间线中主线不够突出。 | 降低交通和休息的卡片权重，用更轻的标签和连接线表现。 |
| 中 | 修改操作抽屉化 | 当前修改表单嵌在每条安排下方，多个项目展开时页面会变长。 | 改为底部抽屉或统一编辑面板，保留当前安排上下文。 |
| 中 | 计划数据覆盖提示 | 计划标题可能写“6 天 5 晚”，但实际 `days` 数据可能只有 5 天，页面没有提示缺少返程日。 | 以实际 `days` 数量为准；发现日期覆盖不完整时显示“返程日尚未安排”等明确提示。 |
| 低 | 移动端操作固定区 | 确认计划、继续修改等操作目前随页面内容滚动，长行程中需要返回顶部。 | 评估增加底部或顶部的轻量固定操作区，避免遮挡时间线。 |

## 已取消

| 项目 | 决定 |
| --- | --- |
| “已满足 X 项”数量标签 | 不做。保留具体内容，不增加数量汇总标签。 |
| “待确认 X 项”数量标签 | 不做。保留具体待确认事项，不增加数量汇总标签。 |
| “风险 X 项”数量标签 | 不做。保留具体风险说明，不增加数量汇总标签。 |

## 推荐实施顺序

### 第一阶段：先改善手机端阅读

1. 折叠计划说明。
2. 折叠单条安排的详细说明。
3. 强化每日标题和时间线层级。

### 第二阶段：提升处理效率

1. 为待确认事项增加聊天入口。
2. 将单项修改改为统一底部抽屉。
3. 评估固定操作区。

### 第三阶段：补充数据提示

1. 检查标题日期与实际 `days` 是否一致。
2. 对缺少返程日、日期待确认和安排不完整的情况增加页面提示。
3. 检查餐食推荐、预算和门店来源的展示边界。

## 验收标准

- 手机宽度 390px 时，打开行程页后首屏能看到目的地、日期、行程概览、实际已安排天数和主要安排数量。
- 用户能在一次滑动内看到第一个完整日程安排。
- 长行程中，默认页面不会展开所有原因、备注和修改表单。
- 用户可以从待确认事项直接进入聊天补充信息。
- 用户可以在不丢失当前阅读位置的情况下提交单项修改。
- 行程实际天数与日期范围不一致时，页面明确提示缺少的日期或返程安排。
- 不显示“已满足 X 项”“待确认 X 项”“风险 X 项”三类数量标签。
