# 行程页面产品化优化计划

> 文档状态：2026-10-02
>
> 目标：让用户在手机端快速看懂行程安排，按需查看细节，并能从待处理事项直接进入聊天。页面文案面向旅行者，避免暴露 Agent、版本确认和内部数据处理方式。
>
> 范围：只涉及行程页面的展示和交互。旅行数据、模型生成协议、计划保存和版本数据继续由现有后端负责。

## 当前页面结构

```text
行程页
├── 行程概览
│   ├── 旅行日期
│   ├── 已安排天数
│   └── 行程安排数量
├── 安排说明
│   ├── 整体安排
│   ├── 已纳入行程
│   ├── 待处理事项
│   └── 出行提醒
├── 行前清单
│   ├── 衣物与装备
│   └── 住宿区域
├── 日期导航（位于第一天行程上方，吸顶，点击跳转）
├── 每日时间线
│   ├── 时间、类型、标题、地点、时长
│   ├── 查看安排说明
│   └── 调整 → 底部编辑面板
└── 版本记录
```

## 已优化

| 项目 | 当前状态 | 当前产品表现 |
| --- | --- | --- |
| 行程摘要 | 已优化 | 顶部使用“行程概览”，显示旅行日期、实际已安排天数和行程安排数量。 |
| 内部状态隐藏 | 已优化 | 页面不展示“草案”、确认计划按钮、版本编号和版本数量等内部状态。 |
| 安排说明层级 | 已优化 | 使用“安排说明”作为统一标题，详情按“整体安排、已纳入行程、待处理事项、出行提醒”分组。 |
| 说明折叠 | 已优化 | 说明面板默认收起，点击后只展开当前分组，不增加数量统计标签。 |
| 待处理事项入口 | 已优化 | 每条待处理事项都有“去聊天确认”入口，并把对应问题自动带入聊天输入框。 |
| 每日时间线 | 已优化 | 按 Day 分组，展示游览、用餐、交通、住宿和休息等安排。 |
| 时间线信息层级 | 已优化 | 默认只展示时间、类型、标题、地点和时长。餐食细节、偏好、原因、备注和修改入口收进“查看安排说明”。 |
| 单项调整 | 已优化 | 每条安排直接显示“调整”，打开统一底部面板；面板显示目标标题、时间和地点。输入按条目暂存，失败可继续编辑，成功后返回对应安排。 |
| 餐食信息 | 已优化 | 餐食详情保留推荐菜品、菜系、预算和预约状态，放在对应安排的详情中。 |
| 行前清单 | 已优化 | 衣物与装备、住宿区域独立展示，使用状态标签和清单卡片。 |
| 行前清单视觉 | 已优化 | 卡片统一使用雾蓝主题，手机端单列，桌面端双列。 |
| 版本记录 | 已优化 | 版本记录放在页面末尾，低频操作不干扰当前行程阅读。 |
| 日期覆盖提示 | 已优化 | 摘要卡会在实际日期未完整安排时提示“返程日尚未安排”等信息。 |
| 每日标题信息 | 已优化 | 日期、天序与当天主题分层显示，右侧保留安排数量；未知日期明确显示“日期待定”。 |
| 日期导航 | 已优化 | 在安排说明、行前清单之后，第一天行程上方提供横向日期导航，滚动时吸顶；点击定位到当天，手动滚动同步选中状态。只展示已有行程天，不补造缺失日期。 |
| 时间轴阅读 | 已优化 | 起止时间上下排列并顶部对齐，以细线和圆点连接安排，移除拉满卡片高度的时间色块。 |
| 时间线视觉层级 | 已优化 | 交通、休息和住宿使用更轻的卡片层级，游览和用餐保持主要视觉权重。 |
| 餐食结论展示 | 已优化 | 餐食推荐、预算和预约信息收在安排详情中，推荐内容位于详情前部。 |

## 未优化

| 优先级 | 项目 | 当前问题 | 计划调整 |
| --- | --- | --- | --- |
| 高 | 行前清单标题 | 部分模型生成的事项标题仍然偏说明文档，例如“10月初济南穿衣建议”。 | 将可提炼的标题转成结论式表达，例如“薄外套 · 舒适运动鞋”；无法可靠提炼时保留原文。 |
| 中 | 版本记录表达 | 版本记录仍使用 v1、v2 等内部版本语言，普通用户不一定需要理解版本机制。 | 后续评估改成“历史调整记录”，只显示调整原因和时间；恢复功能保留在详情中。 |

## 已取消或不展示

| 项目 | 决定 |
| --- | --- |
| 确认计划按钮 | 不在行程页面展示。后端确认接口和历史数据暂时保留。 |
| “草案”状态 | 不在行程页面展示。 |
| “确认后，后续调整会作为新草案记录” | 不展示。 |
| 顶部版本编号和版本数量 | 不展示；版本记录仍放在页面底部。 |
| “已满足 X 项”数量标签 | 不做。保留具体内容，不增加数量汇总标签。 |
| “待确认 X 项”数量标签 | 不做。当前使用“待处理事项”逐条展示。 |
| “风险 X 项”数量标签 | 不做。当前使用“出行提醒”逐条展示。 |
| “待你确认”文案 | 不使用，统一使用“待处理事项”和“去聊天确认”。 |

## 产品交互规则

- 页面首屏先展示旅行日期和实际已安排内容，不展示模型或版本内部术语。
- 说明类内容默认收起，用户点击后只打开当前需要查看的分组。
- 时间线默认服务于“下一步去哪儿”，细节服务于“为什么这样安排”和“如何修改”。
- 点击“去聊天确认”时，聊天输入框自动带入对应问题，用户可以直接发送或编辑后再发送。
- 单条安排的调整按钮直接打开底部面板，显示目标标题、时间、地点；无额外说明的条目也可调整。
- 关闭面板和刷新页面后，修改意见在当前浏览器标签页内按旅行与条目暂存；提交成功后清除该条草稿并回到对应安排。
- 提交中显示真实的等待状态并防止重复提交。服务返回失败时保留输入；网络中断不能断言保存失败，提示先检查行程再重试。
- 日期导航支持点击和随滚动选中，定位后日期标题不能被导航遮挡。
- 日期范围与实际安排天数必须以页面提示为准，不能只依赖行程标题。
- 真实门店、评分、预算和预约状态需要区分来源；街区级推荐不能显示成已预约门店。

## 后续实施顺序

1. 将可提炼的行前准备标题改成行动结论。
2. 评估历史版本记录的用户文案，逐步弱化 v1、v2 等内部术语。

## 本轮验证

- 页面交互使用独立测试页面与模拟提交结果，不调用真实模型或写入用户行程。
- 覆盖 320px、390px、430px 和桌面宽度下的时间轴、日期导航、无日期单日和空行程。
- 检查日期跳转、滚动选中、键盘焦点、关闭返回、不同条目的草稿隔离和刷新恢复。
- 检查提交目标 ID、防重复提交、模型失败/断网反馈，以及成功后返回原条目。

## 验收标准

- 390px 手机宽度下，首屏能看到目的地、日期、实际已安排天数和行程安排数量。
- 长行程打开时，安排详情、修改表单和说明文字默认收起。
- 每条时间线安排默认可以在一眼内看清时间、标题、地点和时长，时间列不随卡片拉伸。
- 日期导航跳转和手动滚动均更新选中状态，目标日期标题不被吸顶栏遮挡。
- 点击“调整”即可编辑当前条目，关闭时恢复焦点和阅读位置；失败保留输入，成功后返回对应安排。
- 用户可以从待处理事项直接进入聊天，并看到自动带入的问题。
- 展开安排详情后，餐食、偏好、原因和备注关系清晰；调整入口独立展示，无需嵌套展开。
- 行前清单卡片在手机端单列、桌面端双列，状态标签使用统一雾蓝主题。
- 日期范围与实际安排天数不一致时，页面明确说明缺少的日期或返程安排。
- 页面不出现确认计划、草案状态和顶部版本数量等已取消功能。
- 页面不显示“已满足 X 项”“待确认 X 项”“风险 X 项”三类数量标签。

## 浏览器验证命令

使用项目 Python 环境执行，Node 环境需可加载 Playwright 和 Chrome：

```powershell
python tests/browser/render_itinerary.py .cache/itinerary-ui-check
node tests/browser/itinerary_browser.cjs .cache/itinerary-ui-check
```

测试使用临时端口提供模拟页面，覆盖成功跳转和失败返回；不连接运行中的 8000 服务、不调用模型、不写入业务数据库。
