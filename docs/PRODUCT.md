# Product

## Platform

web

## Product Purpose

TravelAssistant 帮助用户以已确认的住宿为起终点，生成、理解和调整同城游玩路线。下一阶段以“一天路线拿起来能用”为核心，不以聊天轮数、Agent 数量或生成长文作为产品目标。

## Users

待验证的首要场景：已订好住处、来到陌生城市，希望少查攻略、少自行拼接路线的人。此定位是产品假设，尚未经真实用户研究确认。

## Operating Context

产品面向手机浏览器，工作区采用最多 430px 的单列布局。用户直接进入私人聊天，通过消息提供住处、日期、出行方式和游玩想法，Agent 在聊天中查询并核对住宿位置、生成或修改路线；网页 Agent 将保存的行程制作成 HTML/CSS 攻略。点击“攻略”进入预览，顶部左侧返回聊天、右侧下载当前网页；支持打开完整网页和下载；重试、确认通过聊天消息提出。宽屏浏览器沿用同一手机交互。旧行程链接打开聊天内攻略，旧结构化方案保留只读文字。必填开始日期和游玩天数，支持多天同城游玩。

## Capabilities and Constraints

### 当前阶段：聊天是唯一业务操作入口

用户通过发送消息表达需求整理、住宿匹配、生成、修改、确认和清空意图，不再选择业务入口；攻略网页统一使用默认“轻松、愉悦”风格。前端保留想法墙查看和管理自由要求；Agent 输入中，结构化字段与想法条目统一放在 requirements 下，具有相同约束地位，既有存储保留。想法页生成快捷操作发送聊天消息。新建对话直接进入聊天，缺少住宿、日期不妨碍普通对话；Agent 按需追问并通过地图查询匹配住宿，重名在聊天中澄清。攻略预览、打开和下载作为查看结果的能力保留。

聊天可自由讨论非旅行话题，并按需读取上下文、查询天气、地点、餐饮和路线。地图使用筛选后的高德原生地点搜索、详情、步行、驾车和公交工具；餐厅使用地点搜索与详情，模型收到原始结果，后端另外保存规范化证据。API 与 Agent 共用地图连接及地点解析。天气继续使用独立服务与 `query_weather`，不切换为高德天气。主 Agent 同时拥有 `submit_changes`，根据本轮用户原话决定是否提出变更；只读回复和查询不会自动保存业务数据。变更须经过服务器原话、证据、账号与版本校验并原子保存，保存行程或调整网页后触发后台攻略生成。模型仅在普通回复中写出的路线仍是建议文字。

模型环境不再携带用户业务入口选择；历史任务类型保留为服务端兼容信息。日期展开列表与真实住宿地图标识统一放在 requirements.known，不另传 travel_window；每日出门和返回时间使用已有需求字段，未知不补默认。聊天不设固定查询顺序或调用次数，保留有限超时、取消、账号隔离、工具参数与真实地点校验；工具调用串行执行，重复无效调用安全结束。

以下规则约束聊天中的实际业务写入；历史数据保留。

- 住宿地址与地图匹配是同城生成的必要条件；出行日期和游玩天数必填；人数、预算和偏好可选，未知不补默认事实。
- 完整文字是主数据，后台 HTML 是派生展示，网页生成失败不能丢失正文；纯视觉调整保持行程、证据、计划 ID 和确认状态。
- 地点信息以查询证据为依据，区域、重名及证据不足保持待核实；生成网页只复用原文明示的 HTTPS 导航链接。
- 路线耗时是查询时估算，地点匹配不代表开放、票价、预约或遮雨条件已核实。
- 保留旧旅行、聊天、想法、需求与当前方案；本轮不增加预订、支付、社区、跨城新能力或额外 Agent。
- 前端采用 Vue 3、TypeScript、Vite、Vue Router 和 Pinia；后端采用 FastAPI JSON API 与 SQLite，仍按单后端进程运行。主界面不再使用 Jinja2；生成攻略保留独立受限 HTML 文档。

### 同城规则

- 住宿须经过实际地图匹配，城市与坐标由程序保存可信来源；重名时选候选，不接受客户端或模型自报坐标作为依据。
- 按已确认日期与天数，每天从同一住宿出发并返回，规划限于住宿城市。住宿变更后重新匹配，旧方案保留并标记依据变化，不自动重排。
- 日期和天数缺少时先补充，不默认今天或一天；人数、预算和每日时刻缺失不补成用户事实。用户给定时段约束与模型建议时段分开说明。
- 默认游玩费用包括餐饮、市内交通和门票，不重复计算住宿与跨城交通；用户自定义费用范围优先。区分人均与全员总额、预算额度与已核实费用，人数未知不擅自乘算。
- 按实际游玩窗口覆盖相关餐次，不机械补三餐；已有含餐、自带餐、预约或固定安排不重复规划。饮食禁忌、必去与明确排除应作为约束保留。
- 局部调整只处理用户授权范围，未指定内容应保持不变；开放式修改仍由模型返回完整正文，程序不保证其他段落逐字不变。用户明确指定字句的精确编辑另有严格规则。目标或条件不清先澄清，不把解释、假设咨询或待确认条件当作写入授权。
- 查询首末接驳只证明有查询尝试，不证明正文采用正确或现实可执行；地点查询结果也不能扩展成未经核实的设施、遮雨、营业或票价承诺。

### 历史记录

保留历史聊天、想法、需求和当前方案，不批量转换旧正文、展示或模式标记。继续生成或调整前，在聊天中完成住宿地图匹配；成功保存后才转入同城流程。历史抵离字段只用于读取原存档，不作为当前规划输入。

### 明确非目标

不提供预订支付、社区、多版本方案恢复，也不把未来地图路况、排队和班次当作确定事实。`task_execution` 使用单个旅行 Agent 的增删改查循环，不再委派四个业务子 Agent；不新增 TurnSession 或模型管理的任务编排。`submit_changes` 是一轮一次的终止提交，变更包全有或全无；后台 HTML 展示独立保留。保存成功或网页就绪均不等于事实、预算或路线质量通过验收。

## Brand Commitments

沿用 TravelAssistant 名称、中文界面与现有雾蓝视觉体系。用户已确认 V2 用 Agent 生成的攻略网页替换固定行程界面；聊天保留既有视觉，攻略统一使用默认“轻松、愉悦”风格，并保持全部业务事实与未知限定。

## Evidence on Hand

离线结构检查与真实模型语义评测必须分开。历史样本曾暴露无依据设施、雨备和餐次覆盖问题，不能据此宣称当前已解决；自动测试通过也不代表路线现实可执行。当前测试入口见[README](../README.md#当前测试入口)，历史报告从 Git 追溯。没有独立第二模型复核，保存成功或网页就绪不证明事实、预算与可执行性验收。合成示例与截图必须注明为测试展示。

## Product Principles

1. 提升路线实用性；聊天保持连续，攻略展示可以按用户偏好生成。
2. 未知诚实可见，不用精确外观伪装已核实事实。
3. 修改基于用户看到的当前方案，旧请求不能覆盖新状态。
4. 失败可恢复，已有正文、需求和用户输入不因后台失败丢失。
5. 先完成一个真实场景的闭环，再按使用证据扩展。

## Accessibility & Inclusion

核心操作有明确文字、键盘焦点和可读状态；手机窄屏不横向溢出，不用颜色单独表示核实状态，尊重减少动态效果设置。
