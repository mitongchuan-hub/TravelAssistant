# Product

## Platform

web

## Product Purpose

TravelAssistant 帮助用户以已确认的住宿为起终点，生成、理解和调整同城游玩路线。下一阶段以“一天路线拿起来能用”为核心，不以聊天轮数、Agent 数量或生成长文作为产品目标。

## Users

待验证的首要场景：已订好住处、来到陌生城市，希望少查攻略、少自行拼接路线的人。此定位是产品假设，尚未经真实用户研究确认。

## Operating Context

产品面向手机浏览器，工作区采用最多 430px 的单列布局。用户通过创建表单填写住处、日期、天数和出行方式，确认地图住宿后进入私人聊天；后续通过消息维护需求正文，Agent 按固定创建资料查询地点、生成或修改路线；网页 Agent 将保存的行程制作成 HTML/CSS 攻略。点击“攻略”进入预览，顶部左侧返回聊天、右侧下载当前网页；支持打开完整网页和下载；网页重新生成、确认通过新的聊天消息提出。宽屏浏览器沿用同一手机交互。旧行程链接打开聊天内攻略，旧结构化方案保留只读文字。必填开始日期和游玩天数，支持多天同城游玩。

## Capabilities and Constraints

### 当前阶段：创建先表单，后续 Agent 操作通过聊天

不提供服务端失败任务重试或旧 plan/revision 恢复执行。失败提示为“本次处理未完成，请重新发送消息。已有内容已保留。”；可将文字移回草稿，但发送始终是新 chat/request/task/用户消息身份。仅网络送达不确定的 pending 复用同一 request_id 确认与去重，undo 的网络幂等恢复另行保留；HTML 结构纠错及 429 备用不受影响。历史任务与 retry_of 只读保留。

新建入口保留住宿、出行方式、开始日期和天数四项必填信息；地图重名时先选候选，确认后才创建旅行并进入聊天。打开或取消表单不创建空记录，不自动生成行程。四项资料及其派生城市、结束日期与真实住宿位置在创建后固定，聊天和旧编辑接口均不能修改；空白对话创建接口退出。其他要求统一维护一份需求正文，聊天与想法页编辑共同更新它，不再维护想法卡片、分类或逐卡覆盖状态。想法页外壳、导航及发送生成消息的快捷入口保留；正文编辑用版本检查防覆盖。行程正文独立保存，攻略统一使用默认“轻松、愉悦”风格，预览、打开和下载能力保留。

聊天按意图受理旅行咨询与合理辅助，不提供完整菜谱、独立解题、代码、诗歌等非旅行实质内容；旅行餐饮偏好和餐厅查询合法，歧义先澄清。可按需读取上下文、查询天气、地点、餐饮和路线。地图使用筛选后的高德原生地点搜索、详情、步行、驾车和公交工具；餐厅使用地点搜索与详情，模型收到原始结果，后端另外保存规范化证据。API 与 Agent 共用地图连接及地点解析。天气继续使用独立服务与 `query_weather`，不切换为高德天气。主 Agent 同时拥有 `submit_changes`，根据本轮用户原话决定是否提出变更；只读回复和查询不会自动保存业务数据。变更须经过服务器原话、证据、账号与版本校验并原子保存，保存行程或调整网页后触发后台攻略生成。模型仅在普通回复中写出的路线仍是建议文字。

Agent 读取固定创建资料、完整需求正文及需求版本，不另维护偏好字段、卡片列表或段落 ID。需求正文以完整替换维护，允许清空，同值不推进版本；只保存要求不自动生成行程。正文实际变化使旧行程依据过期，同轮明确授权更新需求并生成时，新行程绑定更新后的完整需求快照，两者原子保存。人数、预算和健康状况未知不推断；未说明的规划偏好可使用暂定假设，不作为用户事实或保存到需求正文。聊天不设固定查询顺序或调用次数，保留有限超时、取消、账号隔离、工具参数与真实地点校验；工具调用串行执行，重复无效调用安全结束。

以下规则约束聊天中的实际业务写入；历史数据保留。

- 住宿地址与地图匹配是同城生成的必要条件；出行日期和游玩天数必填。人数、预算和偏好不再由独立字段维护，用户在聊天中提及时按原话处理，不补默认事实。
- 完整文字是主数据，后台 HTML 是派生展示，网页生成失败不能丢失正文；纯视觉调整保持行程、证据、计划 ID 和确认状态。
- 地点信息以查询证据为依据，区域、重名及证据不足保持待核实；生成网页只复用原文明示的 HTTPS 导航链接。
- 路线耗时是查询时估算，地点匹配不代表开放、票价、预约或遮雨条件已核实。
- 保留旧旅行、聊天、想法、需求与当前方案；本轮不增加预订、支付、社区、跨城新能力或额外 Agent。
- 前端采用 Vue 3、TypeScript、Vite、Vue Router 和 Pinia；后端采用 FastAPI JSON API 与 SQLite，仍按单后端进程运行。主界面不再使用 Jinja2；生成攻略保留独立受限 HTML 文档。

### 同城规则

信息足够且已授权生成时直接查询规划，不逐项追问兴趣。默认仅补未说明部分：暂按首次到访视角、适中节奏，有条件兼顾代表景点、本地美食、特色街区及文化，不硬凑；行程一句话说明实际假设，不认定用户首次到访、不写入需求正文。安全、范围、同城及固定创建资料始终优先，明确偏好和禁忌高于默认。地理就近减少无意义折返，但预约、开放条件及指定顺序优先；现实条件冲突须说明并让用户取舍，不假装全部满足。此为 prompt 行为约束，离线合同仅验证注入，真实模型语义仍待评审。

- 住宿须经过实际地图匹配，城市与坐标由程序保存可信来源；重名时选候选，不接受客户端或模型自报坐标作为依据。
- 按创建时固定的日期与天数，每天从同一住宿出发并返回，规划限于住宿城市；创建后不更换住宿、日期或交通方式，需要改变这些信息时新建旅行。
- 旧旅行基础资料缺失时不默认今天或一天，也不通过聊天补齐；保留聊天、需求和文稿维护，但不能生成或重排行程。人数、预算和每日时刻缺失不补成用户事实。用户给定时段约束与模型建议时段分开说明。
- 默认游玩费用包括餐饮、市内交通和门票，不重复计算住宿与跨城交通；用户自定义费用范围优先。区分人均与全员总额、预算额度与已核实费用，人数未知不擅自乘算。
- 按实际游玩窗口覆盖相关餐次，不机械补三餐；已有含餐、自带餐、预约或固定安排不重复规划。饮食禁忌、必去与明确排除应作为约束保留。
- 局部调整只处理用户授权范围，未指定内容应保持不变；开放式修改仍由模型返回完整正文，程序不保证其他段落逐字不变。用户明确指定字句的精确编辑另有严格规则。目标或条件不清先澄清，不把解释、假设咨询或待确认条件当作写入授权。
- 查询首末接驳只证明有查询尝试，不证明正文采用正确或现实可执行；地点查询结果也不能扩展成未经核实的设施、遮雨、营业或票价承诺。

### 历史记录

保留历史聊天、需求、行程正文与合法网页，不批量重写原方案。旧存档升级前自动备份；schema10将旧想法按原顺序确定性合并为唯一需求正文，不调用模型改写或截断，也不继续双写卡片。缺少正文依据的旧行程不补当前正文伪造有效状态；原有过期或未知状态不能提升。升级清空不兼容的旧撤销条目并推进版本，保留已消费操作回执。历史SQL任务回执与摘要不重写。

### 明确非目标

不提供预订支付、社区、任意多版本方案跳转，也不把未来地图路况、排队和班次当作确定事实。`task_execution` 使用单个旅行 Agent 的增删改查循环，不再委派四个业务子 Agent；不新增 TurnSession 或模型管理的任务编排。`submit_changes` 是一轮一次的终止提交，变更包全有或全无；后台 HTML 展示独立保留。保存成功或网页就绪均不等于事实、预算或路线质量通过验收。

## Brand Commitments

沿用 TravelAssistant 名称、中文界面与现有雾蓝视觉体系。用户已确认 V2 用 Agent 生成的攻略网页替换固定行程界面；聊天保留既有视觉，攻略统一使用默认“轻松、愉悦”风格，并保持全部业务事实与未知限定。

## Evidence on Hand

离线结构检查与真实模型语义评测必须分开。历史样本曾暴露无依据设施、雨备和餐次覆盖问题，不能据此宣称当前已解决；自动测试通过也不代表路线现实可执行。当前测试入口见[README](../README.md#当前测试入口)，历史报告从 Git 追溯。没有独立第二模型复核，保存成功或网页就绪不证明事实、预算与可执行性验收。合成示例与截图必须注明为测试展示。

## Product Principles

1. 提升路线实用性；聊天保持连续，攻略展示可以按用户偏好生成。
2. 未知诚实可见，不用精确外观伪装已核实事实。
3. 修改基于用户看到的当前方案，旧请求不能覆盖新状态。
4. 失败可恢复，已有正文、需求和用户输入不因后台失败丢失。
5. 先完成一个真实场景的闭环，再按使用证据扩展。

## Accessibility & Inclusion

核心操作有明确文字、键盘焦点和可读状态；手机窄屏不横向溢出，不用颜色单独表示核实状态，尊重减少动态效果设置。

### 最近三次 Agent 修改撤销

撤销入口暂时隐藏，不开放新的前端撤销操作；已提交撤销的网络不确定恢复仍保留。后端保留最近三次实际 Agent 变更的恢复机制，只恢复需求正文、行程及来源匹配且安全的 HTML，不修改固定创建资料；聊天保留。手动编辑清空旧撤销链。终止只阻止尚未提交的工作，不自动撤回已提交修改。
