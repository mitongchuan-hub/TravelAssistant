# 旅行规划 Agent 测试集 v1

本目录只定义测试数据和验收标准，不包含执行器、模型调用或测试结果。目标是评估当前“主 Agent + 需求 / 查询 / 规划 / 调整 + 文字行程”链路，而不是复测行程 JSON 格式。

用例位于 [cases.json](cases.json)，共 36 条。所有城市、日期、人物、需求和行程均为合成测试资料，不对应业务数据库中的旅行。固定评测当前日期为 2026-10-08，旅行日期保持绝对日期，避免“明天”随执行时间漂移。

## 数据约定

- `setup`：运行前创建的独立旅行，引用 `fixtures`；各用例重新创建，不能共享写入后的状态。
- `tool_fixture`：工具返回情境，引用 `tool_fixtures`；涉及失败、歧义或证据冲突时必须使用指定情境，不能依赖当天真实搜索碰巧触发。
- `steps`：顺序执行的输入与预期；`chat` 是用户聊天，其他 action 是页面或系统动作。普通步骤完成后才进入下一步，并发用例按 `when` 执行。
- `checks`：该步骤必须满足的行为与内容。`forbidden`：任一出现就判该步骤失败。没有固定答案措辞，除明确要求原样替换或问题前缀外按语义评审。
- `priority`：P0 是硬约束、权限、事实或数据安全；P1 是核心功能与方案质量。
- `layer`：agent 为模型业务表现，integration 为模型与保存/任务结合的表现。并发与版本保护需要系统状态证据，不能仅凭回复文字判定。
- `expected_plan_versions_delta`：相对该步骤开始时新增版本数量；null 表示本用例不锁定数量。需求修订、任务状态、工具日志仍需独立检查。

`fixtures` 是测试情境说明，后续执行器需映射到现有 Store/API，不是给产品新增的数据协议。文字行程 fixture 中的内容须逐字保存为原方案。`tool_fixtures` 是受控证据，不是真实旅行事实，绝不可作为对外推荐来源。

## 判定方法

每条 `checks` 单独标记通过、失败或无法判断；记录相应回复段落、工具事件或状态快照作为证据。全部必需检查通过且没有 `forbidden` 才算用例通过。工具 fixture 未满足、无法注入时间或没有状态观察能力时标记“未执行 / 环境阻塞”，不要计为通过。

评估方案质量时，再按下面五项分别给 0～2 分：0 为不满足，1 为部分满足，2 为充分满足。不适用记 N/A，不用一个主观总分掩盖硬约束失败。

1. 约束遵守：日期、首末日窗口、必去、忌口、预算口径。
2. 可执行性：顺序、接驳、休息和用餐合理，估算与已知事实分开。
3. 证据可靠性：来源、适用范围、时效和未知表达清楚。
4. 修改忠实度：只改授权内容，保持其他安排与待核实事项。
5. 表达完整性：中文完整文字方案，关键取舍清楚，能够独立阅读。

P0 的硬约束失败单独列出；业务通过率、系统通过率、各类失败率分别统计。不要把“接口 200”“任务 succeeded”或“模型说已保存”视为方案合格。开放时间、交通耗时、预算等事实的正确性必须与工具证据对照。

## 未来执行时的记录要求

每次记录 case ID、数据集版本、执行时间、模型/端点标识（不含密钥）、代码 commit 与是否有未提交修改、当前日期、输入/输出、工具 fixture、工具事件、需求/行程/版本前后快照及评审结论。耗时分别记录整轮时间、模型请求时间、每次工具的 `seconds`；委派包含子 Agent 耗时，不能与子工具相加后当成整轮耗时。

建议结果字段：`case_id`、`status`、`check_results`、`quality_scores`、`evidence_paths`、`elapsed_seconds`、`model_requests`、`tool_events`、`failure_reason`。结果另存，不覆盖 cases.json。

后续可先执行 P0，再执行 P1。真实模型存在波动，同一固定情境建议独立重复三次，分别报告每次结果。测试集初版创建时没有调用模型；首次单次执行结果见[2026-10-08测试报告](../../../docs/travel-agent-evaluation-20261008.md)，其中明确区分真实模型结果、受控系统测试与环境阻塞。所有执行应使用内存 Store 或独立临时数据库，不向 8000 业务服务发送测试请求。
